## 1. Verified capability facts (the ground the design stands on)

### 1.1 What the public API actually fills, measured per field type

One hand-built PDF, four field types, each written through the public API, saved, reloaded:

| Field type | Accessor found | Write call | Returns | Actually persisted? |
|---|---|---|---|---|
| **Text** (`/Tx`) | `as_text_field_mut()` | `set_value("…")` | `Ok` | **Yes.** `/V` correct, reads back after reload. |
| **Checkbox** (`/Btn`, no radio flag) | `as_checkbox_field_mut()` | `set_checked(true)` | `Ok` | **No.** See §1.2. |
| **Radio** (`/Btn` + flag 32768) | `as_radio_button_field_mut()` | `set_checked()` | `Ok` | **No.** See §1.2. |
| **Combo box** (`/Ch` + flag 131072) | **none mutable exists** | — | — | **Unreachable:** `as_combo_box_field()` is `&self` only; there is no `as_combo_box_field_mut`. |
| **List box** (`/Ch`, no combo flag) | **none mutable exists** | — | — | **Unreachable**, same reason as combo. |

`field_values()` reads all five back correctly, so **reading is complete and safe**; the gap is
entirely on the write side and entirely on button and choice fields.

### 1.2 The defect that shapes the whole phase: `set_checked` returns `Ok` and changes nothing

Measured, not inferred. Two independent confirmations:

1. **In memory.** `c.is_checked()` is `Ok(false)` before `set_checked(true)` and `Ok(false)`
   immediately after it, with the call returning `Ok(())`.
2. **In the saved bytes.** The checkbox dictionary after the call reads
   `/V(Yes)` — a **string** — where the PDF specification requires a **name** `/V /Yes`, and no
   `/AS` key is written at all. PDFium itself then reads the field back as `false`.

The cause is visible in the crate source, `pdf/document/page/field/private.rs`:
`set_value_impl` calls `FPDFAnnot_SetStringValue_str(…, "V", value)`, and `set_string_value`
does the same for the key it is given. A `*StringValue` FFI call cannot write a PDF *name*.
`set_checked`'s appearance-stream branch additionally calls `set_string_value("AS", …)`, so even
`/AS` would be malformed for the same reason.

**This is the single most important fact in this document.** A phase that wraps
`set_checked` and reports success would ship a checkbox that visibly does not tick, while the
backend said it had. That is the refusal-integrity class this programme already treats as fatal
in redaction, and D-F2 below makes it structurally impossible here.

**Ruled 2026-11-14: forms cannot ship a ticking checkbox through the crate, so we write the
dictionary ourselves.** The ruling, in the words it was given: *"plan our own write of `/AS` and a
Name-typed `/V`, with a measured test that the checkbox actually ticks in a real viewer, and record
the upstream defect as a fact with the crate and version."* That is D-F3 below. The upstream defect
is recorded here as a **fact about a specific version, not a general claim**:

> **Upstream defect, recorded 2026-11-14.** `pdfium-render` **0.8.37** (the version resolved by
> `pdfium-render = "0.8"` with feature `sync` in this tree's `Cargo.lock`, checksum `6553f660…`),
> in `src/pdf/document/page/field/private.rs` and `.../field/checkbox.rs`. Both `set_value_impl`
> and `set_string_value` write through `FPDFAnnot_SetStringValue_str`, and a `*StringValue` FFI
> call can only produce a PDF **string**, never a **name**. So `PdfCheckboxField::set_checked`
> and `PdfRadioButtonField::set_checked` — which return `Ok(())` — produce, depending on branch:
>
> - **no `/AP` appearance streams** (`checkbox.rs:118`): `set_value_impl("Yes")`, giving
>   **`/V(Yes)` as a string and no `/AS` key at all**. *This is the measured case in §1.2, and the
>   case the probe's saved bytes show.*
> - **with `/AP`** (`checkbox.rs:110`): additionally `set_string_value("AS", "/Yes")`, giving
>   `/AS(/Yes)` — the slash preserved inside a **string**, so `/AS` is malformed too, and
>   `/V(/Yes)` likewise.
>
> Either way the value is the wrong PDF type and PDFium reads the field back as `false`. Measured
> two ways in §1.2 (in-memory `is_checked()` unchanged; saved bytes malformed). This is a fact
> about **0.8.37 only** — no other version was tested, and nothing here asserts whether it is
> fixed upstream.

The consequence for the plan is structural: **no form code path may call `set_checked` and treat
`Ok` as success**, including through a `?`. W4 implements buttons with our own writer.

Two further observations from the same probe, both relevant to §4:

- `radio.rs` ships **`println!` debug output** (`*** [radio] set_checked()`, `??? ap: {:#?}`)
  that prints into whatever process calls it. On a GUI app's stderr that is noise at best.
- `set_value_impl` and `set_string_value` also stamp `/M` (modification date) on every write,
  whether or not the caller wanted one.

### 1.3 No `/AcroForm` fixture exists — the real first work item

`src-tauri/tests/fixtures/` holds **54 PDFs**. Searching every one of them for `/AcroForm`,
`/Widget`, `/FT` or `/T ` — **raw and after decompressing every stream**, so that a compressed
object stream cannot hide a hit — returns **zero files**.

So nothing form-related can be tested today. This is named as work item **W1** in §7 rather than
discovered in the middle of implementation, and it is the reason the phase cannot be driven by
fixtures until it is done.

The fixtures that do exist are for text editing (MCID, XObject, Type0, transform), which is why
this gap was never hit before: forms are the first phase whose subject is a PDF structure the
corpus has no example of.

### 1.4 Save discipline that forms must not bypass

`editor/save.rs` implements **P2-D2**: a save writes a *new* file named `"{stem} (edited N).pdf"`
through a temp file and an atomic rename, and never clobbers the original. Any form save goes
through it. §1.2 and §1.4 together mean a form fill is **read with PDFium, written by our own
`lopdf` path, and saved by `P2-D2`** — not `doc.save_to_bytes()` straight to the user's file.

### 1.5 What "fill" has to write, per the PDF specification

Not measured (nothing to measure yet), stated because D-F1 depends on it: a button field needs
`/V` **and** `/AS` as **names** drawn from its `/AP /N` state keys, which are **not**
standardised — real producers emit `/Yes`, `/On`, `/1`, per-option names. A choice field needs
`/V` plus `/I` for list selection. Any writer that hardcodes a state name is wrong for some
real file; `set_checked`'s hardcoded `/Yes` is exactly that mistake.

**In:**
`/Tx` single- and multi-line text; `/Btn` checkbox; `/Btn` radio groups; `/Ch` combo and list

annotation keys, JavaScript actions, calculation order, `/CO`); save through P2-D2; FDF and
XFDF **form-data** import/export paired with P3.1's existing XFDF annotation code.

**No longer in, by ruling of 2026-11-14:** Fill & Sign (report §2.4) moved to its own phase,
**P3.3a**, recorded in `docs/P3-PLAN.md` §1 as the phase after forms. It shares no machinery with
AcroForm and would double this phase's hand-test surface — see D-F8 and §6.3.

**Out — decided here, not deferred by omission:**

| Question | Ruling | Why |
|---|---|---|

## 3. Frozen decisions

### D-F1 — The writer is ours. PDFium reads; `lopdf` writes.

Filling reads through PDFium (field discovery, type, flags, current values, `/Opt` lists,
`/AP` state names) and writes through the existing `lopdf` path. Justification is measured, not
preferential: PDFium's own write path produces a malformed `/V` for buttons (§1.2), so it cannot
be the writer for the types that matter. **Consequence accepted:** every write is a dictionary
edit we own, so every write needs its own guard, and `P2-D2` stays the only save path.

### D-F2 — A fill either persists or fails; it never reports success without a persisted change.

After writing, the new bytes are **reloaded through PDFium** and the field's value re-read. If the
value did not change to the requested one, the operation fails with a refusal naming the field.
No caller can report "filled" on the strength of a return value. **This is the ruling that
exists because `set_checked` returns `Ok` without acting** (§1.2); it is invariant **I-F1**.

### D-F3 — `/V` and `/AS` are written as **names** taken from the field's own `/AP /N` keys.

The state name is discovered per field, never assumed. If `/AP /N` has no key other than `/Off`,
the field is reported as unfillable rather than written with an invented name. A checkbox whose
producer used `/On` fills; one whose producer used `/Yes` fills; neither is special-cased.

**Ruled 2026-11-14 (the answer to §1.2): we write `/AS` and a name-typed `/V` ourselves, and a
test measures that the box actually ticks in a real viewer.** `lopdf` represents a PDF *name* as
`Object::Name`, which is a different object type from `Object::String` — that type distinction
*is* the fix, and it is why the write cannot go through the crate's string-based FFI. Concretely:

- `/V` is written as `Object::Name(state)` where `state` came from the field's own `/AP /N`.
- `/AS` is written as `Object::Name(state)` on the widget annotation that carries the appearance.
- Both go through the D-F4 in-place edit; nothing else in the dictionary is re-emitted.
- D-F2's reload check reads the field back through PDFium and requires the *requested* state,
  which is what makes a silent non-tick impossible at our own API boundary.

**The measurement the ruling requires, and why the reload check is not sufficient on its own.**
PDFium agreeing with our write proves the dictionary is well-formed enough for PDFium; it does
**not** prove a viewer *draws* the tick. So W4 carries a separate, explicitly-named test —
`the_checkbox_ticks_in_a_real_viewer` — whose evidence is **rendered pixels**, not a value read:

1. fill the checkbox on a fixture carrying `/On` (the `/Yes` fixture is the control),
2. save through `P2-D2`,
3. reopen the saved file and **rasterise the widget's rectangle** through the existing PDFium
   render path,
4. assert the rendered region differs from the `/Off` render of the same rectangle by more than a
   stated pixel threshold, and that the `/Off` render of the same field is unchanged.

A test that only re-read `is_checked()` would pass on a file whose `/AS` points at a missing
appearance stream — it would be a green pass wearing a label. The pixel comparison is the
observable a user actually gets.

### D-F4 — Values this build does not model are preserved byte-for-byte at the dictionary level.

The writer edits keys in place and re-emits the surrounding object untouched. Unmodelled keys
(`/AA` JavaScript actions, `/CO` calculation order, `/Tabs`, producer-private keys) survive. If a
structure cannot be preserved by an in-place edit, the operation refuses instead of rewriting it.
Rationale: a form filler that silently strips a document's JavaScript or calculation order is a
data-loss tool, and the loss would be invisible to the user.

### D-F5 — Save goes through `P2-D2` and says so in the UI.

A filled form saves as a new `(edited N)` file, exactly like a text edit. No "overwrite original"
affordance is added in this phase. Rationale: §1.4, plus the fact that a form fill is often done
on a document the user cannot re-obtain.

### D-F6 — Refusals are typed and named, in the same shape P3.2 used.

At minimum: `FieldUnfillable` (no usable `/AP` state, or a locked/read-only flag),
`XfaNotSupported`, `FieldTypeUnsupported` (signature fields, unknown `/FT`), `ValueRejected`
(the reload in D-F2 did not agree). Each carries the field name and the reason; none is a bare
string, and none is silently skipped.

### D-F7 — Read-only and permission state is respected, and the reason is reported.

A field flagged read-only (`Ff` bit 1) or inside a document whose protection forbids
form-filling is refused with the flag named, never written. P3.2 already models permissions; this
reuses that model rather than re-deriving it. **Open for ruling:** whether a `P=3`-certified
document (annotation-permitted, as certified in the 1.2.0 hand-test) permits form fill. The
certification semantics say "annotations"; whether a field value counts is the question. Until
ruled, **fill is refused on a certified document** and the refusal says why — refusing is the
recoverable direction.

### D-F8 — Fill & Sign is **not in this phase**; it is P3.3a, and stays visual when it lands.

**Ruled 2026-11-14: Fill & Sign is its own phase, recorded in `docs/P3-PLAN.md` as the phase
after forms.** The reasoning that carried: a visual signature shares **no machinery** with
AcroForm — it is a page-content overlay, not a field-dictionary edit — and folding it in would
double the hand-test surface of a phase that already opens with fixture construction (§1.3).

The decision below therefore binds **P3.3a**, carried forward rather than re-derived:

A drawn/typed/image signature is placed as a page overlay with a visible, permanent label that it
is a *visual* signature and carries no cryptographic weight. It is **not** a digital signature and
must never be presented next to P3.2's `valid`/`modified` badges as if it were one. Rationale:
report §2.4 asks for visual Fill & Sign; conflating it with PKCS#7 would make the badge meaningless.

### D-F9 — No network, no JavaScript, no calculation engine.

Form calculations (`/AA` `/C` actions) are **preserved but never executed**. A filled form's
computed totals will therefore be whatever the last producer wrote, not what our fill implies.
That is stated in the UI when a document carries calculation actions, because a user who fills a
form and sees a stale total must be told why rather than left to discover it.

## 4. Named invariants

Each is a property a test can assert, and each names what breaks if it is violated.

- **I-F1 — No false success.** No fill operation returns success unless the value persisted and
  re-reads. Violating it ships §1.2's defect at our own API boundary (D-F2).
- **I-F2 — No invention.** No state name, option value or field name is ever written that was not
  already present in the document or supplied by the user. Violating it corrupts forms from
  producers we did not anticipate (D-F3).
- **I-F3 — No silent loss.** Every key present before a fill is present after it, unless the fill
  itself was required to change that key. Violating it destroys JavaScript, calculation order or
  producer metadata invisibly (D-F4).
- **I-F4 — No privilege escalation.** A read-only field, or a document whose permissions forbid
  form fill, cannot be filled by any path, including a direct command call. Violating it breaks
  P3.2's protection promise on a document the user believed was locked (D-F7).
- **I-F5 — Original untouched.** The source file's bytes after a fill are identical to before.
  Violating it is data loss with no undo (D-F5).
- **I-F6 — Visual signature stays visual.** *(Binds P3.3a, not this phase — carried forward per
  the 2026-11-14 ruling that moved Fill & Sign out.)* No code path returns a cryptographic verdict
  for a Fill & Sign overlay, and no badge renders `valid` for one. Violating it makes P3.2's badges
  untrustworthy (D-F8).
- **I-F7 — Refusals name the field and the reason.** No unfillable field is skipped without a
  record, and no error is a bare string. Violating it produces the "green pass wearing a label"
  failure the charter bans.

## 5. The acceptance shape this phase must satisfy

Per `AGENTS.md` and P3.2's precedent, a phase closes only when: the gate is green in both cargo
shapes with PDFium available, every new guard is mutation-verified with the mutation placed in the
guarded file, `--include-ignored` passes, and **the user hand-tests the installer**. Version is
bumped across all six carriers, and the release-notes section is written before the bump lands.

A row is promoted to `Have` in the parity matrix only with recorded dispatch, commit, size and
digest, exactly as B7/B9 were for 1.2.0.

## 6. Questions: what was ruled on 2026-11-14, and what is still open

**Ruled on 2026-11-14 — closed, recorded in place:**

3. **Fill & Sign placement — RULED: its own phase, not part of P3.3.** It is recorded in
   `docs/P3-PLAN.md` §1 as **P3.3a**, the phase after forms. This phase closes on form data alone.
   D-F8 and I-F6 carry the visual-signature decisions forward to that phase rather than dropping
   them, so P3.3a inherits them instead of re-deriving them.
4. **A form-bearing real-world fixture — RULED: permitted, with conditions.** In the ruling's
   words: *"A real-world form fixture may be committed provided it carries no personal data: use a
   form you generate that a real producer wrote, so the `/On` versus `/Yes` quirk survives; strip or
   avoid names, addresses and signatures, and record in the fixture README what it is and why it is
   committed."* The operative constraint is **no personal data**, and the two halves of that rule
   are not the same test:
   - **"a real producer wrote it"** — the bytes must come from a real producer's writer, because a
     hand-built fixture cannot exhibit the `/On`-versus-`/Yes` variance that §1.2 is about. The
     W1 fixture set therefore pairs the synthesised fixtures with **at least one real-producer
     form**, generated by us through that producer, and both `/On` and `/Yes` must be represented
     between them.
   - **"no personal data"** — no names, no addresses, no signatures, no filled values identifying
     a person, and no producer metadata naming one. Field *labels* are structure, not personal
     data; a value is. The fixture README must say **what it is** (which producer, which quirks it
     carries) and **why it is committed** (which guard would be untestable without it).

   **Still open, and a sign-off question rather than a code question:** which producer's writer
   the committed fixture comes from. That choice is not free — it decides which quirks exist to
   test — so it is named at sign-off, not picked during implementation.

**Still open — needs a ruling before implementation:**

1. **D-F7's certification question** — does a `P=3` certified document permit form fill? Default
   recorded above is refuse-until-ruled.
2. **Scope of XFDF form-data**: does 1.3.0 ship *both* FDF and XFDF form data, or XFDF only with FDF
   refused? Recommendation: both, one work item, because a half-format is not a format.

## 7. Task order

**W1 — Build the form fixture set (blocks everything).**
Synthesise, in the style of `examples/make_p24_fixtures.rs` and `make_p277_fixtures.rs`: a text
field (single- and multi-line), a checkbox with `/Yes` states, a checkbox with `/On` states (the
§1.2 case), a radio group, a combo, a list with `/I`, a read-only field, a field inside a
protected document, and a document carrying `/XFA`. Each is committed with a generator and a
README line stating what it exists to prove. **No implementation starts before this exists**,
because §1.3 means there is nothing to test against.

W1 also commits **at least one real-producer form**, per the 2026-11-14 ruling (§6.4): written by
a real producer's writer so the `/On`-versus-`/Yes` variance is a measured fact rather than our
assumption, carrying **no personal data** (no names, addresses, signatures or identifying values),
with a README entry stating what it is and why it is committed. The producer is chosen at sign-off.

**W2 — Read-side model.** Enumerate fields with type, flags, current value, options, `/AP` state
names, page and rectangle. Guard: reads all fixture fields without writing.

**W3 — Text fill (the one type PDFium already does correctly).** Our `lopdf` writer for `/Tx`,
D-F2 reload check, D-F5 save path. Mutation-verify I-F1 by making the writer write the old value
and confirming the reload check fails the operation.

**W4 — Button fill.** Checkbox and radio via `/V` + `/AS` **names** written by our own `lopdf`
path (D-F3) — never `set_checked`, whose `Ok` is a lie in 0.8.37 (§1.2). This is where I-F2 and
I-F3 are decided; the `/On` and `/Yes` fixtures must both pass. Carries the ruled measurement:
`the_checkbox_ticks_in_a_real_viewer`, comparing rendered pixels of the widget rectangle before
and after the fill, so a tick that PDFium reads but no viewer draws fails the test.

**W5 — Choice fill.** Combo and list, including `/I` for multi-select. First point at which the
crate's read-only accessors force our own writer rather than a wrapper.

**W6 — Refusals.** `XFA`, read-only, unsupported `/FT`, certified-document default. Every refusal
gets a fixture and a test (I-F4, I-F7).

**W7 — FDF/XFDF form-data import/export**, paired with P3.1's annotation XFDF, sharing its parser
where the shapes overlap and explicitly diverging where they do not.

**W8 — Release mechanics**: six carriers to 1.3.0, notes section, build-only dispatch, hand-test,
tag per the order recorded in 1.2.0's notes.

Fill & Sign (D-F8) is **not** in this order and is not this phase's work: the 2026-11-14 ruling made
it **P3.3a**, the phase after forms (§6.3).

## 8. Consequences of this design that the user should weigh at sign-off

- **The phase is mostly writer work, not binding work.** The premise the plan row carried would
  have produced a spike into crate internals; the measured reality is that the crate can read
  everything and correctly write almost nothing, so the substance is a `lopdf` field writer with
  its own guards.
- **§1.3 costs a work item before any visible progress.** A phase that opens with fixture
  construction looks slow; the alternative is tests that assert against documents no real
  producer emits.
- **The crate is not a safe foundation for buttons.** Wrapping `set_checked` in a `?` would ship a
  broken checkbox. Any implementation must go around it, and this design makes that a ruling
  rather than a reviewer's preference.
- **The ruled fix is a type distinction, not a workaround.** `Object::Name` versus `Object::String`
  is the whole difference between a checkbox that ticks and one that does not. It is one line of
  writer code and a pixel test — but it also means the crate's field-mutation API is bypassed, so
  the writer's correctness rests on our own guards rather than on the dependency.
- **Splitting Fill & Sign out removed the hand-test surface's largest unknown.** P3.3 now closes on
  form data alone; a visual-signature overlay (its own placement, label, and the "never look like a
  cryptographic signature" rule) is P3.3a's problem, and P3.3a inherits D-F8/I-F6 rather than
  rediscovering them.
- **The real-producer fixture is a supply-chain question, not a test-fixture question.** It is
  someone else's bytes in the repo. The ruling permits it only without personal data, so the README
