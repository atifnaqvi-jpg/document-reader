## 2. What the §5 sweep proves, and what it does not

The sweep fills all three spellings the design names — `/Yes`, `/On`, `/yes` — plus the
real-producer file, and asserts three things per row: the value persisted (I-F1), the saved
file begins with the source bytes verbatim (D-F4), and the source on disk is untouched.

The tamper negative is the part worth reading. The committed LibreOffice file has `/V /Yes`
and an `/AP /N` key of `/yes` — measured, not assumed: the test asserts both halves before it
fills anything. A writer that took the legal state set from `/V` would write an `/AS` naming
a stream that does not exist. The test requires the refusal to name `yes`, which is only
possible if the legal set came from `/AP /N`, and it then fills `yes` successfully so the
refusal is a distinction rather than a blanket rejection.

**It does not prove a viewer draws the tick.** That is §3.

Mutation-verified for this unit, each mutation placed in `editor/forms.rs`:

| Mutation | Killed by |
|---|---|
| take the legal state set from `/V` as well as `/AP /N` | `the_tamper_negative_refuses_the_spelling_the_appearance_does_not_draw` |
| make the writer rewrite instead of append | six tests, including the sweep |
| write the old value, leaving `/V` alone (W3's prescribed mutation) | `every_field_type_reads_back_the_value_that_was_written`, `a_second_fill_keeps_the_first_fills_value`, `a_fill_sets_need_appearances_on_the_saved_file` |

One mutation **survives** and is recorded rather than papered over: removing the sweep's own
byte-prefix assertion changes no test outcome, because
`a_fill_preserves_the_source_bytes_verbatim_as_its_first_revision` asserts the same property.
The sweep's assertion is a restatement, not a second guard. That is acceptable in a test whose
job is to be readable, but it must not be counted twice as evidence.

## 3. What W4 and W6 do not yet have

**The pixel test the design names does not exist.** W4 carries
`the_checkbox_ticks_in_a_real_viewer`, which compares rendered pixels of the widget rectangle
before and after the fill, so that a tick PDFium *reads* but no viewer *draws* fails. It is
still listed in `tests/docs_citations.rs`'s `PLANNED_SYMBOLS`, which is the honest state: the
citation guard passes precisely because the symbol is declared planned. The write path sets
`/V` and `/AS` correctly and the value reads back, but **nothing on this tree proves a viewer
renders the new state**. D-F2's persist-or-fail covers the bytes, not the appearance.

**The certification gate is not called from the fill path.** `EditKind::FormFill` exists in
`editor/signature/editpolicy.rs` and `permits` handles it — the design's 2026-11-14 ruling
made form fill *permitted* at `P=2` and `P=3` and refused at `P=1`. But `editor/forms.rs`
never calls `refuse_if_certification_forbids`, and no `fill` command is in the `GOVERNED`
table in `tests/certification_gate.rs`. So today a `P=1` certified document can be filled
through this module without the refusal the ruling requires. The guard that would catch this —
"a governed command missing from `GOVERNED` fails" — enumerates commands in
`src/commands/`, and this module has no command, so the guard cannot see it.

These two are the phase's remaining correctness work, and both are *absence of evidence* in a
place Rule 6 forbids treating as evidence of absence.

## 6. The question this report cannot answer

**Does P3.3 close without the pixel test, or does the pixel test block it?**

The design is unambiguous that W4 *carries* `the_checkbox_ticks_in_a_real_viewer`, and the
2026-11-14 producer ruling explains why it cannot be faked, since LibreOffice sets
`/NeedAppearances true` and a viewer regenerates appearances itself. What is not unambiguous is
whether the acceptance row for P3.3 requires it, or whether the phase ships with the value
read-back and the pixel test lands as P3.3 debt.

The release-notes brief names "the checkbox tick workaround" as a line to write. Writing that
line today would describe a fix whose effect no test on this tree demonstrates. That is the
ruling needed before 1.3.0 prep starts: **either the pixel test is written first, or the notes
say plainly that the tick is unverified in a viewer.**

Release prep (W8) is halted at this boundary. It is a short unit — six carriers, notes, bump,
build-only dispatch — and it is deliberately not started, because the notes cannot be written
truthfully until §6 is answered, and a bump that lands before its notes is the ordering the
design forbids.
