## 0. Ruling reconciliation (read first)

The authorising pulse cited "DECISIONS section 9 rulings **R3/R4**" as the basis for signatures.
**That is half wrong and the plan is right.** Checked against `docs/DECISIONS.md` §9:

| Ruling | Actual subject | Bearing on P3.2 |
|---|---|---|
| **R3** | Digital signatures: offline mode ruled in, TSA mode out. The document hash never leaves the machine; RFC-3161 and AATL-equivalent trust services stay out until separately ruled. Redaction/sanitize/signatures carry correctness obligations with **named invariants up front** (the B-1 note). | **Governing ruling for this entire phase**, all three scopes. |
| **R4** | **Compress/optimize uses a bundled qpdf sidecar** — a P3.4 concern. | **No bearing.** Nothing in P3.2 uses qpdf. |

This design follows **R3 only** and does not read R4 into the phase. If qpdf were pulled in here it
would be scope creep into P3.4, and R4 freezes that bundling shape in the *P3.4* design, not this one.

The only P3.2 row that could be misread from the pulse is the certificate source: "PFX/PKCS#12
import + Windows store read via the existing `PasswordStore` pattern". That is a **storage/secret
handling** borrow (§D-SG3), not a decision to reuse the compress sidecar.

## 1. Verified capability facts (the ground the design stands on)

### 1.1 Encryption write path — `lopdf 0.45.0` **can** do it (corrects the working assumption)

| # | Fact | Consequence |
|---|------|-------------|
| **K1** | `lopdf 0.45.0` **does** expose a working encryption *writer*. `Document::encrypt(&mut self, state: &EncryptionState) -> Result<()>` encodes the security dictionary, encrypts **every** object in place via `encryption::encrypt_object`, adds the `/Encrypt` object, and sets `trailer["/Encrypt"]`. | Protect-on-save is **not** a from-scratch implementation. The phase is a wiring + verification job, not a crypto build. |
| **K2** | `EncryptionState` has **no public constructor** in the ordinary sense, but `impl TryFrom<EncryptionVersion<'_>> for EncryptionState` is public. `EncryptionVersion` is a public enum with usable password-driven variants. | The supported entry point is `EncryptionState::try_from(EncryptionVersion::V4 { .. })`. We do not need `unsafe`, a fork, or a patch. |
| **K3** | Variant coverage, read from the `TryFrom` arms: **V1** (40-bit, RC4 or AES), **V2** (variable key length, ≥40), **V4** (AES-128, revision 4, derives the file key **from the passwords** itself), **V5** (AES-256, revision 6, **requires the caller to supply the 32-byte file key** and rejects a key of the wrong length). **R5** exists but is `#[deprecated]` with a "testing purposes only" note. | Two complete password-driven paths. **V4** needs nothing from us but passwords + permissions. **V5** needs us to generate the 32-byte key from a CSPRNG and pass it. See §D-PR2. |
| **K4** | `Permissions` is a public `bitflags` type with `PRINTABLE`, `MODIFIABLE`, `COPYABLE`, `ANNOTABLE`, `FILLABLE`, `COPYABLE_FOR_ACCESSIBILITY`, `ASSEMBLABLE`, `PRINTABLE_IN_HIGH_QUALITY`. `correct_bits()` force-sets the reserved bits. `Default` is `Self::all()`. | The permission UI maps 1:1 onto real bits. `Default = all` means an omitted bit is a **silent permission grant** — the UI must be explicit per bit, not "start from default". |
| **K5** | The `encryption` module is **not feature-gated**: `pub mod encryption;`, and the cipher crates (`aes 0.9`, `cbc 0.2`, `md-5 0.11`, `sha2 0.11`) are **unconditional** dependencies. Our build sets `default-features = false`, which drops only `chrono-clock` and `rayon`. | **No Cargo.toml change is needed to write encryption.** This is a fact worth stating because the repo's `default-features = false` invites the opposite assumption. |
| **K6** | After `Document::encrypt`, the doc sets `self.encryption_state = None`, and the writer refuses to write object streams for an encrypted document, because "the objects are already encrypted by the time they reach the writer and the file encryption key is gone". | **Encryption must be the last mutation before save.** Any edit after `encrypt()` silently produces a file whose `/Encrypt` claims every stream is encrypted while new objects go out in the clear. This is the single sharpest hazard in SCOPE-A — see **I-PR3**. |
| **K7** | `Document::save_to` is a **full rewrite** (P2-DESIGN F6 still holds). Existing save discipline is `editor::save::write_atomically` (sibling temp + rename), already used by the decrypt-copy path. | Protect-on-save keeps D2/P2-D2 untouched: new file, temp+rename, never in-place. |
| **K8** | The existing protect module is **read-side only**: `is_encrypted`, `is_encrypted_bytes`, `read_only_guard`, `unprotected_path`, `decrypt_document`, `decrypt_copy`, with 6 tests including "decrypt_copy writes a working unprotected file and leaves the original alone". | Half of SCOPE-A already exists and is tested. The delta is the write direction plus the permission model, not the file policy. |

### 1.2 Redaction — **PDFium cannot do it**, and the bundled binary proves it

### 1.3 Signatures — the primitives are split, and one is missing from our dependency set

## 2. Frozen decisions (P3.2)

ID convention: `D-PR*` (protect), `D-RD*` (redaction), `D-SG*` (signatures), continuing P3.1's
scoped-prefix style (`D-A*`) and avoiding collision with the §9 rulings `R1..R6`.

### 2.1 SCOPE-A — Protect on save

| ID | Decision | Rationale |
|----|----------|-----------|
| **D-PR1** | **Protect is a save-time transform, never an open-time mutation.** The user chooses a password and permissions in a dialog; the transform runs on the bytes at save. The in-memory document is never left in an encrypted state. | K6: `encrypt()` is one-way in practice (the file key is dropped), and `AlreadyEncrypted` makes a second call an error. Doing it at save means exactly one call, at one place, with nothing after it. |
| **D-PR2** | **AES-256 (V5) is the default; AES-128 (V4) is offered as a compatibility choice.** For V5 **we generate the 32-byte file key from the OS CSPRNG** and pass it into `EncryptionVersion::V5`. | K3: V5 is the only modern choice but requires a caller key, so generation is unavoidably ours. V4 stays because it is the only path where lopdf does **all** key derivation internally, and offering it is the honest hedge if V5 has a compatibility surprise we have not yet measured. Default is AES-256 because shipping AES-128 by default in 2026 is not defensible. |
| **D-PR3** | **Permissions are explicit per-bit, and "all permissions" is a visible checkbox state, never a default.** The UI starts from an explicit set the user sees. | K4: `Permissions::default()` is `all()`, and `correct_bits()` silently force-sets reserved bits. A UI that starts from the default and clears nothing ships a document granting everything while looking like it granted nothing. |
| **D-PR4** | **Protect reuses P2-D2 unchanged: new file, temp + rename, never in place.** The output name follows the existing `unprotected_path`/edit-copy shape. Overwriting the original remains an explicit, confirmed action. | K7/K8: the discipline exists, is tested, and protect is exactly the class of write D2 was written for. Changing it for this feature would be the first crack. |
| **D-PR5** | **Changing the password of an already-protected file requires the current password**, taken from `PasswordStore` if held, otherwise prompted. The flow is: decrypt in memory → edit → re-encrypt → save. The plaintext never touches disk. | K8/K6. `PasswordStore` already holds, zeroises and never prints the password, with `forget` on close. Reusing it means no new secret-handling path. Refusing to strip a password we cannot prove is a trust property, not a nicety. |
| **D-PR6** | **Unprotect ("remove password") is a distinct, confirmed action with its own output file**, and it warns that the result is plaintext on disk. | It is the one operation that converts a protected document into an unprotected one. Burying it inside "save" would let a user strip protection by accident. |

### 2.2 SCOPE-B — Redaction

| ID | Decision | Rationale |
|----|----------|-----------|
| **D-RD1** | **Mark and apply are two distinct user actions with two distinct persistence rules.** *Marking* stores redaction rectangles and pattern matches in our DB (a new `Redaction` table), not in the PDF. *Applying* performs the destructive rewrite and produces a **new file**, after which the marks are cleared and the source is untouched. | Marks are working state that must survive a crash; the PDF is the deliverable that must not contain them. Storing marks only in the PDF means an unsaved mark is invisible to the DB but visible to a viewer — two truths. Storing them only in the DB means an unapplied redaction can never be mistaken for an applied one. This also keeps D2 intact: apply writes a new file. |
| **D-RD2** | **Apply removes content; it never paints over it.** The rewrite must delete the text-showing operators that produce glyphs inside each rectangle, delete intersecting annotation objects, and delete fully-or-partly intersecting image XObjects **whole**. A black fill is drawn **last, for appearance only**. | This is the phase's central claim and the pulse's explicit requirement ("not overlay, not flatten"). Deleting the operator is what makes the text unrecoverable; the black box alone is the failure mode this decision forbids. |
| **D-RD3** | **Redaction fails safe by removing more, never less.** If a glyph, annotation or image *cannot be proven* to be outside the rectangle, it is removed. An image that intersects by one pixel is removed entirely. | The asymmetry of the error matters: over-removal is visible and recoverable (the user has the source and a new file); under-removal is a silent disclosure that cannot be undone. Every ambiguous case resolves toward removal. |
| **D-RD4** | **After the rewrite, a reachability GC runs and the xref is rebuilt from it.** Objects unreachable from the trailer are dropped; no xref entry may reference a dropped object. | K13: lopdf has no GC. Without this pass, "deleted" objects survive as orphaned data that a recovery tool can extract — the exact failure the feature is supposed to prevent. This is where **I-RD4** is enforced. |
| **D-RD5** | **Sanitize is part of apply, not a separate opt-in step, and its scope is named:** document `/Info` metadata, XMP metadata, outgoing `/Outlines` (bookmarks), `/Names`/`/EmbeddedFiles` attachments, annotation `/Contents`/`/T` outside the redaction rects, form-field values, and document-level JavaScript actions. | "Remove hidden information" that leaves metadata behind is theatre. Making it a separate step invites the user to skip it. The list is closed and testable; anything not on it is explicitly not claimed (§8). **Caveat, stated rather than discovered later:** sanitising bookmarks and attachments is *destructive to document navigation and content*. That is why it is inside the same confirmed apply action, and why the confirmation names these classes explicitly rather than saying "hidden information" and hoping. |
| **D-RD6** | **Search-and-redact uses the existing text locator**, matching runs through `textlocate::locate_runs`, and converts each hit to the glyph bounding box(es) of the matched run segment before it becomes a mark. | K14: the locator already resolves glyphs to positions, including inside forms and nested XObjects. Re-implementing pattern matching over a second text model would give two answers to "where is this word", which P2 already paid to unify. |
| **D-RD7** | **Partial-pixel image redaction is out of scope for 1.2.0 and is refused, not approximated.** An intersecting image is removed whole (D-RD3); the UI states that the entire image will be removed. | Doing it properly means decoding, masking, re-encoding each image with acceptable fidelity — a separate project, and a half-version silently leaks the un-masked pixels. Refusing with a visible consequence is honest; approximating is not. |

### 2.3 SCOPE-C — Offline signatures

| ID | Decision | Rationale |
|----|----------|-----------|
| **D-SG1** | **PKCS#7/CAdES is built on the RustCrypto stack: `rsa`, `pkcs8`, `pkcs1`, `pkcs7`, `x509-cert`, `der`, `sha2`, plus `pkcs12` for PFX import.** No `openssl` dependency, no `qpdf`, no external signer process. | K16: nothing asymmetric exists in the graph, so this is a real addition. Pure-Rust wins here because the product is Windows-only, self-contained and offline: a vendored OpenSSL build adds a C toolchain and a native-DLL bundling problem to the installer for one feature. The chosen crates are the same family `rustls`-ecosystem code already trusts. **This is the decision most worth your scrutiny** — see §9. |
| **D-SG2** | **Signing writes an incremental revision and preserves the original bytes verbatim.** The `/ByteRange` is computed over the actual file bytes as written, and the signature's `/Contents` placeholder is sized before writing. Signing uses **`lopdf::IncrementalDocument`**, not PDFium's save path (K17b: PDFium cannot write incrementally — its save flags are hardcoded to 0). | K15/K17b: a signature over a rewritten file is a signature over a *different* file. Incremental append is the only shape where the signed range is the user's bytes, and it is the only incremental writer in the graph. **D2 is reinterpreted here, deliberately and narrowly:** the original file is still never modified — the signed output is a new path — but the *content* of that new file begins with a byte-identical copy of the source. **D-SG2a (the D2 exception, written out):** the source file is never modified; the signed output is a new path; and the only reason the output contains the source's bytes is that a signature is meaningless otherwise. D2 forbids destroying the user's file from an edit action — it has never forbidden producing a new file that contains their bytes, which every save already does. |
| **D-SG3** | **The document hash never leaves the machine and no network call is made anywhere in the sign or verify path.** Enforced structurally: the signature module has no HTTP client in its dependency set, and a guard asserts the module's import surface. | R3, verbatim. This is not a policy we hope holds; it is a compile-surface property we can test. |
| **D-SG4** | **Trust is local configuration only.** The trust store is a local file (or the Windows store) the user has chosen; a certificate that chains to nothing there is reported **`unknown`**, never `valid`. Revocation information is read **from the document** (embedded CRLs/DSS if present) or **imported by the user**; it is never fetched. | R3. The dangerous default would be "chains to a public root, therefore valid" — that is an implicit network trust decision even without a fetch. `unknown` is the correct answer for offline verification and must be the *rendered* badge, not an error. |
| **D-SG5** | **Certificate sources are: PFX/PKCS#12 import (password handled through the `PasswordStore` pattern), and the Windows certificate store read directly via the `windows` crate.** No macOS keychain, no PKCS#11 for 1.2.0. | K21 and the shipping platform is Windows. The `PasswordStore` shape (zeroising `SessionPassword`, `with_password` closure so the lock cannot escape, `forget` on close) is reused for the PFX password rather than invented again. PKCS#11/HSM is a later, separate decision. |
| **D-SG6** | **Certification (DocMDP) is an explicit choice with the level shown before signing**: `P=1` no changes, `P=2` form-fill + signatures, `P=3` + annotations. A certify signature is written with the matching `/Reference` → `/TransformParams`. | The report §2.5 lists `CertifyInvisible` separately from signing precisely because the levels mean different things. A certify signature that silently means `P=1` turns the user's own later annotation into "document was modified" — a false alarm on their own file. |
| **D-SG7** | **Validation badges are computed locally and are honest about what they did not check**: `valid`, `modified`, `unknown`, `unsigned`. "Modified" covers both byte-range damage and a subsequent incremental revision; "unknown" covers unanchored chains and absent revocation data. Reading the signature dictionary and its declared MDP level comes free from `PdfDocument::signatures()` (K17); the badge is our judgement layered over that reading. | K17: PDFium reads the signature dictionary and DocMDP level but cannot judge trust. Anything beyond these four states would be a claim we cannot support offline, and a green badge that means "we did not check" is worse than no badge. |

## 3. Correctness obligations — the named invariants (R3 / B-1, stated before mechanism)

R3 requires invariants **up front**. These are the acceptance tests; the mechanism in §4 exists to
satisfy them and is revisable if one cannot be met. Each is a test, not a sentiment.

### 3.1 Redaction — `I-RD1 … I-RD7`

| ID | Invariant | How it is tested (the oracle, not our own writer) |
|---|---|---|
| **I-RD1** | **Extraction invariance.** For every redacted rectangle, text extracted from the *output* file over that rectangle contains none of the characters the redaction removed. | Re-open the output with PDFium and extract via `FPDFText_*` (K12), restricted to the rect in page coordinates. This is the invariant the whole feature exists for, and it uses an engine we did not write. |
| **I-RD2** | **Search invariance.** Searching the output for a redacted string returns nothing, including in annotations, form fields and metadata. | Run the product's own search index path over the output and assert zero hits, plus a raw scan of §I-RD3. |
| **I-RD3** | **Structure-walk invariance (no survivor anywhere in the object graph).** Walks every object reachable from the trailer, decompresses every stream, and asserts the removed byte pattern appears **nowhere** — not in an orphan, not in a leftover XObject, not in a content stream we forgot to rewrite. | A raw scan over the decompressed object graph, independent of I-RD1. I-RD1 can pass while I-RD3 fails (text removed from the page but still in an abandoned Form XObject) — that is precisely the leak this catches. |
| **I-RD4** | **Xref integrity: no dangling references.** Every reference in every reachable object resolves to an object that exists in the output; no xref entry points at a freed offset; the xref and the object table agree after the GC of D-RD4. | Post-GC reachability assertion + a reopen in PDFium + a parse of the output's xref (both table and stream forms). A dangling reference is what makes a half-redacted file fail to open in exactly one viewer, which is the worst support case. |
| **I-RD5** | **Round-trip survival.** The output opens without repair in PDFium and preserves page count, page geometry (MediaBox/CropBox/Rotate) and the content outside redaction rectangles. | Reopen + compare geometry to the source; render a page and diff the non-redacted region against the source render. Over-removal (D-RD3) is allowed; *unintended loss outside the rects* is a failure. |
| **I-RD6** | **Idempotence.** Applying the same mark set twice, or applying to an already-redacted output, is a no-op that reports it — it does not double-remove or corrupt. | Apply twice, compare output bytes (modulo timestamp), assert the second run reports "nothing to apply". |
| **I-RD7** | **The marks do not survive as marks.** After apply, the output contains no `/Redact` annotation and no redaction rectangle metadata, so a viewer cannot reveal what was hidden by un-marking it. | Object-graph scan for `/Subtype /Redact` and for our own mark identifiers. |

**A note on I-RD3 vs I-RD1.** They are not redundant, and I-RD1 alone is the trap this phase
must not fall into. A file can pass extraction invariance and still carry the removed text in a
discarded XObject, an object stream, an incremental revision, or the `/Info` dict. I-RD3 is the
one that makes "true removal" a testable statement rather than a claim about the visible page.

### 3.2 Protect — `I-PR1 … I-PR4`

| ID | Invariant | How it is tested |
|---|---|---|
| **I-PR1** | **Round-trip under the password.** The output opens with the user password, and **fails** to open with a wrong password. | Reopen in PDFium with the right password (must render page 1) and with a wrong one (must be refused). |
| **I-PR2** | **Permissions are the ones requested.** The `/P` bits in the output decode to exactly the set the user chose, with the reserved bits set as the spec requires. | Parse `/P` from the output and compare to the requested set, bit by bit. |
| **I-PR3** | **Nothing after encryption.** Asserted structurally: the save pipeline is ordered so that `Document::encrypt` is the final mutation before serialisation, and a test proves a mutation attempted after `encrypt()` is not silently dropped (K6). | A test that encrypts, then attempts a mutation, and asserts the pipeline refuses or the mutation is visible — either is acceptable; **silence is not**. |
| **I-PR4** | **The plaintext original is not modified**, and the protected output does not leak the plaintext anywhere in its bytes. | Source bytes unchanged (hash compare); scan output for a known plaintext marker outside its encrypted containers. |

### 3.3 Signatures — `I-SG1 … I-SG5`

| ID | Invariant | How it is tested |
|---|---|---|
| **I-SG1** | **The signature verifies over the bytes as shipped.** Recomputed digest over `/ByteRange` matches `/Contents`, using an independent implementation. | Verify with a second implementation (the test harness uses a separately written check), not just our verifier — otherwise a symmetric bug passes both sides. |
| **I-SG2** | **The original revision is byte-identical.** The signed file's first N bytes equal the source file exactly, where N is the first byte range. | Direct byte compare of the prefix. This is the invariant that makes D-SG2 real. |
| **I-SG3** | **No network.** Sign and verify complete with no socket opened. | Guard over the module's dependency/import surface (D-SG3) **plus** a run-time check that the path completes in an environment with no network. |
| **I-SG4** | **Badges tell the truth.** A tampered byte yields `modified`; an unanchored chain yields `unknown`; an unsigned file yields `unsigned`. None yields `valid`. | Deliberate corruption tests per state, each asserting the exact badge. |
| **I-SG5** | **Certification level is what was written.** A `P=1`/`P=2`/`P=3` certify signature reads back as that level, and a post-signature edit produces `modified` consistent with the level. | Parse `/Reference`/`/TransformParams` from the output; make a permitted/disallowed edit per level and assert the badge. |

## 4. Architectural shape

**Everything marked NEW below does not exist yet.** The diagram is the shape implementation is
building toward; only files that exist in the tree today may be cited as such (see the note at the
end of this section).

```
editor/  (PLANNED SHAPE - not yet in the tree)
  protect.rs          EXTENDED  (write direction: protect_save, permissions, re-protect)
  protect_save/       NEW       key generation (CSPRNG), EncryptionVersion selection,
                                post-encrypt ordering guard (I-PR3)
  redact.rs           NEW       mark storage bridge, mark -> rect resolution
  redact/
    apply.rs          NEW       the destructive rewrite (the only module allowed to delete)
    text_removal.rs   NEW       content-stream surgery, reusing textlocate glyph geometry
    sanitize.rs       NEW       D-RD5 closed list (Info, XMP, outlines, names, annots, forms, JS)
    object_gc.rs      NEW       reachability GC + xref rebuild (D-RD4)
    verify.rs         NEW       I-RD1..I-RD7 oracles; the tests live beside it
  signature.rs        NEW       sign entry point, DocMDP, badge computation
  signature/
    cms.rs            NEW       PKCS#7/CAdES construction over rsa/pkcs7/x509-cert
    pfx.rs            NEW       PKCS#12 import via PasswordStore pattern
    winstore.rs       NEW       Windows cert store read (windows crate), cfg(windows)
    verify.rs         NEW       I-SG1..I-SG5 oracles
```

Two rules the shape enforces:

1. **Only the apply module and the object-GC module may delete content.** Every other module
   treats the document as append-only. A deletion anywhere else is a bug by construction, and the
   guard for that is a source-level check like P3.1's `app_css_chrome.rs` precedent.
2. **Verification lives next to the operation, not in a distant test file**, because I-RD/I-SG are
   the acceptance criteria and must be runnable per operation.

Tauri commands stay thin (P2-D1): redact_mark, redact_apply, protect_save, protect_remove,
sign_pdf, verify_signatures, list_certificates. Each delegates to the `editor::` seam.

**Citation discipline.** This document is registered in `GOVERNED_DOCS`, so the citation guard
reads it against the tree. Two rules follow and were applied when the document was frozen: it
cites **symbols, never line numbers** (a line number is stale by construction), and it names
identifiers it intends to create in plain prose rather than backticking them as if they existed.
Third-party crate APIs are described rather than cited, because they live outside this tree.

## 5. Data model delta

New table `Redaction` (marks only — D-RD1):

| Column | Type | Purpose |
|---|---|---|
| `id` | UUID | mark identity |
| `document_id` | UUID FK | owning document |
| `page` | INTEGER | page index |
| `kind` | TEXT | `rect` \| `pattern` |
| `rect` | TEXT | normalised `x0,y0,x1,y1` in page space |
| `pattern` | TEXT NULL | the search text for `pattern` marks, for the mark list only |
| `created_at` | TEXT | timestamp |

No change to `Annotation`. Redaction marks are deliberately **not** annotations: annotations are
renderable, removable state that ships in the PDF (P2-D3), and a redaction mark must not ship at
all (I-RD7). Signature records are **not** stored: the signature lives in the PDF, and the DB
storing a second copy would create the "two truths" problem D-A2 exists to avoid.

## 6. UI / pane discipline

Same discipline as P3.1: no new top-level surface, no modal maze.

| Surface | Behaviour |
|---|---|
| **Redact tool** (in the annots tool group) | Toolbar toggle → drag rectangles on the page; a *Mark for redaction* mode distinct from annotation tools. Marks render as a distinct outline style (not as PDF annotations). A **Redact panel** lists marks per page with a count, offers search-and-redact pattern entry, and has one destructive button: **Apply redactions**. Apply always warns that it writes a new file and that images intersecting a mark are removed whole (D-RD7). |
| **Protect flow** | File-level *Protect with password…* opens a single dialog: password + confirm, then an **explicit permissions list, every box shown with its current state** (D-PR3). *Remove protection…* is a separate menu item with its own confirmation (D-PR6). Changing the password of a protected file prompts for the current one if `PasswordStore` has none. |
| **Signatures** | *Sign…* opens certificate selection (PFX import / Windows store list), then reason/location plus an explicit **certification level** choice (D-SG6). A **signature badge** appears in the viewer status area with the four honest states (D-SG7), and clicking it shows what was and was not checked — including "revocation: not checked (offline)". |

Consistency rules carried from P3.1: one gesture = one undo entry; the panes are views over state,
not caches of it; a destructive action states its output file before performing it.

## 7. Risks

| Risk | Mitigation |
|---|---|
| **K6 hazard**: a mutation after `encrypt()` silently writes plaintext under an encrypted `/Encrypt` dict | **I-PR3** makes it a test; ordering is structural, not conventional. |
| Redaction leaves text in an object we never walked (orphan, object stream, incremental revision) | **I-RD3** scans the decompressed graph independently of the page; **I-RD4** GC + xref rebuild; **I-RD1** uses PDFium's own extractor. Three independent oracles, not one. |
| Over-removal destroys legitimate content (D-RD3) | Accepted and **visible**: apply writes a new file and the UI states the consequence. Chosen deliberately over silent under-removal. |
| Image redaction is refused, and a user assumes it happened | D-RD7 makes it explicit in the UI at apply time; §8 records it as not claimed. |
| V5 encryption has a compatibility surprise with some viewers | V4 remains an offered alternative (D-PR2); a fixture round-trip through PDFium gates the default. |
| New crypto dependency surface (D-SG1) is large and security-relevant | Pure Rust, no C; the choice is flagged for sign-off (§9); R3's no-network rule is enforced as a dependency-surface guard, not a hope. |
| Offline verification cannot prove revocation or long-term validity | D-SG4/D-SG7: the honest state is `unknown`, rendered as such. Absence of evidence is not evidence of validity. |
| **Open `STATUS_ACCESS_VIOLATION` (K20)** makes a Windows-only green unreliable | **Non-blocking, stays open, not fixed here.** No P3.2 claim may rest on one Windows run: every Windows assertion needs a Linux-side equivalent, or an explicit same-SHA re-run policy. Purely Windows items (cert-store read) are unit-tested against fixtures where possible and hand-tested once. **Carried teardown flake, known and named:** exit `0xc0000005` in the Windows PDFium suite, intermittent at the same SHA (re-run 2 of run 42432916098 went green on an unchanged tree), observed in the `provider::pdf` teardown path. It is **not a release blocker**. Deeper instrumentation is gated on a **third reproduction** per the standing ruling; one same-SHA green is not a diagnosis and this row is not closed by it. |
| Redaction of text inside a Form XObject shared by multiple pages | I-RD3 walks XObjects; a shared XObject's removal is page-scoped by rewriting the referencing content stream, and the object is only dropped when no page still references it (D-RD4 reachability). |

## 8. Explicitly out of scope (not claimed, not attempted)

- **TSA / RFC-3161 timestamping**, AATL, EU qualified trust services, LTV/DSS generation (R3).
- **Any network call** — no CRL/OCSP fetch, no AIA chasing, no cloud anything (charter, R3).
- **Cloud/DRM**: MSRMS/IRM, "Information protection" (charter).
- **Partial-pixel image redaction** (D-RD7) — images intersecting a mark are removed whole.
- **qpdf / compress / optimize** — that is P3.4 under R4, and R4 freezes its shape in *that* design.
- **PKCS#11 / HSM / smart-card signing**, macOS keychain, PAdES-B-LT — later, separately ruled.
- **Security policies / policy favourites** (`SecurityPolicyFavoritesRdr`) — not in the P3.2 row.
- **Redaction of vector graphics** (a filled path under a mark): removed only if it is a
  text-showing operation; arbitrary path surgery is not attempted, and the mark list says so.

## 9. Open for sign-off

These need your decision before any code is written. The rest is frozen above.

1. **D-SG1 — the crypto dependency set.** This is the largest new dependency addition in the
   programme (`rsa`, `pkcs8`, `pkcs1`, `pkcs7`, `x509-cert`, `der`, `pkcs12`, plus a direct
   `windows` with certificate features). The alternative is a vendored OpenSSL, which costs a C
   toolchain in the installer build. **Recommendation: pure Rust (as written).** Confirm, because
   it is hard to reverse later.
2. **SCOPE-B's destructive semantics.** D-RD1/D-RD2/D-RD3 mean *apply* permanently removes content
   from a **new** file while leaving the source untouched, and over-removes by design. Confirm that
   "fail safe by removing more" is the behaviour you want, including for images (whole-object
   removal, D-RD7).
3. **D-RD5 sanitize scope.** Confirm the closed list (Info, XMP, outlines, embedded files,
   annotation text outside rects, form values, document JS). Anything removed from that list is a
   claimed-but-not-delivered; anything added is a new obligation.
4. **D-RD7 — is refusing partial-pixel image redaction acceptable for 1.2.0?** The alternative is
   shipping visually-lossy re-encoding, which I do not recommend.
5. **D-SG2 — the narrow P2-D2 exception for signed output.** Signing writes a new file whose
   content begins with a byte-identical copy of the source, so the source file is untouched but its
   bytes are reproduced. Confirm that reading of D2.
6. **D-SG6 — default certification level**, if any, when the user does not choose. My default is
   *signature, not certification* (no implicit DocMDP), because an accidental `P=1` turns the user's
   own later annotation into a "modified" warning.
7. **Version.** `1.2.0` per the plan (P3.2's reserved number). Confirming no renumbering.

## 10. Task order (after sign-off; each step gated)

1. **Facts to fixtures — including the two load-bearing unknowns.** Build encrypted-output and
   redaction fixtures and prove Protect round-trips through PDFium (I-PR1/I-PR2) before any UI.
   **Also prove, here, that `lopdf::IncrementalDocument` can append a second revision that a viewer
   accepts** (§11, the likeliest failure) and that `FPDFText_*` reports per-glyph rectangles usable
   by I-RD1. Both are cheap to test and both invalidate whole sections if they fail. No SCOPE-B or
   SCOPE-C code before these two fixtures exist.
2. **SCOPE-A**: protect_save + permissions + ordering guard (I-PR3) + tests (I-PR1..4).
3. **SCOPE-B core**: object_gc + xref rebuild first (I-RD4), because everything else depends on it.
4. **SCOPE-B text removal** over `textlocate`, then sanitize (D-RD5), then the oracles I-RD1..I-RD7.
5. **SCOPE-B UI**: mark tool + redact panel.
6. **SCOPE-C**: the CMS module + the PFX module + verify (I-SG1..I-SG4), then the Windows-store module (Windows), then
   DocMDP (I-SG5), then badges.
7. Gate, hand-test, release 1.2.0 — a phase is `[x]` only when the gate is green **and** the
   installer is hand-tested (AGENTS.md rule 1).

Redaction lands before signatures: it is the higher-consequence feature and its invariants are the
harder proof, so it should not be scheduled behind new crypto.

## 11. What would make this design wrong

Recorded so a later reader can check the claim rather than trust it:

- If `Document::encrypt` turns out to produce files PDFium refuses to open (I-PR1 fails on the
  fixture), SCOPE-A falls back to a different writer or a sidecar, and D-PR1/D-PR2 are reopened.
- If PDFium's text extractor cannot report coordinates for a glyph we removed (K12 gives the
  functions, not a proven per-glyph mapping), I-RD1's oracle weakens and I-RD3 becomes the primary
  proof. That is a **weaker** claim and would be stated as such, not glossed.
- If `pkcs7`/`x509-cert` cannot express CAdES' signed attributes in the shape a Windows viewer
  accepts, D-SG1 must be revisited before implementation, not after.
- If `lopdf::IncrementalDocument` cannot produce an xref a Windows viewer accepts as a valid second
  revision (its its internal save-support check is a guard, not a conformance claim), D-SG2 has
  no substrate in the current graph and signing would need its own writer. This is the most likely
  of the four to bite, and step 1 of §10 must prove it with a fixture before SCOPE-C is scheduled.

**A note on how these facts were obtained.** They were read out of vendored crate sources and the
bundled `.so`'s symbol table, not from documentation or memory. Two claims in the first draft of
this document were **wrong and were corrected during writing**: that `IncrementalDocument` had no
`save` (it does — a second `impl` in the crate's writer module), and that pdfium-render had no typed signature
reader (it does — the pdfium-render crate's signature module, missed because the first grep covered only
`bindgen/` and the crate's thread-safe bindings module). Both are recorded rather than quietly fixed, because a design
document whose facts cannot be checked is worth nothing, and a reader is entitled to know which of
these were re-derived after an initial miss.
