## B. Must answer before committing the plan

### B-1. Is this plan scoped to *text editing*, or to *all of Acrobat*?

The plan calls itself "Adobe parity" but its matrix covers only the text-edit engine (A) and the
document surface we already touch (B). It omits large Acrobat areas entirely: forms, redaction,
signatures, OCR, comments/markup parity, optimize/compression, PDF/A, attachments/portfolios,
layers (OCG), outlines, Bates numbering, compare, print production/preflight, page labels,
headers/footers, resize.

**Recommendation:** commit P2.7 as **"text-editing parity"** and rename it accordingly. Then
produce a second inventory for the remaining Acrobat surface, with the same three-test inclusion
rule, as a separate programme. A plan that claims "all functionality" while listing only text
invites exactly the confusion we have already had.

### B-2. Contradiction with the existing Stage gate (P2.4 T11)

`P2.4-DESIGN.md` T11 froze: "Stage 2 (embedding/subsetting) and Stage 3 (reflow) are separate
future phases, each with their own frozen-design doc." The P2.7 plan renumbers reflow as
**P2.7.2** and embedding as **P2.7.6**, without stating the mapping.

**Recommendation:** state explicitly that P2.7.2 **is** P2.4 Stage 3 and P2.7.6 **is** the
outstanding MECH-B half of P2.4 Stage 2. Either map the numbers in the plan, or adopt one
numbering and retire the other. Two live names for the same gate is how a stage gets done twice.

### B-3. Is the "silent wrongness first" ordering still the right ordering?

The plan's own rule ranks silent wrongness above refusals. By that rule the order is A7
(rotation) → A6 (XObjects) → … , not A2 first. A2/A3 are already done, so the question is what
comes *next*: the plan says P2.7.2 reflow; the rule says rotation.

**Recommendation:** **rotation first, as a targeted hotfix**, not a phase. It is the only item
that is editable and wrong. Under the P2.4.1 precedent a hotfix does not need a programme phase.

### B-4. Rotation: refuse or transform?

Today a rotated run is editable with a horizontal `advance` (verified: `Tm [0 1 -1 0 …]` →
`origin=(300,100)`, `advance=114.67`). `fits-width` therefore checks the wrong axis.

**Recommendation:** add an interim **refusal gate** now (hours, honest, stops wrong writes),
then do the transform properly. Do not ship a known-wrong editable path while a multi-day phase
is pending.

### B-5. `Ts`: fold into 0.5.0, or defer?

`Ts` (rise) does not move the pen horizontally, so it does not affect `fits-width`. It only
affects the recorded baseline, which matters for pairing a run to a box.

**Recommendation:** **fold into 0.5.0.** It is a field, a `BT` reset, and one test. Deferring it
means changing `RawRun` in a later phase for no benefit.

### B-6. `ActualText` fidelity: fix the decoder before claiming preservation?

See A-4. We currently claim "preserved" while possibly writing a different character than we
read.

**Recommendation:** implement real PDFDocEncoding (a 32-entry exception table over Latin-1) or
**refuse to rewrite** any `ActualText` containing bytes `0x80`–`0x9F`. Refusing is safe; the
current behaviour is not.

### B-7. Named `/Properties` with `ActualText`: disclose, or make rewritable?

Today a named bundle carrying `ActualText` is never rewritten; the edit lands and
`actual_text_preserved=false`. That is the *correct* conservative choice, but it leaves the
document's accessible text stale on every InDesign file that names its property bundles.

**Recommendation:** add a **copy-on-write** path: duplicate the named property under a new key
(e.g. `/P0_edit1`), point only this `BDC` at it, and rewrite the copy. The shared original is
untouched, so no other sequence changes. This converts a disclosure into a real fix and is the
main remaining gap in A3.

## C. Must answer to start the next design

### C-1. What is the next phase, concretely?

B-3/B-4 imply rotation (hotfix) first, then one of: XObjects (P2.7.3) or reflow (P2.7.2).
**Recommendation:** rotation hotfix → P2.7.2 reflow (largest user-visible win) → XObjects.
Rationale: reflow turns "refused, your text is too long" into a working edit, which is the
single most common Acrobat action.

### C-2. Reflow needs a scope decision that the plan does not make

Reflow cannot work by editing one operand: it must move following text (and possibly following
lines), i.e. **mutate content outside the edited run**. That collides with:
- "we never split a run" (P2.7.1 out-of-scope bullet),
- one-edit-one-undo (the inverse currently restores one operand),
- the `fits-width` gate itself, which reflow is meant to relax.

**Decide:** (a) single-line only — adjust `Tc`/`Tz` within the run, never touch neighbours;
(b) line-level — move trailing runs on the same baseline; (c) paragraph-level — full reflow.
**Recommendation:** ship (a) in P2.7.2, design (b) separately. (c) is a layout engine and should
not be bundled into a text-editing programme.

### C-3. XObjects: edit in place or materialise?

A Form XObject is **shared** — the same stream may be drawn on ten pages, or twice on one page.
Editing it changes every use.

**Decide:** refuse runs in XObjects used more than once; or copy the XObject (and its
resources) for the edited page, leaving the original for other users.
**Recommendation:** copy-on-write, same argument as B-7. Refusal would make a large class of
real PDFs permanently uneditable; in-place editing is a silent multi-page wrong write.

### C-4. CID / Identity-H: what is the honest ceiling?

Editing a CID run requires mapping the replacement's Unicode to a glyph id via the font's CMap,
and the glyph may not exist in a subset.

**Decide:** substitute to standard-14 (changes typeface, loses fidelity) vs. embed
(needs P2.7.6) vs. refuse.
**Recommendation:** keep refusing until embedding exists, then offer substitution with the
same explicit `allow_substitution` consent the UI already has. Do not silently substitute.

### C-5. MECH-B font: bundle or not?

Still open since `P2.4-stage2-DESIGN.md` §1: ~350 KB OFL font in the installer, needed for
non-WinAnsi replacements (`GLYPHS_NOT_COVERABLE`).

**Decide:** bundle Liberation, bundle a narrower subset, or download on first use.
**Recommendation:** bundle. 350 KB is noise against a PDF renderer; a download introduces an
offline failure into a feature whose whole point is editing a local file.

### C-6. Multi-level undo?

Today each edit produces one inverse operation. Acrobat gives multi-level undo across edits,
page operations, and annotations.

**Decide:** is multi-level undo in P2.7 scope?
**Recommendation:** yes, as cross-cutting infrastructure before P2.7.2. Reflow and XObject
copy-on-write both multiply the objects a single edit touches; a one-shot inverse will not
survive them.

### C-7. Form filling and redaction: still deferred?

Both are in the plan as "deferred, not planned".

**Decide:** keep deferred? And separately: **does the UI currently imply redaction?** If
delete-pages + flatten is presented anywhere as removing content, that is a legal exposure and
should be relabelled regardless of this plan.
**Recommendation:** keep both out of P2.7; relabel any redaction-adjacent UI immediately.

### C-8. Does the plan need an explicit "stop" condition?

"All functionality from Adobe" has no natural end.

**Decide:** what closes the programme?
**Recommendation:** close when every row in the matrix is either `Have`, `Keep (divergence)`, or
an explicitly accepted refusal with a documented way out. Capability gaps that remain deferred
should be listed as accepted, not pending.

### Recorded obligations from these answers

- **Redaction** — failure to remove underlying text is a **data-leak bug**. Silent wrongness outranks everything here.
- **Signatures** — the invariant is **"the signature is definitively invalid once content it covers changes"**, not "detect the edit". A non-invalidating signature is a **legal-reliance bug**.
- **Reflow** — splitting runs is permitted **only** in the reflow path; the relaxation must not leak into ordinary edits.
