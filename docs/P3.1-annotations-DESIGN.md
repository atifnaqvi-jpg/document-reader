# P3.1 — Annotations breadth (DESIGN)

Status: **DESIGN — frozen pending user sign-off. No code written.** Covers the **P3.1** row of
`docs/P3-PLAN.md` §1, target version **1.1.0** (one minor bump per phase, Q7). Requirements
source: `docs/reference/acrobat/acrobat-reader-feature-extraction-report.md` §2.2 (annotation
types, comment list/summary, statuses), §4.3 (XFDF/FDF/XML interop) and §4.4 M2 (annotate/comment
sequencing). Local-first charter per `docs/DECISIONS.md` §9.1: shared reviews and comment sync
(§2.9) stay out and are not referenced further.

## 1. Verified capability facts (the ground the design stands on)

Checked against `pdfium-render 0.8.37` and `lopdf 0.45.0` crate sources and the tree at
`96e7c2a`. Two of these **correct a frozen P2 document**, which is why they are stated with the
method used to check them rather than asserted.

| # | Fact | Consequence |
|---|------|-------------|
| **A1** | `pdfium-render 0.8.37` **does** expose annotation creation publicly: `PdfPage::annotations_mut()` is `pub`, and `PdfPageAnnotations` has public `PdfPageAnnotations::create_highlight_annotation`, `PdfPageAnnotations::create_underline_annotation`, `PdfPageAnnotations::create_strikeout_annotation`, `PdfPageAnnotations::create_squiggly_annotation`, `PdfPageAnnotations::create_text_annotation`, `PdfPageAnnotations::create_free_text_annotation`, `PdfPageAnnotations::create_ink_annotation`, `PdfPageAnnotations::create_square_annotation`, `PdfPageAnnotations::create_stamp_annotation`, `PdfPageAnnotations::create_popup_annotation`, `PdfPageAnnotations::create_link_annotation`. The internal `PdfPageAnnotations::create_annotation` helper is `pub(crate)`, but every per-type wrapper around it is `pub`. | **This corrects `docs/P2-DESIGN.md` F1**, which states that per-type constructors are `pub(crate)` and that "pdfium-render cannot create annotations from external code". Verified by compiling a probe test against the real dependency (the probe was deleted after the fact). F1 was true of the *helper*, not of the wrappers, and the P2 design generalised one line too far. P2 was not harmed — it chose the lopdf path for reasons that still hold (§D-3.1 below). |
| **A2** | Of the palette's shapes, pdfium-render offers constructors for **Square** (rectangle) only. There is **no** `PdfPageAnnotations::create_line_annotation`, `PdfPageAnnotations::create_circle_annotation`, `PdfPageAnnotations::create_polygon_annotation` or polyline constructor anywhere in the crate. `PdfPageAnnotationType` enumerates `Line`, `Circle`, `Polygon` and `PolyLine`, and the crate has `PdfPageAnnotation::as_circle_annotation` accessors, but no public *creation* path for them. | Line, arrow, oval and polygon/cloud **cannot** be created through pdfium-render. They can only be written as lopdf dictionaries, or pdfium's raw `FPDFPage_CreateAnnot` would have to be called through the bindings — which the crate exposes but which would bypass every typed setter. This is the single most important fact in this design: it decides the writer split in D-A3. |
| **A3** | Common setters exist on `PdfPageAnnotationCommon`: `PdfPageAnnotationCommon::set_bounds`, `PdfPageAnnotationCommon::set_position`, `PdfPageAnnotationCommon::set_width`, `PdfPageAnnotationCommon::set_height`, `PdfPageAnnotationCommon::set_contents`, `PdfPageAnnotationCommon::set_creator`, `PdfPageAnnotationCommon::set_creation_date`, `PdfPageAnnotationCommon::set_modification_date`, `PdfPageAnnotationCommon::set_fill_color`, `PdfPageAnnotationCommon::set_stroke_color`, `PdfPageAnnotationCommon::set_is_hidden`, `PdfPageAnnotationCommon::set_is_printed`, `PdfPageAnnotationCommon::set_is_zoomable`, `PdfPageAnnotationCommon::set_is_rotatable`, `PdfPageAnnotationCommon::set_is_invisible_if_unsupported`. Highlight-specific geometry is via `attachment_points_mut()`. | Enough to author the markup and text families from pdfium without hand-building dictionaries — **including appearance, which the current lopdf path does not write** (A5). |
| **A4** | `lopdf 0.45.0` writes arbitrary PDF dictionaries: `Document::add_object`, `Dictionary::set`, `Object::string_literal`, `Object::Array`, `Object::Real`. The tree already does this in `src-tauri/src/editor/lopdf_write.rs` (`annotation_dictionary`, `attach_annotation`, `set_annots`). | Every annotation type in the palette is writable as a dictionary regardless of pdfium's constructor gap. lopdf is the **complete** writer; pdfium is the **convenient** one. Neither is a blocker. |
| **A5** | The current writer deliberately writes **no `/AP` appearance stream** — `dictionary_for` records `/Rect`, `/QuadPoints`, `/C`, `/F` and lets the viewer render it. `annotate.rs` documents this as intentional. | Works for the shipped four types because viewers synthesise markup appearances from `/QuadPoints`. It does **not** work for ink, free text, callout or line-with-arrow, where `/AP` (or at minimum `/InkList`, `/CL`, `/L`) is what a non-Adobe viewer draws. P3.1 must decide per type whether to write appearance streams (D-A8). |
| **A6** | `AnnotationKind` is a closed enum (`Highlight`, `Underline`, `Strikeout`, `Note`, `Ink`, `Shape`) with `as_str`/`parse`, and `atype` in the DB is its serialised form. `docs/P2-DESIGN.md` D4 says adding a tool needs no migration because the blob is schema-versioned JSON. | The ~11 new types need `AnnotationKind` to grow, which is a `match`-exhaustive change across the writer, the appearance builder and the frontend. The *schema* needs no migration, but the *enum* is not free. `shape` in particular is one variant currently covering several PDF subtypes. |
| **A7** | The DB is the source of truth and the PDF is a projection: `apply_annotations` rebuilds **every** annotation from the DB on save and is idempotent (P2-D3/D8). Annotations made in another application are left alone because they are not in the DB. | P3.1 keeps this wholesale. It is what makes a 15-type palette tractable: adding a type is a blob shape plus a dictionary builder, not a new persistence model. It also bounds reply chains — see D-A5. |
| **A8** | FTS5 push is transactional with the annotation write: `src-tauri/src/db/annotations.rs` inserts into `AnnotationSearch` in the same transaction, deletes on removal, and `SearchHit` carries `origin` and `annotation_id` so a hit can select the annotation (P2-D5/D5c). | Comment text is already searchable. P3.1 must extend the *push predicate* to the new text-bearing types, not build a search path. |
| **A9** | Undo is **frontend-owned**: `src/state/EditorProvider.tsx` keeps a per-document stack of `StackEntry { undo, redo }` closures with `MAX_STACK = 100`, dropping oldest. Text edits additionally carry a Rust-side `ContentOperation` inverse (`EditOutcome.inverse`). | P2-D7's "coalescing" is realised as one stack entry per user gesture, not a time-window merge. P3.1 must keep that shape: one gesture, one entry, for every new tool. Reply chains make this harder (D-A6). |
| **A10** | `src-tauri/src/editor/annotate.rs` reads a schema-versioned blob (`v`) and **skips** a blob whose `v` exceeds `SUPPORTED_BLOB_VERSION` rather than misinterpreting it. | A v2 blob written by P3.1 is skipped, not corrupted, by an older build. The version field is the extension mechanism; it must be bumped, not bypassed. |

## 2. Frozen decisions (P3.1)

| ID | Decision | Rationale |
|----|----------|-----------|
| **D-A1** | The palette ships **13 types** in three families: markup (`highlight`, `underline`, `strikeout`, `squiggly`), text (`note`, `textbox`, `callout`, `typewriter`), drawing (`ink`, `line`, `arrow`, `rect`, `oval`). `polygon`/`cloud` are **named, not scheduled** — they need the same lopdf path as `line` and can follow without a new ruling. | The plan's "~15" is met at 13 concrete types plus two named. Committing to polygon/cloud now would add a geometry editor (vertex handles) that nothing else in the palette needs; naming them keeps the promise visible without pretending it is free. |
| **D-A2** | **The DB stays the source of truth; the file stays a projection.** Every new type is a JSON blob plus a dictionary builder, rebuilt wholesale on save (A7). No per-type persistence model, no incremental apply. | Continuing P2-D3/D4 is what makes 13 types affordable. Changing it would be a different, much larger phase. |
| **D-A3** | **Split writer, decided per type by capability, not by preference.** Types pdfium can author (A1/A3) use pdfium *only to measure and validate* their geometry; the bytes are still written by lopdf (A4). Types pdfium cannot author (A2: line, arrow, oval) are lopdf-only. lopdf is the single byte-writer in every case. | One writer means one place where a malformed dictionary can be introduced, one round-trip test discipline, and no dependence on pdfium's save path — which P2-F6 records as a full rewrite anyway. Using pdfium to *measure* keeps the coordinate discipline in one place (P2 §4) without splitting the output. |
| **D-A4** | `AnnotationKind` grows to distinguish the new types (`Squiggly`, `FreeText` with a `mode`, `Line` with `arrow: bool`, `Rect`, `Oval`), and `shape` is **retired** as a name — existing `shape` rows migrate to `rect` on read via an alias in `parse`, not a DB migration. | A6: the enum is the type of the write path. Keeping one `shape` variant for five PDF subtypes would force the blob to re-discriminate what the enum already knows. An alias on read means the stored rows of a shipped build keep working, which is the same trick `SUPPORTED_BLOB_VERSION` uses. |
| **D-A5** | **Reply chains are modelled as annotations with a parent, not as a separate table.** The blob gains `parent: Option<uuid>`; a reply is a `note` whose text is the reply body and whose parent is the annotation replied to. Rendering draws replies in the comment pane, not as 13 separate icons on the page. | The file format has a native mechanism (`/IRT`, the "in reply to" reference) that A4 can write. A separate table would need its own FTS push, its own undo entries and its own GC — three duplications of machinery that already exists. |
| **D-A6** | **One gesture is one undo entry**, including a reply and a status change. A status change (accepted/rejected/completed/cancelled) is an annotation *update*, so it pushes a `StackEntry` like any other update. | A9: that is the shape P2-D7 already has. Making status changes silent would let a user lose a triage decision with no way back. |
| **D-A7** | **Statuses are the report's four**: accepted, rejected, completed, cancelled, plus "none/marked". Stored in the blob, **not** in the PDF dictionary — with the `/State` key written when the annotation has a status, so other viewers see it. | The report §2.2 lists exactly those four; inventing a fifth would be parity theatre. Writing `/State` costs one key and stops our statuses being invisible outside the app. |
| **D-A8** | **Appearance streams (`/AP`) are written for the types that need them** — ink, free text, callout, line/arrow — and not for markup. Markup keeps relying on `/QuadPoints` (A5), which every viewer synthesises. | A5: writing `/AP` for markup would duplicate what viewers already do correctly and add a code path whose output can disagree with `/QuadPoints`. For ink and free text there is no synthesis to rely on, so `/AP` is the difference between "visible everywhere" and "visible in Adobe only". |
| **D-A9** | **XFDF is the interchange format**: import and export, covering annotation list, page, geometry, colour, contents, author, dates and status. **FDF is out**; export of *forms* data is P3.3's row, not this one. | The report §4.3 lists XFDF/FDF/XML as interop. XFDF is XML and maps cleanly onto our blob; FDF is the AcroForm data container, which belongs with the forms phase that will own it. Bundling FDF here would put form-data semantics in an annotations phase. |
| **D-A10** | **Import never overwrites.** An imported annotation whose `/NM` matches an existing row is skipped and counted; the count is reported to the user. | The DB is truth (D-A2). Silently overwriting a local edit with an imported one loses work the user did, and silently ignoring a conflict misreports what the import did. Counting and reporting is the only option that is neither. |
| **D-A11** | The comment-manager pane lists **every** annotation for the document in one table with sort (page, author, date, type, status), filter (by each of those, plus text search) and status editing inline. It is a **view** over the DB, with no state of its own beyond sort/filter. | The report §2.2 lists exactly this surface. Keeping it stateless means the pane cannot disagree with the page, which is the failure mode a cached list would have. |
| **D-A12** | Search integration is **extended, not rebuilt**: `AnnotationSearch` gains the new text-bearing types, and a hit still carries `origin` + `annotation_id` for jump-to-page (A8). A reply is indexed with its parent's document/page. | P2-D5/D5c already deliver this; the work is a predicate, not a subsystem. |
| **D-A13** | Blob version goes to **2**. A v1 blob is read by the v2 reader (the v1 shapes are unchanged); a v2 blob is skipped by a v1 reader rather than misread (A10). | Forward-safe in both directions, which is the property that lets a hand-test install of 1.0.x and a 1.1.0 install share a database during the transition. |

## 3. Data model delta

The `Annotation` table is unchanged (A7). Only the blob grows, at `v: 2`:

```jsonc
// v2 common
{ "v": 2, "tool": "callout", "author": "…", "status": "accepted",
  "parent": "uuid-or-null",      // D-A5 reply chains
  "created": 1700000000, "modified": 1700000000,
  // … per-type geometry, unchanged in shape from v1 where the type already existed
  "text": "…" }
```

`AnnotationKind` gains the variants named in D-A4; `atype` keeps storing `as_str()`, so no
migration is required and a v1 row still parses.

## 4. Architectural shape

```
src-tauri/src/editor/
  annotate.rs        unchanged role: blob -> dictionary, wholesale rebuild (A7)
  annotate/appearance.rs   NEW: /AP stream construction for the D-A8 types
  annotate/xfdf.rs         NEW: XFDF import/export (D-A9/D-A10)
  lopdf_write.rs     grows the per-type dictionaries (D-A3)
src/
  components/CommentPane.tsx   NEW: the D-A11 view
  components/AnnotationOverlay.tsx  grows the new tools' in-progress drawing
  state/EditorProvider.tsx     one StackEntry per gesture (D-A6)
```

The coordinate discipline is unchanged: one `page_to_pdf` / `pdf_to_page` pair in
`src-tauri/src/editor/geometry.rs`, every op declaring which space it speaks (P2 §4). New tools do not get
their own conversion.

## 5. Risks

| Risk | Mitigation |
|------|-----------|
| A new type renders in our viewer but not in others | D-A8 writes `/AP` where synthesis is absent; round-trip test opens the saved file with pdfium *and* asserts the dictionary keys |
| `/AP` disagrees with the geometry the annotation claims | Both are built from the same blob through one builder, mirroring the `appearance_for` discipline that already prevents bake/render drift |
| Reply chains orphan when a parent is deleted | Deletion cascades to replies in the same transaction; a reply whose parent is missing is **detached to a root**, never dropped |
| XFDF import duplicates on re-import | D-A10 matches on `/NM`; a repeat import is a no-op that reports its count |
| 13 types × save-rebuild becomes slow on a large document | Rebuild is per-document and already O(annotations); measured in the phase, and the edit copy is written once per save (P2-D2) |
| Enum growth breaks stored rows | D-A4 alias-on-read + D-A13 forward-safe version; tested with a v1 fixture row |
| Status changes not undoable | D-A6 makes them StackEntry pushes; tested |
| Comment pane disagrees with the page | D-A11 stateless view over the DB |

## 6. Definition of done

1. 13 types create, save, reopen and render; a round-trip test per family, not per type, plus a
   dictionary-keys assertion for the `/AP` types.
2. Comment pane: sort, filter, status edit, and a vitest covering each.
3. Reply chain: create, render, delete-parent cascade, FTS push of the reply text.
4. XFDF: export a document's annotations, re-import into a copy, assert equality and **zero**
   duplicates on a second import.
5. Search: a hit in each new text-bearing type resolves to page + annotation (D-A12).
6. Undo: one entry per gesture for create, update, status, reply, delete (D-A6).
7. `cargo fmt --check`, clippy deny-warnings, both `cargo test` shapes, `tsc`, vitest — all green,
   counts recorded.
8. `docs/RELEASE-NOTES.md` `## 1.1.0` written **before** the bump; build-only dispatch; user
   hand-confirms; tag.

## 7. Open for sign-off

1. **D-A1's 13 + 2 named** — confirm the palette boundary, and specifically that polygon/cloud
   stay unscheduled.
2. **D-A3's single-writer rule** and **D-A5's reply model** — the two decisions that would be
   expensive to reverse later.
3. **D-A9 excluding FDF** — confirm it is acceptable for XFDF to be the only annotation
   interchange in 1.1.0, with FDF waiting for P3.3.
