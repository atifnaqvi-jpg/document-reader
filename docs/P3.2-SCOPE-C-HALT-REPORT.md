## 2. The unit-5 work, and why it was not optional

D-SG4 says trust is "local configuration only", which places the anchor store under the
user's control. Before this unit it was not: `import_trust_anchor` could grow the store,
but `store::list_anchors` and `store::remove_anchor` had no caller outside the store's own
unit tests.

The consequence is not cosmetic. A user could import a CA and then never see, audit or
withdraw what they had trusted. If they imported the wrong CA — a test root, one from
another organisation, one since compromised — every later signature chaining to it would
reach `valid` forever, and there would be no way to say otherwise. A trust store that only
grows is not "configuration you control", whatever the design text says.

Two commands close it, both following the established `_with` split so the shipped path is
the tested path:

- `list_trust_anchors` — returns each anchor's base64 DER identity (what `forget_trust_anchor`
  takes), subject, expiry and import time. Newest first, so a just-imported anchor is where
  the user is looking. An empty store is an empty list, not an error.
- `forget_trust_anchor` — removes one anchor by that identity. Returns *whether* a row was
  deleted rather than raising on an unknown id: "it is already gone" is the state the user
  asked for, and a repeated click must not read as a fault.

The load-bearing test is `forgetting_an_anchor_takes_a_valid_badge_back_to_unknown`. One
fixed signed file, a clean CRL imported once and left alone, and the anchor as the only
variable across three assessments: `unknown` → `valid` after the import → `unknown` again
after forgetting. It ties the command to the badge, not to a row count.

## 3. What is explicitly not claimed

- **No UI for the new commands.** They are reachable and tested through the command path;
  nothing renders them yet. The same shape SCOPE-B was in before `744b64d`, and it must be
  closed before the phase row can be `[x]`.
- **CRL management does not exist at all.** Anchors can be listed and forgotten; for CRLs
  the store has only `add_crl` and `has_crl` — there is no list and no remove, so the
  capability is missing rather than merely unwired. A stale or wrong CRL currently cannot be
  withdrawn through the app, and a user cannot even see which lists are in force. This is the
  same *class* of gap unit 5 closed, but it is more work, and it is *not* fixed here.
- **No tag, no installer hand-test.** 1.2.0 is not released. AGENTS.md rule 1 means a phase
  is `[x]` only with the gate green *and* the installer hand-tested by the user.
- **The Windows `STATUS_ACCESS_VIOLATION` is still undiagnosed.** It did not reproduce on
  any run today, including both Windows jobs in this phase. Not reproducing is not
  diagnosing; the item stays open.

## 4. The question that needs a human answer

The unit numbering in use does not match `docs/P3.2-protect-redact-signatures-DESIGN.md` §10.

§10 step 6 lists SCOPE-C's internal order as: CMS module + PFX module + verify (I-SG1..I-SG4)
→ Windows-store module → DocMDP (I-SG5) → badges. The working history recorded unit 1 as
certify/DocMDP, unit 2 as the DER-length flake fix, and unit 4 as the UI/command wiring. Both
numberings are in the record, so "unit 5" does not deterministically mean the same thing to
two readers.

Rather than guess, this unit was chosen on the *substance* of what D-SG4 requires and what
the tree was actually missing, not on its position in either list. That is why the work is
defensible whatever the numbering turns out to be — but the next unit's identity is not, so
it is being asked rather than assumed.

**Question for the user:** which is authoritative for the remaining SCOPE-C work — the
`§10` sub-order, or the unit numbering used in the session logs? The answer determines what
"unit 6" is, and this report deliberately stops short of picking.

## 5. Candidate next steps, in the order the evidence suggests

1. **CRL listing and removal** — the exact asymmetry named in §3, same invariants already
   proven for anchors. Smallest gap with a correctness argument behind it.
2. **A UI surface for trust management** — list, import, forget, in one panel. Without it the
   commands are reachable only from a test, which is the state SCOPE-B was in before
   `744b64d` and was worth a whole unit to fix.
3. **1.2.0 release prep** — notes, version bump across the six carriers, prerelease gate.
   Blocked on the UI work above, per rule 1.
