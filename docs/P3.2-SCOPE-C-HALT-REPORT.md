## 2. The unit-5 work, and why it was not optional

D-SG4 says trust is "local configuration only", which places the anchor store under the
user's control. Before this unit it was not: `import_trust_anchor` could grow the store,
but `store::list_anchors` and `store::remove_anchor` had no caller outside the store's own
unit tests.

The consequence is not cosmetic. A user could import a CA and then never see, audit or
withdraw what they had trusted. If they imported the wrong CA — a test root, one from
another organisation, one since compromised — every later signature chaining to it would
reach `valid` forever, and there would be no way to say otherwise. A trust store that only
grows is not "configuration you control", whatever the design text says.

Two commands close it, both following the established `_with` split so the shipped path is
the tested path:

- `list_trust_anchors` — returns each anchor's base64 DER identity (what `forget_trust_anchor`
  takes), subject, expiry and import time. Newest first, so a just-imported anchor is where
  the user is looking. An empty store is an empty list, not an error.
- `forget_trust_anchor` — removes one anchor by that identity. Returns *whether* a row was
  deleted rather than raising on an unknown id: "it is already gone" is the state the user
  asked for, and a repeated click must not read as a fault.

The load-bearing test is `forgetting_an_anchor_takes_a_valid_badge_back_to_unknown`. One
fixed signed file, a clean CRL imported once and left alone, and the anchor as the only
variable across three assessments: `unknown` → `valid` after the import → `unknown` again
after forgetting. It ties the command to the badge, not to a row count.

Mutation-verified (each mutant red, then restored green):

|--------|--------|
| `remove_anchor` always reports `false` | CAUGHT — 3 tests red, including the badge test |
| `remove_anchor` deletes then re-inserts the row | CAUGHT by the badge assertion itself: `left: Valid, right: Unknown` |
| `list_anchors` clears its rows before returning | CAUGHT — 3 tests |
| both new commands removed from `invoke_handler` | CAUGHT by `every_declared_command_is_registered` |

## 3. What is explicitly not claimed

Revised 2026-11-12. Two of the four original bullets were true at `417637f` and were closed
later the same day; they are struck through with the commit that closed them. The other two
still stand.

- ~~**No UI for the new commands.** They are reachable and tested through the command path;
  nothing renders them yet.~~ **Closed by `af6b095`.** `TrustPanel.tsx` lists anchors and CRLs,
  refreshes both together, and offers forget for each; `SignDialog`'s `TrustImportSection`
  imports both. It is mounted inside `SignDialog` rather than on a settings screen, because the
  question it answers — "why is this signature unknown?" — is the one that dialog exists for.
  The `af19780` guard (`every_registered_command_has_a_frontend_caller`) now makes a command
  with no caller a build failure, so this class cannot reopen silently.

- ~~**CRL management does not exist at all.** Anchors can be listed and forgotten; for CRLs the
  store has only `add_crl` and `has_crl` — there is no list and no remove, so the capability is
  missing rather than merely unwired.~~ **Closed by `1738798`.** `store::list_crls` and
  `store::remove_crl` exist, behind `list_trust_crls` / `forget_trust_crl`. `list_crls` carries
  `nextUpdate` deliberately: past that date a clean list silently stops being evidence, and a UI
  that could not show the date would let a user keep trusting it. The load-bearing test is
  `forgetting_a_revocation_list_gives_the_badge_back` — one fixed signed file, anchor and clean
  CRL held constant, the revoked list as the only variable: `valid` → demoted → `valid` again.

- **No tag, no installer hand-test.** 1.2.0 is not released. AGENTS.md rule 1 means a phase
  is `[x]` only with the gate green *and* the installer hand-tested by the user.

- **The Windows `STATUS_ACCESS_VIOLATION` is still undiagnosed, and it has a second symptom.**
  It did not reproduce on any run on 2026-11-11, including both Windows jobs in this phase. On
  2026-11-12 it did, at `8d12b49`, in three of four attempts on the same `--include-ignored`
  step: two `0xc0000005` crashes in `textedit_gates` (~30/65 tests) and two hangs (25 min in CI,
  62 min in the release run), with one clean pass. **Not reproducing is not diagnosing, and one
  clean pass does not close it.** See §7 for the bound added in response.

- **Vector drawing under a redaction mark is disclosed, not removed.** D-RD2 scopes apply's
  removal to text operators, annotations and image XObjects; §8 lists vector graphics as not
  attempted. `69d726f` implements the disclosure: a mark covering only vector drawing is refused
  with the path count named, and a mixed mark reports `vectorPathsRemaining`. This is a
  deliberate limit, not an open defect.

## 4. The question that needs a human answer

**Revised 2026-11-12: the question was never answered, and the work proceeded anyway.** That
is recorded here rather than quietly forgotten, because the ambiguity is still real and will
recur at the next numbering decision.

The unit numbering in use does not match `docs/P3.2-protect-redact-signatures-DESIGN.md` §10.

§10 step 6 lists SCOPE-C's internal order as: CMS module + PFX module + verify (I-SG1..I-SG4)
→ Windows-store module → DocMDP (I-SG5) → badges. The working history recorded unit 1 as
certify/DocMDP, unit 2 as the DER-length flake fix, and unit 4 as the UI/command wiring. Both
numberings are in the record, so "unit 5" does not deterministically mean the same thing to
two readers.

Rather than guess, this unit was chosen on the *substance* of what D-SG4 requires and what
the tree was actually missing, not on its position in either list. That is why the work is
defensible whatever the numbering turns out to be — but the next unit's identity is not, so
it is being asked rather than assumed.

**Question for the user:** which is authoritative for the remaining SCOPE-C work — the
`§10` sub-order, or the unit numbering used in the session logs? The answer determines what
"unit 6" is, and this report deliberately stops short of picking.

**What happened next.** No answer arrived. `1738798` was committed as "unit 6" and is the CRL
work — §5's candidate 1, i.e. the numbering followed *substance*, not §10. That is defensible
but it is not a resolution: under §10's order the next thing would have been the Windows-store
module or DocMDP, depending where the reader places CMS/PFX/verify. Anyone reading "unit 6"
in the log still cannot tell which convention produced it. **The question stands**, and it
should be settled before SCOPE-C numbering is cited in any release-facing document.

## 7. The Windows bound added on 2026-11-12

The `--include-ignored` step on Windows has now been observed to fail three ways on the same
binary: `0xc0000005` crash in `textedit_gates`, a hang, and a clean pass. The hang is the worst
outcome because the step declared no `timeout-minutes`, so it reported `in_progress` until
GitHub's six-hour job cap — telling nobody anything, and blocking `rerun-failed-jobs` for the
whole time.

Both offending jobs now carry a bound, and the bound is measured rather than guessed:

| Job | Healthy duration (measured) | Bound |
|-----|-----------------------------|-------|
| `ci.yml` → `windows-check` | 380 s (2026-11-12, run 43126273588) | `timeout-minutes: 30` |
| `release-windows.yml` → `build-windows` | 523 s (run 43133327347) | `timeout-minutes: 45` |

30 and 45 minutes are roughly 5× the observed healthy duration, which leaves room for a cold
cache and a slow runner while still turning a hang into a named failure inside a coffee break
instead of an overnight silence. The bound does not make the flake go away — it makes the flake
*legible*, which is the prerequisite for diagnosing it. The root cause remains open.
