# P2.4.3 §1 — Why metric extraction fails for the Maastricht font class (investigation)

Ran before any code, on `p2-windows-test` at `79295f3` (0.4.2), with a throwaway probe
(`src-tauri/tests/zz_probe.rs`, deleted before the Phase-A commit) that builds one page per
font class with lopdf's public API and asks the real production functions —
`textlocate::font_info`, `substitute::FontMetrics::resolve`, `FontMetrics::advance` — what
they can measure. Output is verbatim.

## The resolver under test

`FontMetrics::resolve` (`src-tauri/src/editor/substitute.rs:261`) has two sources, in order:

1. **AFM** — `textlocate::font_info(...).base_font`, `strip_subset_prefix`ed, looked up in the
   pinned standard-14 table (`afm::widths_for`). Decided *entirely by the `/BaseFont` name*;
   no program is read.
2. **TrueType** — `embedded_font_program(...)`, which reads **only**
   `/FontDescriptor /FontFile2` (TrueType) and `/FontFile3` (OpenType). `ttf_parser::Face::parse`
   then has to accept the bytes.
3\. Otherwise `Nominal` → `advance()` returns `None` → T22 ("unmeasurable") → the page refuses.

## Findings

* **There is no single cause, and none of the plausible ones in the design's §1 list is it.**
  Verified, class by class:

  | Class | Font shape | Verdict |
  |---|---|---|
  | A | No `/FontDescriptor` at all, `/BaseFont /Monaco` | **the AFM path is name-only** — `Monaco` is not standard-14, so the *name* decides: `Nominal`, no measurement |
  | A′ | `/FontDescriptor` present but **no `FontFile*` key** | same — no program to read, name not standard-14 → `Nominal` |
  | B | `/FontFile` (Type 1 / PFB), the classic Type-1 embedding | **skipped by design**: `embedded_font_program` reads only `FontFile2`/`FontFile3`; `ttf-parser` cannot read PFB → `Nominal` |
  | C | `/FontFile3 /Subtype /Type1C` carrying a **bare CFF** (the PowerPoint/OpenType-subset shape) | program **is** found (19436 bytes) but is **not an sfnt** → `ttf_parser::Face::parse` → `UnknownMagic` → `Nominal` |
  | D | `/FontFile3` carrying a whole **OTF** (sfnt wrapper + CFF outlines) | **measurable** (`ttf-parser` 0.25 reads CFF in an sfnt) |
  | E | `ABCDEE+Helvetica`, subset prefix, no program | **measurable by name** — the AFM path claims Helvetica's tables for a font whose actual glyphs were never checked |
  | F | `/FontFile2` real TrueType (the shape P2.4.2's fixtures use) | measurable |

* So the field report's font class is **A/A′/C, not A alone**: the class is
  *"the AFM path is a name lookup, and the program path is sfnt-only"*. `ABCDEE+Monaco`, a
  PowerPoint-embedded subset, is **A′** (a descriptor exists for the metrics but the program
  lives where `embedded_font_program` does not look, or `ttf` rejects what it finds), and a
  `Type1C` **bare-CFF** subset (C) fails even when the program *is* found. Both end at
  `Nominal`.

* **Is it a cheap parser gap?** Partly, but it is not the fix to lead with, for three reasons:

  1. **Bare CFF (C) has no `hmtx` at all.** CFF carries its own `CharStrings`/`Private DICT`
     widths in a format `ttf-parser` does not expose even for the `OTF` case — it reads the
     `hmtx` table, which a bare CFF does not have. Fixing C means a second font-format parser
     (CFF INDEX/CharString decoding), a new dependency-shaped change, and design §4 forbids a
     new dependency.
  2. **Type 1 / PFB (B) is the same story**, and `embedded_font_program`'s comment already
     records that skipping it is deliberate.
  3. **A is unfixable by extraction** — there is no program in the file to parse.

  So a parser patch would still leave A and B refusing, i.e. it would not clear the field
  report. **T23 (render-measured spans) is the only fix that covers every class**, which is
  exactly the design's stated reason for making it primary. No `substitute.rs` extraction fix
  is warranted; the honest change is the fallback chain, not the parser.

* **One real bug the probe did surface, and it is *not* a no-metrics bug:** class **E**. A
  subset-prefixed name whose tail is standard-14 (`ABCDEE+Helvetica`) gets the *standard-14
  metrics* with no check whatever that the glyphs match — the exact "silent mis-measure" T23
  exists to remove, in the one branch that *does* return a number today. It is left as-is in
  this round (changing it would re-open P2.4.2's frozen AFM-first ruling, and T23's ordering
  fixes it naturally: char-grid first, so E's quota stops being the name's guess), and
  recorded here as a finding rather than silently patched.

## Consequence for the primitive

Measured spans must come from **PDFium's per-character geometry**, which is present for A, A′,
B, C, D and E alike — the probe of the same fixtures (below) shows a complete char grid with
usable `tight`/`loose` boxes and per-char origins for the *unmeasurable* fonts too. That is T23a:
the rendered page is the oracle precisely because it is the one source every font class shares.

## Char-grid probe (same fixtures, for the primitive's shape)

```

  #0 'S' tight=(72.00,700.00,84.00,700.01) loose=(72.00,697.60,84.00,709.60) origin=(72.00,700.00)
  ... one 12pt advance per glyph, tight boxes exactly tile the run
  RUN "Science" box=(72.00,700.00,144.00,700.00) w=72.00 font=""

  #8 'n' tight=(168.00,700.00,180.00,700.01)
  #9 ' ' gen=true tight=(187.20,700.00,187.20,700.00)   <- the kern seam, PDFium *generates* the space
  #10 'c' tight=(187.20,700.00,199.20,700.01)
  RUN "DataScien ce" box=(72.00,700.00,199.20,700.00) w=127.20

=== space-kern-gap.pdf               page text: "foo bar"       chars: 7
  #2 'o' tight=(86.40,700.00,93.60,700.01)
  ...

=== fragmented-tj.pdf                page text: "Hello"         chars: 5
  #0 'H' tight=(72.92,700.00,79.75,708.62)  <- *tight* ink is inset from the advance box
  RUN "Hello" box=(72.92,699.83,99.11,708.62) w=26.18 font="Chrom Sans OTF"

=== simple-winansi.pdf               page text: "ALPHA\r\nDocument Reader P1 fixture, page one."
  #5 '\r' gen=true tight=(150.70,700.00,150.70,700.00) size=1.00   <- a generated break, zero-width
```

Two facts the primitive must honour, both visible above:

* **`tight` is ink, not advance.** For `Hello` (a proportional face) tight boxes leave gaps of
  ~0.6pt between glyphs; summing tight widths would under-measure the run by ~6%. `loose` is
  the per-character advance box (`72.00..80.66`, contiguous, no gaps). The primitive measures
  spans from **loose** boxes; `tight` is used only where the design asks for ink (none here).
* **PDFium inserts generated characters** — the `\r\n` after `ALPHA`, and the space at a kern
  seam (in `wider-replacement-orphan.pdf`). The walk must decide whether a generated char
  consumes a run character, or the alignment between a run's text and the grid drifts.

## Implementation notes (Phase B; deviations recorded verbatim)

* **T23c's preference order is implemented literally**, with P2.4.2's box≈span test demoted to
  the *suspicion* flag only. Where a span exists (clause 1: char-grid, else font metrics) the
  span **is** the quota, and a box wider than `span × BOX_SPAN_SLACK` marks the pair
  `box_suspicious`. Where **no** span exists, clause 2 supplies the box **only** for a strong
  pair whose box is the smallest one containing the run (`smallest_containing`, a new predicate);
  otherwise clause 3 refuses with the unchanged `fits-width` message. This differs from 0.4.2
  only in the new *source* of the span — 0.4.2's `Quota::Box` for a strong box ≈ span is now
  unreachable whenever a span exists, so every quota is a measured span or a smallest box, never
  a line box. Nothing was loosened: `span × BOX_SPAN_SLACK = 1.25` and the O1 tolerance formula
  are untouched, and clause 2 still requires `smallest_containing` (0.4.2 had no such guard for
  the orphan case, which is why the orphan's line box could be trusted).

* **New constant `ANCHOR_TOLERANCE = 0.1` (T23a).** The char-grid walk anchors at the run's own
  text-space origin. The first implementation used the pairing tolerance (`origin_tolerance`,
  `0.25 × size` = 3pt at 12pt) as the anchor slack, and `fragmented-tj.pdf` — the existing
  P2.4.1 gate fixture — **failed**: the second `l` in `Hello` re-anchored to the first `l`
  (whose advance is only 2.66pt at 12pt), matching one character too early. The span then began
  at character 3 instead of 4, so the head's `x1` overshot the next span's `x0` and the seam read
  as a ~3pt *overlap*, breaking the chain and splitting `Hello` into five runs. The anchor slack
  is a rounding band, not an ink offset — the two origins are the same pen position measured
  twice — so `0.1` is the correct order of magnitude. The walk also clamps the anchor to the
  paired box's left edge (`rect.x0 − origin_tolerance`), so it can never start left of the box.

* **`fragment_advance` is unchanged.** It still supplies `RawRun::advance` /
  `advance_exact` for the *fallback* and for the `mergeable` metric path; the char-grid gap
  simply pre-empts it inside `measured_gap` when both fragments have a span. No formula changed.

* **Fixtures regenerated, not edited by hand.** `unmeasurable-font.pdf` and
  `unmeasurable-chain-break.pdf` are emitted by `examples/make_p24_fixtures.rs` from
  `testpdf::unmeasurable_font_page()` / `unmeasurable_chain_break()`. The first attempt at the
  chain-break fixture used a single `TJ` array with a `-600` kern and did **not** reproduce the
  intended shape (PDFium joined it into one box, so there was no seam to break); the committed
  fixture instead uses two `Tj` operators placed at a zero rendered seam, which is the
  Maastricht line-1 geometry.
