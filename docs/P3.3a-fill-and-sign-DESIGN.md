### 1.1 What these facts settle about scope

N1 and N2 mean **two of the three signature kinds are UI work over an engine that already
works**. N3 means the third is not, and N4 means a drawn signature's pen weight is fixed at 2pt.
N10 means "permanently part of the page" is not available. Those four facts, not a preference, are
what §2's scope is built from.

## 2. Scope, and what this phase will not do

### 2.1 Delivers

1. A **Fill & Sign surface** reachable from the viewer: choose drawn, typed, or (if signed off)
   image; place it on a page at a point the user picks.
2. A **drawn** signature as an `Ink` overlay — pointer strokes captured by the existing ink tool
   path and stored as one or more strokes.
3. A **typed** signature as a `FreeText` overlay, with a small set of name-like styles rather than a
   script-font engine (D-N4).
4. A **mandatory visible label** carrying the meaning D-F8 requires, rendered in the artifact and
   in the UI (§2.2, D-N2).
5. **Placement assistance** from measured page geometry (§3.2), so a signature lands on the line
   rather than near it.
6. The **same save discipline as every other overlay**: nothing is written until the user saves, and
   the save produces a sibling copy (N7).

### 2.2 The label is part of the artifact, not a hint in the UI (D-N2)

D-F8's words are *"a visible, permanent label that it is a visual signature and carries no
cryptographic weight"*. Two readings are possible and only one survives the words:

- *A UI badge that disappears when the file is saved* satisfies "visible" on screen and leaves a
  file that claims to be signed with nothing to say otherwise. It also fails the moment the file
  leaves this application, which is exactly when the misreading matters.
- **A mark in the page content, beside the overlay, produced by the same save** is permanent and
  travels with the document.

**Ruling (D-N2, signed off 2026-11-22 as Q2 and Q3): the label is drawn into the page content as
part of the save that commits the overlay, and it reads:**

> **Visual signature — no cryptographic weight. This is not a digital signature.**

Q2 accepted the cost and Q3 approved that wording; both are settled. The cost, restated so it is not
a surprise in a hand test: the label is **not removable** without a content edit, which is the point,
and it makes the saved page differ from the original in a way the user did not draw.

**This is new engine work and the design admits it.** No current writer adds text to page content for
an annotation; `append_marks` emits graphics operators for shapes only. The label therefore needs a
content-stream text emission with a font resource, which is closer to the watermark path
(`editor/export.rs`, P2-F5) than to the annotation path.

### 2.3 Image signature — deferred out of 1.4.0 by ruling (Q1)

Given N3/N5, an image signature is a new writer path: decode the user's image, embed it as an image
XObject, wrap it in a form XObject that draws it, and point a new annotation kind at that form. That
is a self-contained unit of work with its own correctness surface (colour space, `/SMask` for
transparency, decode filters, size limits, and a decompression-bomb guard for a hostile image — the
tree already has one for PDFs, `bomb.pdf`, and an image path would need its equivalent).

**Ruling (Q1, signed off 2026-11-22): image signatures are deferred to their own later unit. 1.4.0
ships drawn and typed only.** The fork is closed: the recommendation was taken, and the reason it
was made stands — image's correctness surface must not hold the hand-test verdict on drawn and typed
hostage. The plan row names three kinds, so the deferral is recorded as a plan-row correction
(D-N3a) rather than left as an unmentioned shortfall. **This is not a silent skip**: the UI must not
offer an image option that does nothing, and the notes must say image is absent and why.

### 2.4 What this phase will not do

- **Not a digital signature.** No PKCS#7, no `/ByteRange`, no certificate, no TSA (R3). Nothing here
  calls `signature::sign` or `signature::store::assess`.
- **Not a badge.** No new `Badge` state, no new `SignatureBadge` rendering, and no path by which an
  overlay influences one (I-N2).
- **No flattening into page content** (N10). A saved signature stays an annotation.
- **No signature *fields*.** A signature field with a real signing handler is a different feature and
  is what `/FT /Sig` means in the specification; writing one without cryptographic weight would be
  the worst of both — a field a verifying tool would try to validate. Named here so it is not
  discovered as a gap.
- **No "remember my signature" store.** Out; it needs a storage and privacy decision of its own.
- **No stamp/business-card library.** Out.
- **No new save mechanism, no new command** (N7, N9/D-N3).

### 2.5 Pen weight for a drawn signature (N4)

The ink engine's 2pt fixed stroke is a fine *marker* and a heavy *signature* relative to the
handwriting a user expects to see. Two options: accept 2pt (zero work), or add a stroke-width field
to the ink blob (schema change, `SUPPORTED_BLOB_VERSION`-gated).

**Ruling (Q4, signed off 2026-11-22): the 2pt pen is accepted for 1.4.0, and a width field is a later
row.** The reason is worth keeping: changing a shared blob's shape for one tool's aesthetics is how a
marker blob becomes a signature blob with two meanings. If the hand test finds 2pt unusable for
signing, that is a finding to report — not a licence to change the blob mid-phase.

## 3. Placement

### 3.1 What is measured, and which baseline

Two baseline notions coexist in this tree and are **deliberately distinct** (`editor/textlocate.rs`):

- `RawRun::baseline()` — pen origin plus rise, **text space**, lopdf-derived.
- `RawRun::page_baseline()` — the frame applied to the origin plus rise, **page space**, documented
  as the one for comparing against PDFium (P2.7.4).

`Ts` moves the ink, not the pen, so the two disagree exactly where a rised line is involved. A
signature is placed on *the page*, so **placement uses the page-space notion only**. Using the
text-space one would put a signature above or below its line by the rise — a small, plausible,
wrong placement, which is the kind of defect that survives a hand test because it looks deliberate.

The measurement substrate is real: `editor::runmetrics::char_grid` reads every character's origin
from PDFium (via `character.origin()` in pdfium-render 0.8.37), and `commands::get_page_text_runs`
already puts that work behind the IPC boundary.

### 3.2 How placement is assisted (D-N1)

The correction in §3.3 matters here: the wire type carries `rect` and `width`, **not** a baseline.
So the design has two candidate mechanisms and picks the cheaper one:

| Mechanism | Needs | Verdict |
|---|---|---|
| **A. Snap to a run's box, corrected by the page's measured descender depth** — the user's release point picks the nearest `PageTextRun` whose `rect` contains the x, and the signature's baseline is set to the box's bottom edge **plus a measured offset** | nothing new on the wire; the offset is measured from the same PDFium grid the run came from | **Chosen, with a correction the measurement forced.** The box's lower edge is *not* within a rounding error of the page-space baseline: measured on the LEA form at `/home/ubuntu/work/lea-aufenthaltstitel.pdf`, a run's box bottom sits **1.46–2.59pt below** the pen origin at the page's type sizes (mean 1.57pt, and 0.063pt spread at one size across 1,658 characters). Snapping to the raw box bottom would put every signature a descender low — a quarter of a line at 6.96pt. The offset is a stable per-size constant, so one measured correction serves a page. See §3.2.1 |
| **B. Expose a page-space baseline field on `PageTextRun`** and snap to it exactly | one field on the wire type plus its mapping | **Rejected for 1.4.0.** It is a small change, but it puts a second baseline notion into a wire type whose comment already warns that box and baseline disagree for suspicious runs; and for the runs where they disagree, the UI needs the flag as well as the number. Recorded as a later row if hand-test shows box-snapping is visibly off — and **the measurement below strengthens rather than weakens this**: the correction is a single constant, not per-run data, so it does not need a wire field |

**Ruling proposed (D-N1): placement snaps to the nearest run box's bottom edge plus the measured
descender correction when the release point lies within a line-height of a run, and otherwise lands
exactly where the user released.** A snap is shown before it is committed, so an unwanted snap is
visible rather than silent. The `boxSuspicious` runs are **excluded from snapping** rather than
snapped with a warning: a box that claims a whole line for one word is the shape that put an earlier
misalignment into 1.1.0, and snapping to it would place a signature against a line the user did not
pick.

#### 3.2.1 The measurement that corrected this section (2026-11-22)

This section originally claimed the box bottom "is within a rounding error of the page-space
baseline for a line-sized run". That claim was a reading of the code, not a measurement of a
document, and it is **wrong**. Measured through `PdfProvider::char_grid` on the LEA fixture page 0
and pinned by `tests/fillsign_facts.rs`:

| Quantity | Measured |
|---|---|
| positioned characters on page 0 | 2,526 |
| type sizes present | 6.96pt (dominant, 1,658 chars) and 12pt |
| `origin_y − box_bottom` at 12pt | 0.000 to 2.592pt, mean 1.567pt |
| same, at 6.96pt across 1,658 chars | 1.462 to 1.524pt, **spread 0.063pt** |

Two facts follow, and both are what the implementation must encode:

1. **The box bottom is a descender, not the baseline.** The loose box is the *advance* box and
   extends to the font's descent. A raw box-bottom snap is wrong by that depth on every run.
2. **The depth is essentially constant per size** (0.063pt spread over 1,658 characters). So the
   correction is one number measured per page, not per-run data and not a wire field.

The 0.000 minimum at 12pt is the honest part of the number: some runs report no descent at all, so
the correction must clamp rather than subtract blindly — subtracting 1.57pt from a run whose box
already ends on the baseline would lift it above the line. That is why the tests pin a bound
(`min_depth > -0.5`, `max_depth < font_size`) and consistency rather than a single magic constant.

The tests are `#[ignore]`d and gated on `LEA_FIXTURE`, so a checkout without the identity document
prints a skip rather than silently passing.

### 3.3 The correction this design makes to the inherited fact

The 2026-11-15 probe recorded that *"the measurement substrate for signature placement exists; it is
not new work"*, and that is true of the engine. It is **not** true of the UI boundary: the wire type
`PageTextRun` exposes `rect` and `width` and no baseline, so a UI that wanted an exact page-space
baseline has nothing to read. **This is the one place the inherited note overstates readiness**, and
§3.2 resolves it by snapping to the box rather than adding the field. Stated here because the
alternative — writing a design that assumes a field exists and discovering it in implementation — is
the drift `docs_citations` exists to catch.

## 4. Frozen decisions

### D-N1 — Placement snaps to a measured run box, excludes suspicious boxes, and shows the snap before committing.

See §3.2. Rationale: measured page geometry beats a raw pointer position, and the exclusion is the
difference between using a measurement and trusting it blindly.

### D-N2 — The "visual signature, no cryptographic weight" label is part of the artifact.

See §2.2. This is D-F8 taken literally. **Signed off 2026-11-22 (Q2, Q3):** the label is written into
page content, and its wording is exactly *"Visual signature — no cryptographic weight. This is not a
digital signature."* One constant in the code is the single source for both the page-content string
and the UI string.

### D-N3 — Fill & Sign adds no new command; it reuses `add_annotation`.

Rationale: `add_annotation` already refuses on a document whose certification forbids annotation
changes (N9), already pushes the FTS row in the same transaction (P2-D5), and is already governed.
A new command would need its own gate call, and a gate call a test cannot reach is the unreachable
guard the forms phase's own note warns about. Reuse also means D8's save boundary and D7's
single-render rule arrive already satisfied, because they were built for annotations.

### D-N4 — Typed signatures are `FreeText` with a small, named set of styles.

No script-font engine, no font embedding beyond what the free-text path already does (`/Helv` in
`/DR`). A signature is not typography; a user who wants a particular look draws it.

### D-N3a — 1.4.0 ships two of the three signature kinds; image is deferred by ruling.

**Signed off 2026-11-22 (Q1).** Drawn and typed ship in 1.4.0. Image is deferred to its own later
unit with its own design and its own hand test. Consequences that follow, all of which the
implementation must honour:

- The surface offers **drawn** and **typed** only. No disabled image button, no "coming soon" — an
  option that cannot act is a worse answer than its absence.
- `docs/P3-PLAN.md` P3.3a's scope text said three kinds; that row is corrected to two in this landing
  cycle, with image recorded as a later row rather than dropped.
- Release notes say image is absent and name the deferral as a decision, not a defect.

### D-N5 — Drawn signatures are `Ink` at the engine's existing stroke width.

See §2.5. **Signed off 2026-11-22 (Q4): 2pt accepted for 1.4.0, width field is a later row.** Recorded
as a decision with its reason rather than left as an unexamined default, because "the marker tool's
pen weight is the signature tool's pen weight" is a claim a reader should be able to disagree with.

### D-N6 — An overlay is never an input to signature assessment, and the test is on the boundary, not on the badge.

I-N2 is enforced where the mistake would happen: a test asserts that placing an overlay leaves
`signature::store::assess` returning `None` for an unsigned document, and that a signed document's
badge is byte-identical before and after an overlay is added. The second half is the one that
matters: it is easy to satisfy "no verdict" by returning a *different* wrong answer.

**FINDING 2026-11-23 — the second half cannot be satisfied as written, and it is not a missing
test.** The first half landed (`an_overlay_never_makes_an_unsigned_document_look_signed`, proven
by mutation: making any annotation count as a signature fails it). The second half is blocked, and
the reason is a contradiction inside the project rather than unfinished work.

Measured on a real signed file (`tests/fixtures/signing/trust/leaf.pfx`, anchored so the badge is
`valid`), against `signature::store::assess`:

| What was done to the signed bytes | `integrity` | `badge` |
|---|---|---|
| untouched | `Intact` | `Valid` |
| re-saved by `lopdf` with **no** annotations at all | `Damaged` | `Modified` |
| `apply_annotations` with one overlay | `Damaged` | `Modified` |
| pure `IncrementalDocument` append, empty revision | `Intact` | `Modified` |

So an overlay *cannot* leave the badge unchanged, for two independent reasons:

1. **`annotate.rs` rewrites the whole file.** Its module header states this deliberately: "load the
   original bytes, rebuild *every* annotation ... and write the result", which is a full `save_to`,
   not an incremental append. That drops the signature's `/Contents` revision, and the table above
   shows a bare re-save with zero annotations does the same. The overlay is not the culprit; the
   writer is. Fixing it means making annotation saves incremental — a change to the P2 save path
   that this phase's own N7/D-N3 forbids ("no new save mechanism").
2. **`badge.rs` defines `Modified` to *include* a later revision**, not only damaged bytes: "the
   signed bytes changed, or a later revision was appended" (the `Badge::Modified` doc
   comment in `badge`). An incremental append — the
   only way to keep `Intact` — still yields `Modified` by that definition, as the fourth row shows.
   So even after fixing (1), "badge byte-identical" would still fail unless `badge.rs`'s
   definition changed.

The row as written therefore asks for a state the product deliberately does not have. This is a
ruling-class question, not a test-writing one: either D-N6's second half is amended to "an overlay
does not make a signed document's badge *worse* than a later revision already makes it" (i.e.
`Modified`/`Intact`, not `Valid`), or the save path becomes incremental and `badge.rs` distinguishes
"appended, integrity intact" from "bytes damaged". The first is a documentation fix; the second is
a change to P3.2's badge contract and cannot be made inside P3.3a. `PLANNED_SYMBOLS` still carries
`an_overlay_leaves_a_signed_documents_badge_unchanged` so the gap stays visible and the guard fails
if it is quietly dropped.

## 5. Where Fill & Sign sits in the UI

`AnnnotationOverlay`-style sibling layers already arbitrate by precedence in `ViewerPane.tsx`
(`docs/P3.3-forms-DESIGN.md` §10.2). Fill & Sign takes a place in that chain as a **placement mode**,
not a fourth independent surface: while it is active the pointer places a signature, and the ink
pointer handler is what supplies the strokes for the drawn case. The Save control is the existing
one that commits annotations — no second Save, for the same reason the forms phase refused N copies
per keystroke: one user action must not produce two files.

## 10. Implementation addendum — the surface unit (2026-11-15, after §5 was given the word)

Section 5 was ruled the next unit with the instruction to work facts-first. This section records
what the enumeration found, because three of the four facts changed what had to be built and two
of them contradict what earlier state notes claimed.

### 10.1 How a placement can reach `apply_annotations` today

Enumerated by reading the tree, not by reading the plan. There are exactly **two** commands that
call `annotate::apply_annotations`, and they differ in a way that matters:

| Command | Where it writes | Certification gate | Use for Fill & Sign |
|---|---|---|---|
| `save_edits` (`commands::save_edits`) | a **new sibling** path via `save::next_edited_path` | **none in the function** | yes — this is "one sibling copy" |
| `overwrite_edits` (`commands::overwrite_edits`) | **overwrites the original** via `write_atomically` | `refuse_if_certification_forbids(…, Annotation)` | no |

**The finding that changes the surface.** The sibling-copy path — the only one a Fill & Sign
save may use, because §8.1 and the acceptance row both say "one sibling copy" — carries **no
`P=1`/`P=2` refusal**. The certification gate lives on the *overwrite* path. So the §6 acceptance
row `the_certification_gate_refuses_a_p1_and_p2_signature_placement` cannot be satisfied by
"the save does it": on the path Fill & Sign actually uses, nothing refuses.

That is not a defect to fix in `save_edits` — a plain annotation save legitimately writes a new
copy of a certified document without altering the original, and adding a refusal there would
break that. It means **the refusal must happen at the placement surface**, which is the point at
which the user is told why. `add_annotation` already refuses on a certified document (it calls
the same gate before writing the row), so a placement that goes through `add_annotation` *is*
refused today. **Verified:** `add_annotation` refuses before the row exists, so a refusal leaves
no row to clean up. The surface therefore inherits the refusal for free and must not add a second
copy of it.

### 10.2 What `SignDialog` does and does not cover

`SignDialog.tsx` is the **P3.3 cryptographic signing flow**: pick a certificate, choose an approval
or certification level (D-SG6), write a `/Sig` dictionary. It is a different feature that shares a
verb. It does not, and must not, place a visual mark — I-F6 forbids any code path returning a
cryptographic verdict for a visual overlay, and conversely a cryptographic signature is not a
visual one. **Nothing in it is reusable for Fill & Sign**, and the one thing that must never
happen is the two appearing adjacent in a way that invites reading our visual label as a verdict.

### 10.3 What geometry the char-grid gives the placement assistance

`get_page_text_runs` is already an invoke (`src/api/invoke.ts:374`) returning `PageTextRun[]`,
whose wire shape carries `rect` (page-space box, bottom-left origin), `width`, `fontSize`,
`boxSuspicious`, and `pairConfidence`. It carries **no baseline** — §3.3's correction stands.

Two independent sources for the baseline now exist, and it matters which the surface uses:

* the grid's **character origins** (`origin_y`), which *are* the pen origin — this is what
  `textedit::rendered_baseline` uses, and it is exact;
* the box's `y0`, which sits below the baseline by the descender depth.

§3.2.1 measured the depth at 1.462–1.524pt for 6.96pt type (spread 0.063pt) and 0.000–2.592pt at
12pt. **The 0.000 minimum is not a rounding curiosity, it is a hazard**: a correction that
subtracts blindly would lift a signature *above* the line on those runs. D-N1's decision is
therefore implemented as: snap the *baseline* to the run's measured baseline, computed from
`rect.y0` **clamped** against `fontSize` (never above `y0`, never more than one em below), and
refuse to snap at all when `boxSuspicious` is true, because a suspicious box is the case where the
box is known not to be line-sized.

`boxSuspicious` is the wire's own warning and is used as the exclusion rather than a second
heuristic, so a run the rest of the app already distrusts cannot silently become a signature
anchor.

### 10.4 How the label and the `/AP` are proven on the placed file

Three layers, because each can pass while another fails:

1. **The label is in the artifact** — `annotate.rs`'s existing `*_carries_its_label_in_page_content`
   tests, on the real `apply_annotations` path.
2. **A viewer draws the mark and the label** — `tests/signature_label_pixels.rs` (this phase,
   added 2026-11-22). Proved for `signature_label` directly; §10.5 extends the same oracle to a
   file produced by `apply_annotations` rather than by the writer alone.
3. **The surface produces a row the backend accepts** — a frontend test asserting the emitted
   `InkData`/`FreeTextData` carries `visualSignature: true`, which is the flag whose absence is
   the entire reason no user can place a signature today.

### 10.5 Decisions this surface forced (recorded, not invented)

* **D-N6 — The surface sets `visualSignature` on the row, and the backend does not infer it.**
  Inferring "this ink is a signature" from a stroke count or a size would be a guess, and a wrong
  guess either labels an ordinary annotation (§2.5's accepted cost, inverted) or leaves a real
  signature unlabelled. The flag is the caller's declaration, written where the user's intent is.
* **D-N7 — A placed signature is an ordinary annotation row until saved.** No new table, no new
  column: §5's "one Save" and P2-D2 persistence both fall out of the existing `annotations` table
  plus `save_edits`. A surface with its own storage would be a second file-writing path, which is
  the thing §5 explicitly refuses.
* **D-N8 — The snap is shown before it commits.** D-N1 requires the snap be visible pre-commit.
  Implemented as a preview outline of the target box's baseline while the pointer is over it,
  drawn in the overlay layer, cleared on pointer-leave. No preview is drawn for a suspicious box,
  because there is nothing honest to preview.
