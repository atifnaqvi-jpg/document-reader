## 2. Scope, and what this phase will not do

### 2.1 Delivers

1. A **Fill & Sign surface** reachable from the viewer: choose drawn, typed, or (if signed off)
   image; place it on a page at a point the user picks.
2. A **drawn** signature as an `Ink` overlay — pointer strokes captured by the existing ink tool
   path and stored as one or more strokes.
3. A **typed** signature as a `FreeText` overlay, with a small set of name-like styles rather than a
   script-font engine (D-N4).
4. A **mandatory visible label** carrying the meaning D-F8 requires, rendered in the artifact and
   in the UI (§2.2, D-N2).
5. **Placement assistance** from measured page geometry (§3.2), so a signature lands on the line
   rather than near it.
6. The **same save discipline as every other overlay**: nothing is written until the user saves, and
   the save produces a sibling copy (N7).

### 2.2 The label is part of the artifact, not a hint in the UI (D-N2)

D-F8's words are *"a visible, permanent label that it is a visual signature and carries no
cryptographic weight"*. Two readings are possible and only one survives the words:

- *A UI badge that disappears when the file is saved* satisfies "visible" on screen and leaves a
  file that claims to be signed with nothing to say otherwise. It also fails the moment the file
  leaves this application, which is exactly when the misreading matters.
- **A mark in the page content, beside the overlay, produced by the same save** is permanent and
  travels with the document.

**Ruling (D-N2, signed off 2026-11-22 as Q2 and Q3): the label is drawn into the page content as
part of the save that commits the overlay, and it reads:**

> **Visual signature — no cryptographic weight. This is not a digital signature.**

Q2 accepted the cost and Q3 approved that wording; both are settled. The cost, restated so it is not
a surprise in a hand test: the label is **not removable** without a content edit, which is the point,
and it makes the saved page differ from the original in a way the user did not draw.

**This is new engine work and the design admits it.** No current writer adds text to page content for
an annotation; `append_marks` emits graphics operators for shapes only. The label therefore needs a
content-stream text emission with a font resource, which is closer to the watermark path
(`editor/export.rs`, P2-F5) than to the annotation path.

### 2.3 Image signature — deferred out of 1.4.0 by ruling (Q1)

Given N3/N5, an image signature is a new writer path: decode the user's image, embed it as an image
XObject, wrap it in a form XObject that draws it, and point a new annotation kind at that form. That
is a self-contained unit of work with its own correctness surface (colour space, `/SMask` for
transparency, decode filters, size limits, and a decompression-bomb guard for a hostile image — the
tree already has one for PDFs, `bomb.pdf`, and an image path would need its equivalent).

**Ruling (Q1, signed off 2026-11-22): image signatures are deferred to their own later unit. 1.4.0
ships drawn and typed only.** The fork is closed: the recommendation was taken, and the reason it
was made stands — image's correctness surface must not hold the hand-test verdict on drawn and typed
hostage. The plan row names three kinds, so the deferral is recorded as a plan-row correction
(D-N3a) rather than left as an unmentioned shortfall. **This is not a silent skip**: the UI must not
offer an image option that does nothing, and the notes must say image is absent and why.

### 2.4 What this phase will not do

- **Not a digital signature.** No PKCS#7, no `/ByteRange`, no certificate, no TSA (R3). Nothing here
  calls `signature::sign` or `signature::store::assess`.
- **Not a badge.** No new `Badge` state, no new `SignatureBadge` rendering, and no path by which an
  overlay influences one (I-N2).
- **No flattening into page content** (N10). A saved signature stays an annotation.
- **No signature *fields*.** A signature field with a real signing handler is a different feature and
  is what `/FT /Sig` means in the specification; writing one without cryptographic weight would be
  the worst of both — a field a verifying tool would try to validate. Named here so it is not
  discovered as a gap.
- **No "remember my signature" store.** Out; it needs a storage and privacy decision of its own.
- **No stamp/business-card library.** Out.
- **No new save mechanism, no new command** (N7, N9/D-N3).

### 2.5 Pen weight for a drawn signature (N4)

The ink engine's 2pt fixed stroke is a fine *marker* and a heavy *signature* relative to the
handwriting a user expects to see. Two options: accept 2pt (zero work), or add a stroke-width field
to the ink blob (schema change, `SUPPORTED_BLOB_VERSION`-gated).

**Ruling (Q4, signed off 2026-11-22): the 2pt pen is accepted for 1.4.0, and a width field is a later
row.** The reason is worth keeping: changing a shared blob's shape for one tool's aesthetics is how a
marker blob becomes a signature blob with two meanings. If the hand test finds 2pt unusable for
signing, that is a finding to report — not a licence to change the blob mid-phase.

## 3. Placement

### 3.1 What is measured, and which baseline

Two baseline notions coexist in this tree and are **deliberately distinct** (`editor/textlocate.rs`):

- `RawRun::baseline()` — pen origin plus rise, **text space**, lopdf-derived.
- `RawRun::page_baseline()` — the frame applied to the origin plus rise, **page space**, documented
  as the one for comparing against PDFium (P2.7.4).

`Ts` moves the ink, not the pen, so the two disagree exactly where a rised line is involved. A
signature is placed on *the page*, so **placement uses the page-space notion only**. Using the
text-space one would put a signature above or below its line by the rise — a small, plausible,
wrong placement, which is the kind of defect that survives a hand test because it looks deliberate.

The measurement substrate is real: `editor::runmetrics::char_grid` reads every character's origin
from PDFium (via `character.origin()` in pdfium-render 0.8.37), and `commands::get_page_text_runs`
already puts that work behind the IPC boundary.

### 3.2 How placement is assisted (D-N1)

The correction in §3.3 matters here: the wire type carries `rect` and `width`, **not** a baseline.
So the design has two candidate mechanisms and picks the cheaper one:

| Mechanism | Needs | Verdict |
|---|---|---|
| **A. Snap to a run's box** — the user's release point picks the nearest `PageTextRun` whose `rect` contains the x, and the signature's baseline is set to the box's bottom edge | nothing new on the wire | **Chosen.** The box's lower edge is derived from measured PDFium geometry, and it is within a rounding error of the page-space baseline for a line-sized run — the case N8's `boxSuspicious` flag exists to warn about |
| **B. Expose a page-space baseline field on `PageTextRun`** and snap to it exactly | one field on the wire type plus its mapping | **Rejected for 1.4.0.** It is a small change, but it puts a second baseline notion into a wire type whose comment already warns that box and baseline disagree for suspicious runs; and for the runs where they disagree, the UI needs the flag as well as the number. Recorded as a later row if hand-test shows box-snapping is visibly off |

**Ruling proposed (D-N1): placement snaps to the nearest run box's bottom edge when the release
point lies within a line-height of a run, and otherwise lands exactly where the user released.** A
snap is shown before it is committed, so an unwanted snap is visible rather than silent. The
`boxSuspicious` runs are **excluded from snapping** rather than snapped with a warning: a box that
claims a whole line for one word is the shape that put an earlier misalignment into 1.1.0, and
snapping to it would place a signature against a line the user did not pick.

### 3.3 The correction this design makes to the inherited fact

The 2026-11-15 probe recorded that *"the measurement substrate for signature placement exists; it is
not new work"*, and that is true of the engine. It is **not** true of the UI boundary: the wire type
`PageTextRun` exposes `rect` and `width` and no baseline, so a UI that wanted an exact page-space
baseline has nothing to read. **This is the one place the inherited note overstates readiness**, and
§3.2 resolves it by snapping to the box rather than adding the field. Stated here because the
alternative — writing a design that assumes a field exists and discovering it in implementation — is
the drift `docs_citations` exists to catch.

## 4. Frozen decisions

### D-N1 — Placement snaps to a measured run box, excludes suspicious boxes, and shows the snap before committing.

See §3.2. Rationale: measured page geometry beats a raw pointer position, and the exclusion is the
difference between using a measurement and trusting it blindly.

### D-N2 — The "visual signature, no cryptographic weight" label is part of the artifact.

See §2.2. This is D-F8 taken literally. **Signed off 2026-11-22 (Q2, Q3):** the label is written into
page content, and its wording is exactly *"Visual signature — no cryptographic weight. This is not a
digital signature."* One constant in the code is the single source for both the page-content string
and the UI string.

### D-N3 — Fill & Sign adds no new command; it reuses `add_annotation`.

Rationale: `add_annotation` already refuses on a document whose certification forbids annotation
changes (N9), already pushes the FTS row in the same transaction (P2-D5), and is already governed.
A new command would need its own gate call, and a gate call a test cannot reach is the unreachable
guard the forms phase's own note warns about. Reuse also means D8's save boundary and D7's
single-render rule arrive already satisfied, because they were built for annotations.

### D-N4 — Typed signatures are `FreeText` with a small, named set of styles.

No script-font engine, no font embedding beyond what the free-text path already does (`/Helv` in
`/DR`). A signature is not typography; a user who wants a particular look draws it.

### D-N3a — 1.4.0 ships two of the three signature kinds; image is deferred by ruling.

**Signed off 2026-11-22 (Q1).** Drawn and typed ship in 1.4.0. Image is deferred to its own later
unit with its own design and its own hand test. Consequences that follow, all of which the
implementation must honour:

- The surface offers **drawn** and **typed** only. No disabled image button, no "coming soon" — an
  option that cannot act is a worse answer than its absence.
- `docs/P3-PLAN.md` P3.3a's scope text said three kinds; that row is corrected to two in this landing
  cycle, with image recorded as a later row rather than dropped.
- Release notes say image is absent and name the deferral as a decision, not a defect.

### D-N5 — Drawn signatures are `Ink` at the engine's existing stroke width.

See §2.5. **Signed off 2026-11-22 (Q4): 2pt accepted for 1.4.0, width field is a later row.** Recorded
as a decision with its reason rather than left as an unexamined default, because "the marker tool's
pen weight is the signature tool's pen weight" is a claim a reader should be able to disagree with.

### D-N6 — An overlay is never an input to signature assessment, and the test is on the boundary, not on the badge.

I-N2 is enforced where the mistake would happen: a test asserts that placing an overlay leaves
`signature::store::assess` returning `None` for an unsigned document, and that a signed document's
badge is byte-identical before and after an overlay is added. The second half is the one that
matters: it is easy to satisfy "no verdict" by returning a *different* wrong answer.

## 5. Where Fill & Sign sits in the UI

`AnnnotationOverlay`-style sibling layers already arbitrate by precedence in `ViewerPane.tsx`
(`docs/P3.3-forms-DESIGN.md` §10.2). Fill & Sign takes a place in that chain as a **placement mode**,
not a fourth independent surface: while it is active the pointer places a signature, and the ink
pointer handler is what supplies the strokes for the drawn case. The Save control is the existing
one that commits annotations — no second Save, for the same reason the forms phase refused N copies
per keystroke: one user action must not produce two files.

SHA-256 `c3bbc6e99d372b3a32fd46c2b116215ba49cc57a543322412d96285e2a8656a3`, so the fixture the
acceptance row ran against is identifiable later.

**What kind of fixture this is, and why that matters here.** It is the *no-`/AcroForm`* baseline:
nothing in it declares a field, and its lines are **drawn rules** — graphics, not form widgets. That
makes it the right fixture for this phase and the wrong one for forms: there is no field to fill and
no `/Annots` hint to follow, so any placement assistance must come from **measured text and drawn
geometry**, which is exactly what §3.2's snapping and §8-facts work must do. A form-bearing fixture
would have let a snapping implementation pass by reading widget rectangles instead of measuring.

It is also the fixture that proves the label does not land off the page: a 4-page Excel table has
content close to the margins, and the label is emitted at a fixed offset from the overlay.

## 8. Consequences the user should weigh

### 8.1 Image signature is deferred, not dropped (Q1)

The plan row named three kinds; 1.4.0 ships two. Image moves to its own unit with its own design and
hand test, because its correctness surface (colour space, `/SMask`, decode filters, a decompression
bomb guard) is large enough to fail a verdict on its own terms and small enough to be skipped in a
review of a "Fill & Sign" diff. The notes say image is absent; the UI does not offer it.

### 8.2 The consequences the user weighed at sign-off

1. **A saved signature is an annotation, not baked pixels** (N10). In another viewer it can be moved,
   deleted, or hidden. That is a difference from Acrobat's Fill & Sign worth stating in the release
   notes rather than leaving to be discovered.
2. **The label changes the page** (D-N2) and is not removable without a content edit. Accepted as Q2.
3. **Placement is assisted, not automatic** (D-N1). No field detection, no "sign here" inference —
   that is a different feature with its own correctness obligations.
4. **The drawn signature's weight is the marker's weight** (D-N5), which a user may notice. Accepted
   as Q4.
