# Facts for the CMS signer (P3.2 SCOPE-C, unit 4)

Measured 2026-11-08 on branch `p2-windows-test` at `4725d13`, arm64 Linux, OpenSSL 3.0.13.
Every line below is a measurement, not a reading of documentation. The design it serves is
`docs/P3.2-protect-redact-signatures-DESIGN.md` (I-SG1, D-SG1, D-SG2, K24, K25).

Method: the substrate fixture's own key and certificate (from
`src-tauri/tests/fixtures/signing/signer.pfx`), the substrate's gap-exclusion convention, and
OpenSSL as a **second implementation** — the one I-SG1 demands so a symmetric bug cannot pass
both sides.

## F1. The gap-excluded byte string is what a CMS signature covers

Convention (already fixed by `tests/signature_substrate.rs`): the digest covers everything
except the `<`, the hex digits and the `>`. Concretely, for a signed file laid out
`prefix + "<" + hex + ">" + suffix`, the signed content is `prefix || suffix`.

Verified both directions with OpenSSL 3.0.13:

- `openssl cms -verify -binary -inform DER -in cms.der -content (prefix||suffix) -noverify`
  → `CMS Verification successful`
- the same blob against the same content with **one byte flipped at offset 100**
  → `CMS Verification failure` / `CMS_SignerInfo_verify_content: verification failure`

So a detached CMS over the concatenation is the correct shape, and the oracle rejects a change
outside the gap. This is I-SG1 with an implementation we did not write.

## F2. `cms 0.3.0-rc.1` builds a detached signature OpenSSL accepts

The tree already carries `cms 0.3.0-rc.1` (pulled in by `p12-keystore 0.4.1`, per K24), but its
`builder` feature is not enabled by that path, so this is the first use of it.

Two facts that cost a build each:

- **The published `builder` feature does not compile on its own.** `cms 0.3.0-rc.1` builds against
  `rsa::Pkcs1v15Encrypt`, which is gated behind `rsa`'s `pkcs1v15` feature and is not requested by
  `cms`, so the feature is declared but unusable. Enabling `rsa = { features = ["pkcs1v15"] }` in
  the *consumer* fixes it. Without that the error is `no Pkcs1v15Encrypt in the root ... gated
  behind the pkcs1v15 feature`.
- **A detached signature needs the external message digest.** With `econtent: None` and a `None`
  digest, the builder succeeds and produces DER, and OpenSSL then reports
  `error reading messagedigest attribute` — a *silent* wrong answer if you only round-trip
  through the builder. Passing `Some(&Sha256::digest(content))` produces a blob OpenSSL verifies.
  This is the single most important fact here: the failure mode is a well-formed blob that
  verifies against nothing, which no amount of "it parsed" checking catches.

Measured result: 1411-byte DER for RSA-2048 + SHA-256 with one certificate, and OpenSSL returns
`CMS Verification successful` for it over the F1 content. `sha256(content)` as computed by Rust
and by `openssl dgst -sha256` agree byte for byte
(`f50258a9f1e83b274160e2c568c7f90f37d30fa852b9aa9b84d3f7aaf08d3fbe`).

## F3. Size, against the 8192-byte reserved gap

| blob | bytes |
| --- | --- |
| OpenSSL-produced, RSA-2048/SHA-256, signed attributes, no chain | 1565 |
| Rust `cms`-produced, same key, one certificate | 1411 |
| reserved gap (`CONTENTS_BYTES`) | 8192 |

A three-deep chain adds roughly 1.5–2.5 KiB of certificates. The gap holds the single-signer case
with wide margin and a small chain case with real margin. Over-long must still be refused, which
`SigningRevision::patch_contents` already does and `a_signature_larger_than_the_reserved_gap_is
_refused_not_truncated` already proves.

## F4. Dependency cost is smaller than K24 predicted, and differently shaped

K24 predicted a second `der` generation when `rsa 0.9` arrived. What actually happens:

- `cms 0.3.0-rc.1` requires `rsa 0.10.0-rc.20+`, `sha2 0.11`, `x509-cert 0.3`, `der 0.8`.
- The tree **already has both `sha2` generations** (`0.10.9` and `0.11.0`) in `Cargo.lock`.
- `der` stays at **one** generation (`0.8.3`) — measured in a scratch crate that actually builds
  the signer, not predicted.
- `rsa 0.10.0-rc.22` is a **release candidate**. It is not in the tree today.

So the "two `der` generations" risk did not materialise; the real cost is taking a `-rc` of `rsa`
as a production signing dependency, which is a decision-class question rather than a measurement.
Recorded in the unit report rather than decided silently.

## F5. `x509-cert 0.3` made the certificate fields private

`CertificateInner::tbs_certificate()` is a method, and `TbsCertificateInner` exposes
`issuer()` / `serial_number()` accessors. Field access (`cert.tbs_certificate.issuer`) does not
compile. Affects any code building an `IssuerAndSerialNumber` for `SignerIdentifier`.

## F6. `openssl cms -verify` fails on a correct signature unless `-binary` is passed

OpenSSL's `cms` subcommand treats content as S/MIME text by default and rewrites line endings
before hashing. A PDF's covered bytes contain bare line feeds, so the default invocation reports
`CMS_verify:content verify error` on a signature that is entirely correct.

Measured against the real save path's output: the default form failed, and the same command with
`-binary` succeeded. A reviewer who does not know this will conclude the signer is broken and start
changing the DER. Recorded because it is a false negative from an authoritative tool, not a bug.

## What these facts do *not* establish

- That a PDF reader accepts the result. F1–F2 are OpenSSL-level; the end-to-end claim needs the
  patched file opened and its signature resolved, which the substrate tests prove for the
  container and this unit must prove for the CMS.
- That `rsa 0.10.0-rc` is acceptable as a shipping dependency (F4).
- Anything about DocMDP, `/Reference`, or trust — those are later units (D-SG6, D-SG7).
