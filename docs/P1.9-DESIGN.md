# P1.9 Design — Fullscreen Reading Mode & Menu (v0.1)

Status: **implemented** (see §9 for what changed against this design).
Follows the same structure as `docs/P1-DESIGN.md`. Implementation must not proceed
past a frozen decisions table (repo rule: every phase freezes decisions before code).

## 0. Phase Goal

Distraction-free reading of the currently open document: one toggle puts the
window into OS fullscreen and hides the non-reading chrome (library sidebar,
search sidebar, document metadata). A dropdown **Menu** at the top gives
access to everything that already works — file opening, view options,
navigation, and the bookmark commands that exist in the backend but have no
UI yet.

Non-goal, explicitly: annotations, OCR, EPUB/DOCX, print/export, extra
documents in tabs. Anything the backend cannot do today does not appear in
the menu. Dead menu items are worse than no menu.

## 1. Ground rules from the codebase (verified, not assumed)

| Fact | Consequence for P1.9 |
|------|----------------------|
| `capabilities/default.json` grants `["core:default", "dialog:allow-open"]` | Menu + fullscreen are frontend work; **one** permission must be added (see D2) |
| `set_fullscreen` is *not* in `core:window:default` (tauri build.rs: `("set_fullscreen", false)`); `is_fullscreen` **is** | Calling `setFullscreen(true)` without the capability fails at runtime with a permission error — this is the #1 silent-failure risk and must have a regression test |
| Zero frontend deps beyond React + Tauri API | No dropdown library; hand-roll in house style |
| ThemeProvider = context + localStorage fast path + AppState durable copy | Reuse the identical persistence pattern for focus mode |
| ViewerPane owns page/zoom state internally | Menu-driven navigation needs an imperative handle, not a state lift (see D6) |
| Bookmarks backend commands exist and are tested; UI was never built | The Bookmarks menu section is a real feature, not a stub |
| `min-width 700` window | A single Menu button, not four dropdown roots, keeps the toolbar safe |

## 2. Frozen Decisions (P1.9)

| ID | Decision | Rationale |
|----|----------|-----------|
| **D1** | **Fullscreen = OS window fullscreen (`getCurrentWindow().setFullscreen`) + focus mode (hide sidebars + metadata) together.** They are two composable internal state flags driven by one user-facing toggle. | "Fullscreen for the PDF document" means an unobstructed page. Pure CSS hiding alone is *not* fullscreen; pure window fullscreen without hiding panes still shows library/search chrome. Composing keeps both usable independently later. |
| **D2** | Extend `src-tauri/capabilities/default.json` with **exactly one** permission: `core:window:allow-set-fullscreen`. No other grants. | Minimal grant surface for a local-first app. `is_fullscreen` is already covered by `core:window:default`. Decoration removal / dragging / maximize are not part of P1.9. |
| **D3** | **Do not restore OS fullscreen on launch**, even though a persistence pattern exists. Persist only the focus-mode/chrome preference (AppState key `reading.chromeHidden`, same best-effort semantics as `theme`). | An app that opens fullscreen-ed is hostile UX; the OS may also legitimately refuse. Focus-mode persistence survives restarts harmlessly. |
| **D4** | **Escape exits fullscreen** and also reverts focus mode *if focus mode was auto-enabled by entering fullscreen* (i.e. restores the pre-fullscreen chrome state). Pressing F11 again does the same. | Matches every PDF reader / browser. The subtle part: a user who had sidebars hidden *before* fullscreen must not have them un-hidden by an Escape. |
| **D5** | The menu is **one `Menu` button in `toolbar-left`** opening a single panel with labelled groups: File (Open…, exit fullscreen when active), View (theme, hide/show side panels, enter/exit fullscreen), Go (first / prev / next / last page), Bookmarks (add current page, per-document list with remove). Items without working backends are not present. | Fits `min-width: 700`. Single root = no focus-management complexity of stacked dropdowns. Reuses existing handlers. |
| **D6** | ViewerPane exposes commands via `forwardRef` + `useImperativeHandle`: `{ step, goToFirst, goToLast, getZoom, setZoom, getCurrentPage }` (names to finalise in code review). No page/zoom state is lifted to App. | Lifting viewer state into App is a large refactor that P1 avoided deliberately; a ref handle is contained and idiomatic React. The menu already lives in App, so this is the minimal bridge. Pre-render neighbour logic is untouched — it reacts to `page`/`zoom` state as before. |
| **D7** | A dedicated **⛶ fullscreen quick-toggle button** on `toolbar-right` (next to theme toggle) in addition to the menu entry. Both flip the same state; no separate state copies. | Discoverability. The user asked for "toggle"; a visible button is the shortest path, the menu is the discoverable one. |
| **D8** | In fullscreen+focus mode, the **toolbar stays visible** (containing Menu + exit control). Only sidebars, metadata block and error banner are hidden. | Hiding the toolbar entirely strands mouse users: the only exit left would be the keyboard. The slim toolbar is the escape hatch. |
| **D9** | Menu behaviour: closes on outside click, on Escape, and on item activation. `role="menu"/"menuitem"` with `aria-expanded` on the button; focus is moved into the panel on open and back to the button on close. Arrow-key traversal is a P2 nice-to-have, not mandated. | Basic a11y without building a focus-trap library. |
| **D10** | A Rust test asserts `capabilities/default.json` contains `core:window:allow-set-fullscreen` (parse as JSON, check the permissions array). | House pattern from CI's PDFium-skip assertion: silent permission loss must fail loudly. Pure-frontend regressions are otherwise invisible to `cargo test`. |
| **D11** | Fullscreen API failure (permission denied, unsupported) surfaces as an `AppError`-shaped banner message and toggles nothing in UI state. | The toggle must never diverge from reality; if the window did not change, the UI must not claim it did. |

## 3. State architecture

```
ReadingModeProvider (src/state/ReadingMode.tsx)
  ├─ isFullscreen: boolean        <- source of truth = the window itself
  ├─ chromeHidden: boolean        <- focus mode; persisted ("reading.chromeHidden")
  ├─ preFocusChrome: boolean|null <- snapshot for D4's restore
  ├─ toggleFullscreen(): sets window fullscreen; on success syncs chromeHidden
  |    (enter: snapshot chrome, set true; exit: restore snapshot)
  └─ toggleChrome(): independent hide/show side panels
```

- `isFullscreen` is **reconciled with the window**, not assumed: after each toggle
  we confirm with `isFullscreen()`, and a `tauri://resize` listener re-syncs if the
  OS exits fullscreen itself. Optimistic state + reconciliation prevents the
  "UI says fullscreen but window is normal" divergence (D11's enforcement).
- Provider shape deliberately mirrors `ThemeProvider` so review costs nothing.

## 5. UX spec (menu tree)

```
Menu
--------------------------------- File
  Open...
--------------------------------- View
  Enter fullscreen  F11            hidden when already fullscreen
  Exit fullscreen   F11            shown when fullscreen
  Hide side panels                 shown when chrome visible
  Show side panels                 shown when chrome hidden
  Light/Dark theme                 (existing toggleTheme)
--------------------------------- Go
  First page    Home
  Previous page  Left arrow
  Next page      Right arrow
  Last page     End
--------------------------------- Bookmarks
  Add bookmark (page N)            disabled when no document open
  - list of bookmarks, each with a remove button, click = go to its page
  (empty state: "No bookmarks yet" - shown, greyed, non-interactive)
```

F11 is registered by the provider (window-level keydown) so it works regardless
of where focus sits — mirroring how ViewerPane already registers arrow keys.
Accelerator labels are display-only in P1.9; binding them is P2.

## 6. Risks

| Risk | Mitigation |
|------|-----------|
| Missing permission -> `setFullscreen` denied silently at runtime | D2 + D10 test + D11 error path |
| OS exits fullscreen without our action | reconcile via `isFullscreen()` + `tauri://resize` listener (S3) |
| Toolbar overflows at 700px | one menu button only (D5); the quick-toggle is icon-sized |
| Focus/ARIA holes in dropdown | D9 minimal but correct; arrow-key nav deferred |
| Divergence between two fullscreen entry points | single state in provider (D7) |
| Menu open state vs fullscreen exit race | Escape handling lives in one place (provider), not per-component |
| Persisted `chromeHidden` hides panes with no obvious way back | Menu is always in the toolbar (D8), so an exit control is always reachable |

## 9. Implementation notes (what differed from the design)

Kept as-is: D1-D11, the menu tree, the permission grant (one permission, asserted).

Deviations, all deliberate:

1. **`toggleFullscreen` confirms by reading the window twice, not by trusting the
   requested value.** The first draft passed `!isFullscreen` (render-scope state) to
   `setWindowFullscreen` while deriving the expected result from a *separate* window
   read. Two sources for one decision is a race: a rapid double press could set the
   window one way and the UI the other. It now reads once, requests the inverse of that
   read, and verifies with a second read. Caught in self-review, not by a test -- there
   is no frontend harness to catch it.
2. **Escape is claimed by the menu via `preventDefault()`.** The provider checks
   `defaultPrevented` before leaving fullscreen, and Menu registers its handler in the
   capture phase. Without this, closing the menu with Escape also exited fullscreen --
   two visible effects from one keystroke.
3. **The transient fullscreen hide is never persisted (extends D3).** Entering fullscreen
   hides the panes, which would otherwise be written to `reading.chromeHidden`. Quitting
   from fullscreen would then relaunch with hidden panes and no fullscreen to explain it.
   The persistence effect skips while a fullscreen snapshot is live, so only
   user-initiated chrome toggles persist.
4. **The `.error-banner` hide rule was dropped.** Two reasons: the banner is a sibling of
   `.workspace`, so the selector matched nothing; and suppressing errors in reading mode
   is the opposite of what a reader wants.
5. **`getCurrentPage` is served from a ref.** The handle must stay stable across page
   turns, so the current page is mirrored into a ref rather than captured in the
   `useImperativeHandle` dependencies.

Verified: `tsc` strict clean, `vite build` clean, `cargo fmt --check` clean,
`cargo clippy --all-targets -D warnings` clean, `cargo test` = 147 lib + 1 (new
capabilities) + 2 extract + 3 memory, 0 failed. The capabilities test was confirmed to
fail with the grant removed.
