## 1. Why this is a separate phase

P2.7.6 shipped MECH-B: a replacement outside CP1252 embeds a subset of a bundled face,
written as a **simple** `/TrueType` font with one-byte codes, `/Widths`, `/Differences`
and `/ToUnicode`. That covers the Helvetica/Times/Courier families and nothing else.

A document whose text is set in a CID-keyed font still cannot accept a replacement beyond
what the original face covers. The write path refuses at `substitute.rs`'s `plan`, on a string
comparison of `FontInfo::subtype` against `"type0"` — the same block that decides
`GLYPHS_NOT_COVERABLE` and `SUBSET_BUILD_FAILED` — and the user sees
`TYPE0_EMBED_UNIMPLEMENTED` (or `GLYPHS_NOT_COVERABLE` where coverage is the actual limit). The
refusal is honest. It is also a large class of real documents: anything from InDesign or LaTeX
with a subsetted identity-encoded face.

Note what this refusal is *not*. It is not `substitute::is_type0`, which tests a font
dictionary's `/Subtype` and is used elsewhere for a different job: it closes the one-byte
reader in `decode_simple`, so two-byte codes cannot be split into plausible text, and
`decode_run_bytes` consults it to route a run to the two-byte reader. A guard on the
dictionary's `/Subtype` and a branch on `FontInfo::subtype` are two different checks that
happen to agree today; this phase changes only the second one.

P2.7.6's machinery does **not** transfer directly, and pretending otherwise is how a phase
gets underestimated. A simple font is a flat code → glyph table. A Type0 font is a
two-level structure: `/Type0` → `/DescendantFonts` → `/CIDFontType2`, with a CMap deciding
how byte sequences become CIDs, and a separate `CIDToGIDMap` deciding how CIDs become
glyph ids.

## 2. What has to be written

The five items below say *what objects exist*. They deliberately do not say what values go in
them: §3 fixes those, and item 2 and item 4 read differently once R2 and R5 are applied, so read
them together.

1. **`/W` array** — CID-keyed widths. Not `/Widths`; the format is different, mixing
   ranges and explicit `[cid [w1 w2 ...]]` pairs. Getting the ranges wrong produces a
   font that parses and lays out incorrectly, which is the silent-wrongness shape. R1 fixes
   the policy.
2. **`CIDToGIDMap`** — either a stream mapping CID → glyph id or the name `/Identity`.
   `/Identity` is only correct when CIDs already *are* glyph ids, which is true for
   identity-encoded subsets and false in general. R2 says which this phase writes and why
   that is honest rather than assumed.
3. **A `/CIDSystemInfo` triple** — Registry, Ordering, Supplement. R3 gives the values and
   explains why the triple already in `embed.rs`'s `/ToUnicode` is not the same triple.
4. **An encoding CMap** for the written font — a `Type0`'s `/Encoding` is how two-byte codes
   become CIDs, and the replacement's CIDs exist only in the font this phase writes, so the
   `/Encoding` this phase writes is its own. The source document's CMap is *read*, not
   inherited: it is R4's route 1, the authority on which existing code already denotes a
   character. Copying it into the new font is wrong, because its CIDs name the old font's
   glyphs.
5. **Two-byte encoding of the replacement run** — and the decoder is **already there**.
   `textlocate::decode_run_bytes` reads two-byte Type0 codes today: it skips the one-byte
   reader under `substitute::is_type0` and reads through lopdf's Identity-H machinery, which
   follows `/ToUnicode`. `cid::CidFont::decode` is the other half, and `cid::CidFont::encode`
   already returns two-byte codes. What is missing is a **writer-side sibling of
   `encode_simple`**: that function is one-byte by construction (`u8::try_from(code)`), and so
   are `Subset::codes: Vec<(u8, char)>`, `Subset::encode` and the `/Widths` indexing it drives.
   The decoder needs no sibling; the encoder does, and so does every `u8` in the subset struct.
   The round-trip gate must cover the new pair. R4 fixes the CID assignment the encoder uses.

## 3. The freeze: five rulings

Ruled 2026-10-29. Each names the evidence it rests on. R1 and R5 are measured in this
repository; R2, R3 and R4 restate what `cid.rs` already does on the read side, made binding
on the write side so the two cannot disagree.

### R1 — `/W` naming policy: sparse explicit pairs, `/DW` as the fallback, ranges only where contiguous

**Ruled.** Write `/DW` **always**, to the advance of a representative glyph of the subset (the
first assigned CID, in thousandths of an em). Write `/W` entries for the subset's own CIDs
only, in the `[cid [w1 w2 …]]` form, one list per contiguous run of CIDs. Never use the
`[cfirst clast w]` range form for a subset: the range form only pays when many consecutive
CIDs share a width, and our CIDs are consecutive *and individually measured*, so a range would
silently equalise advances the subset's own `hmtx` distinguishes.

`/DW` is not decoration. A CID the `/W` array does not name still has to measure, and the
program may be consulted for a glyph the array omits; `/DW` is what the renderer falls back to.
Naming neither is the state `cid.rs` already refuses to guess from (`CidFont::advance` returns
`None`), and writing a subset that reproduces that state would make our own output unmeasurable
by our own reader.

CID 0 is not written. It is `.notdef`, its advance is not the replacement's, and a `/W` entry
for it is a claim about a glyph no text run can draw.

Both array forms are already parsed by `cid.rs::width_table`, so a reader disagreement about
form is not the risk; the risk is a width that is individually wrong inside a form that parses.

### R2 — `CIDToGIDMap`: `/Identity` when, and only when, the glyph sits where its CID says

**Ruled.** Write `/Identity`, and make it true by construction: **the glyph ids are the source
document's CIDs, and R5 places each retained glyph at its own CID's slot rather than choosing a
number for it.** `/Identity` is correct exactly when CID equals glyph id, and that equality is
achieved here by honouring the document's numbering, not by inventing one. A stream map is
required only when the equality cannot hold — the case of a font this phase does *not* rebuild,
above all a **source** font whose ids are fixed by the producer's program.

The id space belongs to the document, and saying so is the point of this ruling. The bundled
face has a glyph order of its own that has nothing to do with the source's, so "reuse the
bundled program" and "keep the CIDs" cannot both hold unless the program is built with the
retained glyphs *placed at* their original ids, leaving gaps where the source had glyphs this
subset drops. That is what R5 requires; R2 only says the result may then honestly be called
`/Identity`.

The runtime decision is therefore not a per-document judgement but a per-writer one:

- **Our own subset** → `/Identity`, with CID = GID guaranteed by R5's placement rule.
- **Any font we did not write** → never `/Identity` on the strength of the encoding name.
  `cid::CidFont::resolve` already refuses to assume: it sets `identity_cid_to_gid` only from
  the descendant's `/CIDToGIDMap`, and closes route 2 when the value is not `/Identity`.
  The write side inherits that: appending a CID to a document font whose map is a stream means
  either extending the stream at the right offset or refusing, and extending it is only sound
  when the new CID's glyph id is known.

New characters, which the source never drew, take CIDs **above the highest the source used**,
in the order R4 assigns them. Nothing below that boundary is disturbed, which is what makes
row 6's byte comparison meaningful rather than merely hopeful.

The trap this ruling exists for: `/Identity` next to an encoding CMap that maps `0001` to CID
`0001`, where the *program* puts `A` at glyph 37. Everything parses, `/W` measures, and the page
draws glyph 37. `cid.rs`'s test `a_non_identity_cid_to_gid_map_closes_route_two_only` is the
read-side counterpart; the write side gets its own.

### R3 — `/CIDSystemInfo`: `(Adobe) (Identity) (0)`, fixed, and why the `/ToUnicode` triple is not a precedent

**Ruled.** Write `/Registry (Adobe)`, `/Ordering (Identity)`, `/Supplement 0` on the
descendant's `/CIDSystemInfo`. It does **not** vary per source document, because the ordering
names *our* CID space, and ours is identity-ordered by R2 and R5. A source document's triple
describes the source's CID space, which is exactly what this phase stops using.

`embed.rs`'s `to_unicode_cmap` writes `/CIDSystemInfo << /Registry (Adobe) /Ordering (UCS)
/Supplement 0 >>` — and that value is **correct for its own object and wrong for this one**.
Two different objects carry the same key name:

- Inside a **`/ToUnicode`** CMap, `/CIDSystemInfo` names the character collection the mapping
  targets. `UCS` is right: the destinations are Unicode code points.
- On a **`CIDFontType2`**, `/CIDSystemInfo` names the character collection the font's CIDs are
  drawn from. `UCS` there is a false claim: our CIDs are not Unicode code points, they are
  glyph indices. The honest value is the identity ordering.

So the constant is not copyable, and a literal transcription of the `/ToUnicode` header into
the font dictionary would be a plausible-looking error of exactly the silent class §6 names.
A `CIDFontType2`'s ordering is not something a viewer verifies; it is a claim in the file.

### R4 — CID assignment: `cid.rs`'s two routes, made binding on the encoder, and what happens when neither exists

**Ruled.** The encoder takes the same two routes as `cid::CidFont::encode`, in the same order,
and for the same reason:

1. **Reverse the source's `/ToUnicode`.** A code the document already names is *known* to draw
   the character the user typed, in the document's own words. Tried first, always.
2. **Program `cmap` → glyph id**, and **only** under `/CIDToGIDMap /Identity`, where a CID is a
   glyph id. This is the only route that reaches text the CMap never named.

Route 1 before route 2 is load-bearing and must not be reordered for convenience: a Wingdings
bullet is code `<001F>` in the document, but the program's `cmap` may map U+F0E0 to a different
glyph id, and taking that silently changes which picture is drawn. `cid.rs` states this in its
module doc and `a_non_identity_cid_to_gid_map_closes_route_two_only` pins the second half.

**When neither route is available, the phase refuses — it does not guess.** Route 1 requires a
`/ToUnicode`; route 2 requires both a parseable program and `/Identity`. A font with no
`/ToUnicode` never reaches this code at all: `Gate::FontEncoding` refuses it earlier, in
`font_admissibility`, with "publishes no /ToUnicode". What remains for this phase is the font
that *has* a `/ToUnicode` but cannot express a particular character through either route —
`CidRefusal::Uncoverable(char)`, which names the character because "cannot be encoded" alone is
not actionable.

One consequence worth stating plainly: for a **new** subset, route 1 is unavailable by
construction — the source CMap names the source's CIDs, and our subset has none yet. A
replacement character the source CMap does not name is therefore reachable in the subset only
through the *bundled* face's `cmap`, which is route 2 of a different program. The two routes
name the same operation at two different levels and the implementation must not conflate them.

### R5 — Subsetting: rebuild, never extend, and glyph ids are preserved, not reassigned

**Ruled.** A new subset is **rebuilt** from the bundled face by `embed::subset`'s glyph
extraction, and that rebuild must place each retained glyph **at the glyph id its CID already
names in the source document**, leaving an empty slot where the source had a glyph this subset
does not keep. Glyph ids are therefore *preserved*, not assigned. Extending an existing subset
in place is forbidden.

Placement, not assignment, is the whole mechanism, and the distinction is easy to lose. The
retained glyph's *outlines* come from the bundled face; its *id* comes from the document. The
two are unrelated numbers, and the writer's job is to put the bundled outline down at the
document's id. A writer that instead collects the bundled outlines and numbers them from 1 has
produced a valid font in which every retained glyph has moved — the silent corruption R2's
`/Identity` depends on not happening.

Why rebuild: `embed::subset` starts from `.notdef` and assigns ids in first-use order over the
*replacement text alone*. Under `/Identity` that renumbers every glyph relative to the
document's CIDs, so a retained glyph would move — and the page's untouched runs, which still
name their old CIDs, would draw different shapes with no parse error. The ordering that makes
`/Identity` legal is the document's, not ours; a subset that reorders is only safe with a stream
`CIDToGIDMap`, which R2 then forbids.

Why not extend: an existing subset carries only the glyphs a previous edit needed, and a
`FontFile2` cannot gain a glyph without rewriting `loca`, `glyf`, `hmtx` and `maxp` consistently.
Appending is therefore an optimisation, not a mechanism, and it is permitted only once a test
proves that retained ids did not move.

The invariant this ruling buys is checkable: **for every CID the previous document drew, the
new program must still draw the same glyph at the same id.** That is what §5's acceptance row
asserts, and it is the reason the row looks at runs the edit never touched.

Two mechanical notes. `embed::subset`'s `Subset` is simple-font-shaped — `codes: Vec<(u8, char)>`,
`first_char: u8`, `/Widths` indexed from it — so the CID writer needs a sibling carrying
`Vec<(u16, char)>` and u16 widths; the program-building half is reusable, the code assignment
is not. And the subset must keep the `ABCDEF+` prefix, because two rules key off it and both
bind here unchanged: `/BaseFont` must never carry the Reserved Font Name (P2.7.6 §4.2, OFL
condition 3 — subsetting deletes glyphs, so every subset is a Modified Version), and
`install_embedded_resource` derives the resource name from that six-letter prefix precisely so
two different subsets can never share one. A Type0 subset that dropped the prefix would break
both at once, and the failure would be a licence problem on one side and a silent repaint on
the other.

## 4. Refusal codes

Retiring `TYPE0_EMBED_UNIMPLEMENTED` is only safe if the situations it absorbs keep distinct
codes. It currently absorbs one situation that is *ours* and one that is *the document's*, and
a third that is already handled earlier.

**Two situations are already told apart, and need nothing new.** A run with no usable
`/ToUnicode` is refused by `Gate::FontEncoding` in `font_admissibility`, before `plan` runs —
its message already says "publishes no /ToUnicode". A user who disabled substitution is
`SUBSTITUTE_REFUSED`. Neither becomes this phase's problem.

**The third splits in two.** Today one code says "CID, and we cannot write a subset". After
this phase the writing works, and what can still fail is either a fact about the source
document or a bug in our builder. They must not share a code: one is answered by "use a
different font", the other by "report it".

| situation | code | disposition |
|---|---|---|
| the source's CIDs cannot be matched to glyphs this phase can write — a non-`/Identity` `CIDToGIDMap` on a font we must extend, or a CMap that names a CID the program has no glyph for | **`CID_MAPPING_UNSUPPORTED`** | **permanent document fact.** Retrying, updating or re-running the same edit on the same file changes nothing; only a different font or a narrower range helps. Remedy in the name: the mapping is the obstacle. |
| the bundled face covers the characters, but the CID subset could not be built | **`CID_SUBSET_BUILD_FAILED`** | **temporary — our bug.** Remedy: report it. Kept distinct from `SUBSET_BUILD_FAILED` for the reason that code is already distinct from `GLYPHS_NOT_COVERABLE`: the two builders fail for different reasons, and a report that says which one failed is a report someone can act on. |
| the build has no CID writer at all | `TYPE0_EMBED_UNIMPLEMENTED` — **retired by this phase** | temporary gap, removed rather than redefined, as its own doc comment already promises. |

Two properties these codes need, both borrowed from rulings already in force. Each names its
remedy, because `substitute.rs`'s module doc makes that a rule ("the remedy is in the code's
name because the next person reads the code, not this comment"). And neither may be collapsed
into the other or into the existing pair, because R3 of P2.7.6 already binds this programme to
"you said no" and "the font cannot do it" staying separate.

A third code is tempting and should be resisted: "the replacement character is not in the
bundled face" is `GLYPHS_NOT_COVERABLE` already, and it is checked *before* the Type0 branch
today. Reaching the CID writer at all means coverage has passed.

The P2.7.6 matrix in `tests/embed_acceptance.rs` is the model. Six rows, of which rows 1–5 are

| # | Fixture | Replacement | Expected |
|---|---|---|---|
| 1 | Type0, covered | covered, substitution allowed | embeds; PDFium renders and extracts it |
| 2 | Type0, covered | same, substitution disallowed | `SUBSTITUTE_REFUSED`, document unchanged |
| 3 | Type0, uncovered | `漢` in a Type0 run | `GLYPHS_NOT_COVERABLE`, not `TYPE0_EMBED_UNIMPLEMENTED` |
| 4 | Type0, untouched | no edit | byte-identical |
| 5 | Type0, non-`/Identity` map | covered, substitution allowed | `CID_MAPPING_UNSUPPORTED`, document unchanged |
| **6** | **Type0, multi-run, shared font** | **covered, edits one run** | **every untouched run renders identically; no retained glyph id moves** |

### Row 6 — the glyph-id preservation row

**What it asserts.** That the CID writer is a *rebuild* in the sense R5 requires, not a
renumbering. Concretely, three assertions, all of which must fail independently:

1. **Rendered identity, region by region.** Render the page before and after the edit through
   PDFium at the same scale, decode both PNGs to luma, and compare **the bounding box of every
   run the edit did not touch**. The boxes are computed from the untouched runs' own origins
   and advances, not from the edited run's, so a change anywhere else on the page is not
   excused by the edit. Byte equality of the untouched regions is the assertion; a tolerance is
   not acceptable, because the failure mode is a *different glyph*, which differs by far more
   than antialiasing noise.
2. **Glyph id, checked structurally.** For every CID present in the source program's `cmap` for
   a retained character, the new program's `cmap` must resolve that character to the **same**
   glyph id. This is the assertion that catches the failure even when the two glyphs happen to
   render identically — a space, or two weights of the same letter at small size.
3. **The edited run is not exempt.** The edited run's replacement must render where and as wide
   as the measured advance says (`/W` from R1), so a passing row 6 cannot be bought by leaving
   the edited run broken and the rest untouched.

**Why assertion 2 exists as well as assertion 1.** Rendering alone cannot distinguish "the id
moved and the glyph is identical" from "the id did not move". Both are visually correct today
and only the second survives a later edit to the retained character. Assertion 1 catches the
visible corruption; assertion 2 catches the invisible renumbering. A row with only the first
would pass against a writer that renumbered every glyph to an equal-looking one.

**The fixture it needs: `type0-shared-font-multi-run.pdf`. It does not exist and must be
written.** Requirements, each of which exists to make a specific assertion possible:

- One Type0 font resource referenced by **at least three runs on the page**, of which the middle
  one is the edit target. `cid_tounicode_page` in `testpdf.rs` has a single run and cannot be
  used as-is; a new builder alongside it is the natural home.
- The two untouched runs must draw **different characters** from each other and from the
  replacement, and at least one of them must be a character whose glyph would move under
  first-use renumbering — otherwise assertion 2 has nothing to distinguish.
- The resource must be **shared, not cloned**: a per-run font would let the writer renumber
  safely and the row would pass without testing R5.
- `/CIDToGIDMap /Identity` with a **program present**, since assertion 2 needs a `cmap` to read
  ids from. `cid_tounicode_page` embeds no program; `compressed_program_cid_page` adds one and
  is the closer starting point.
- Written to `tests/fixtures/`, because `embed_acceptance.rs`'s `fixture()` loads from disk and
  the existing matrix is file-based. Adding a builder in `testpdf.rs` *and* a file risks the two
  drifting; the file is the acceptance artifact and the builder is a convenience, as with the
  existing CID fixtures, so whichever is chosen the other must be generated from it.

**Whether comparable infrastructure exists.** Partly. `PdfProvider::render_page_at` returns a
`RasterizedPage { bytes, width, height }` whose `bytes` are **PNG**, and
`tests/export.rs` already decodes such bytes with `image::load_from_memory(..).to_luma8()`, so a
region comparison needs no new dependency — `image` is a regular dependency, already reachable
from tests. What does **not** exist is a helper that turns a run's origin and advance into a
pixel rectangle; the existing render checks in `embed_acceptance.rs` only ask "is there any ink
at all", which is deliberately coarse and must not be reused here. That helper is part of this
row's work, and it is the piece most likely to be written too loosely — a rectangle that is too
generous passes by covering the whole page, and one too tight fails on antialiasing.

### Mechanical consequences, to be handled in the same commit as the rows

- **`the_matrix_rows_are_all_present`** in `embed_acceptance.rs` asserts the file contains the
  literals `row1_`, `row2_`, `row3_` and `row4_`. Type0 rows cannot be named `row5_`/`row6_`
  without implying they belong to P2.7.6's matrix, so either the token list gains the new
  prefixes explicitly or the CID matrix gets its own enumeration test in its own file. The
  second is cleaner and keeps each phase's gate readable on its own; whichever is chosen, the
  guard must be extended in the same commit, or the new rows are collected without being
  required.
- **`ci.yml` pins `489` passed and `81` ignored on Linux**, and `ci_workflow.rs` asserts both
  literals. Every non-ignored row moves the first; every `#[ignore]`d PDFium row moves the
  second. Both numbers are measured, not incremented (`AGENTS.md`, "the count is literal on
  purpose"), so they must be re-measured and the commit message must say so.
- **Row 6 must not be `#[ignore]`d.** It is the row that justifies the phase; a version of it
  that only runs where PDFium exists is a coverage gap wearing a gate's name. The Windows job
  already fetches PDFium, so it can run there; row 5 and rows 1–4's non-PDFium halves run on
  Linux. Which of row 6's three assertions run on Linux needs deciding explicitly and
  recording — assertion 2 is pure `lopdf` and can run everywhere, assertions 1 and 3 cannot.

## 6. Standing constraints inherited from P2.7.6

- **Every guard mutation-verified with `scripts/mutate.sh`.** The mutant must be *caught*;
  a test that is green either way is a rehearsal (`AGENTS.md`, "Absence of evidence").
- **PDFium, not poppler, is the render authority.** A row that only poppler has seen is a
  coverage gap and must be recorded as one in the commit message.
- **A `/W` or `CIDToGIDMap` bug is silent.** It yields a plausible-looking PDF that draws
  glyphs at the wrong widths or wrong shapes. Tests must assert measured advances against
  the source face, not merely that the file parses.
