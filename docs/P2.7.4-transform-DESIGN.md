# P2.7.4 — Transforms: measuring rotated and skewed text

> Status: design, frozen for implementation.
> Replaces the `rotated-text` refusal shipped as hotfix H0 and widened by T-7.
> Target: **v0.7.0** (ruling Q7: one minor bump per phase; 0.8.0 is P2.7.5, 1.0.0 is P2.8).

## 1. What is refused today, and why the refusal was right

H0 refused runs whose text matrix is not axis-aligned. The reason was not that rotated
text is hard to *write* — it is not; see §6 — but that the **width gate compared the wrong
two quantities**.

`RawRun::advance` is measured along the **text axis**: it is the sum of the glyph advances,
which is what the renderer advances the pen by. `fits-width` then compared it against a
**horizontal** number. For a run rotated 90°, `advance` runs down the page while the box is
18pt wide, so a 114.67pt word was checked against an 18.12pt budget and either refused for
no reason or — worse, before H0 — accepted and written. The refusal removed a wrong answer;
it did not add a right one.

**The insight this phase turns on:** `advance` was never the broken quantity. The broken
quantity was the *other* side of the comparison. A replacement written into a rotated run
is drawn through the same text matrix, so its advance is along the same axis as the
original's **by construction**. Comparing advance to advance is therefore valid at any
angle, and needs no projection at all.

## 2. What the renderer actually reports (measured, not assumed)

Probe run on the existing fixtures with PDFium, which is the only component that knows where
ink landed. `origin` is lopdf's text-space origin; `box` is PDFium's rendered box.

| fixture | lopdf `origin` | `advance` | PDFium box (w × h) | PDFium char origins |
|---|---|---|---|---|
| `rotated_text` (`Tm` rotation) | (300.00, 100.00) | 114.67 | 18.12 × 111.41 | (300.00, 100.00) → (300.00, 197.34) |
| `rotated_by_graphics_matrix` (`cm`) | (72.00, 700.00) | 114.67 | 18.12 × 111.41 | (−400.00, 172.00) → (−400.00, 269.34) |
| `unrotated_text` | (300.00, 100.00) | 114.67 | 111.41 × 18.12 | (300.00, 100.00) → (397.34, 100.00) |
| `translated_by_graphics_matrix` | (72.00, 700.00) | 114.67 | 111.41 × 18.12 | (172.00, 750.00) → (269.34, 750.00) |

Three facts follow, and each changes the design:

1. **`advance` is identical in all four rows.** 114.67pt is the text-axis length in every
   case, including both rotations. It is already correct and already axis-independent.
2. **PDFium's char origins walk the advance axis.** For a 90° run they step in `y`
   (+17.33, +18.67, …), not `x`. The grid is therefore usable at any angle, but every
   span computation that folds `x0`/`x1` is meaningless for a rotated run.
3. **PDFium's box width for a 90° run is 18.12pt — the glyph *height*.** So `Quota::Box`,
   which trusts a strong pair's box width, would hand the gate a number 6× too small.

## 3. Four defects found while designing this

### 3.1 `RawRun::origin` is in text space, never composed with the CTM

`origin` is the text matrix's translation. For `rotated_by_graphics_matrix` lopdf says
`(72, 700)`; PDFium drew the glyphs at `(−400, 172)`. Every consumer of `origin` — run
pairing, the anchor window in `locate_span`, the merge gap — compares it against page-space
boxes.

Composing it fixes all three. Verified numerically against the renderer, `tm × ctm` in the
existing `matrix_mul` convention reproduces PDFium's origin exactly:

| fixture | `tm × ctm` translation | PDFium char origin |
|---|---|---|
| `rotated_by_graphics_matrix` | (−400.0, 172.0) | (−400, 172) |
| `translated_by_graphics_matrix` | (172.0, 750.0) | (172, 750) |
| identity | (72.0, 700.0) | (72, 700) |

This is a **prerequisite, not a nicety**: without it, no rotated run can pair with its ink,
so P2.7.4 would replace the refusal with an identical refusal under a different gate.

### 3.2 A translated `cm` is refused end-to-end, and a test says it is editable

`translated_by_graphics_matrix` is *not* rotated, so H0 does not refuse it. But its origin
is 100pt from where PDFium drew it, so `pair_run` finds no box and `describe_single` refuses
with `run-mismatch`. The user-visible verdict is **not editable**.

`a_run_translated_by_the_graphics_matrix_stays_editable` asserts that it is. It does so by
calling `resolve_gates` and `font_admissibility` — the font gates only — and never the
pairing path that actually refuses. The test is true about what it calls and false about
what its name claims. **This is a third vacuous-guard instance in this codebase** (after the
`ci.yml` `branches:` split and the SDK `MagicMock` test), and it is the reason §7.1 is a
gate on the phase rather than a cleanup task.

### 3.3 `Quota::Box` is unsafe for any non-horizontal run

As measured above, a rotated run's box width is its glyph height. `resolve_quota` returns
`Box(box_width)` for a strong pair with `smallest_containing`, before any check on the axis.
A rotated run that pairs strongly therefore gets a quota that is not a width.

### 3.4 Merge geometry is horizontal-only

`mergeable` compares `(head.baseline() - next.baseline()).abs()` — a `y` difference — and
`measured_gap`, which subtracts `x1` from `x0`. For two fragments of one rotated line, the
seam runs along `y` and the "baseline" difference is along `x`. Two fragments at opposite
ends of a vertical line would look like they share a baseline; two on adjacent vertical
lines would look far apart. Merging must be expressed in the run's own frame.

## 4. The model: an advance axis per run

Every run gets a unit **advance axis** `u` and a perpendicular **cross axis** `v`, both in
page space, from its composed matrix `M = tm × ctm`:

```
u = normalize(M[0], M[1])      // where one unit of text advance points
v = normalize(M[2], M[3])      // the glyph "up" direction
```

- **Unrotated:** `u = (1, 0)`, `v = (0, 1)`. Every existing formula reduces to today's.
- **Rotated 90°:** `u = (0, 1)`, `v = (−1, 0)`.
- **Skewed:** `u` and `v` are not perpendicular. That is handled by treating `u` alone as
  the measurement direction; nothing in the design needs `v` to be orthogonal to it.

A quantity that is currently "horizontal" is redefined as **along `u`**:

| today | under this design |
|---|---|
| span width `x1 − x0` | `max(dot(char_origin, u)) − min(dot(char_origin, u))` |
| baseline `origin.1` | `dot(origin, v)` |
| gap `next.x0 − head.x1` | `dot(next.origin, u) − (dot(head.origin, u) + head.advance)` |

For an unrotated run `dot(p, (1,0)) == p.x` and `dot(p, (0,1)) == p.y`, so **the unrotated
path is unchanged bit for bit** — a requirement, because 0.6.0's merge behaviour on
untagged horizontal text is the product.

`advance` itself is untouched: it is already a text-axis length, and §1 shows it is the one
number that was right all along.

## 5. Decisions

**Q1 — Is the width gate still meaningful for rotated text?**
Yes, and it becomes *more* exact. Both sides are text-axis lengths. `old_width` becomes the
run's advance (or its grid span projected on `u`, for a metrics-less font);
`new_width` is what the final font measures for the replacement. No projection of the
replacement is needed.

**Q2 — What replaces `Quota::Box` for a rotated run?**
A projected grid span if the grid located the text; otherwise the run's own `advance_exact`;
otherwise `Unmeasurable` (refuse). `Quota::Box` stays for unrotated runs only, where a box
width is a width. This is deliberate: the box is the right oracle only when the axis is
horizontal, and silently reusing it is defect §3.3.

**Q3 — How is `origin` composed without breaking the unrotated path?**
`RawRun` gains `page_origin: (f32, f32)` (`M`'s translation) and keeps `origin` as the
text-space pen position, which `Td`/`T*` accumulation needs. Pairing, `locate_span`'s anchor
and merge geometry read `page_origin`. `origin` stays for pen arithmetic. Composition is
exact for the identity CTM, so unrotated fixtures do not move.

**Q4 — Does skew work?**
Yes, by the same projection: `u` is whatever direction the matrix advances along. Skew
makes `u · v ≠ 0`, which affects nothing this design measures. It does mean the *box* is a
parallelogram's axis-aligned hull and is even less trustworthy than for rotation — another
reason `Quota::Box` is restricted to horizontal runs.

**Q5 — What about mirrored text (`det M < 0`)?**
Refused, with its own gate (`mirrored-text`). The advance axis still exists, but the glyphs
are reflected, so a replacement's advance runs opposite to the reading direction and the
caret/selection UX has no honest meaning. No fixture needs it; refusing is honest.

**Q6 — Does the write path change?**
No. `edit` replaces operand bytes and never touches `Tm` or `cm`, so a replacement inherits
the original transform. That is precisely why the phase is a *measurement* phase.

**Q7 — What about text rotated *per fragment* within one line?**
The axis is per run, so two fragments with different `u` cannot merge: `mergeable` gains
`axes_agree(head, next)` with a small angular tolerance. Different axes are not one line.

**Q8 — What stays refused?**
`MirroredText`; `Unmeasurable` when neither the grid nor the font can give a length along
`u`; `RunMismatch` when no ink can be paired; and `NestedXObject` unchanged. Rotated text
whose glyphs PDFium cannot locate still refuses — but now because it cannot be *measured*,
not because it is rotated.

## 6. Why writing is not the hard part

`Tm [0 1 −1 0 300 100]` draws text up the page. Replacing the bytes of a `Tj` operand
changes what is drawn, not where the pen starts or which way it advances, so the new text
flows along the original axis with the original `Tf`, `Tc`, `Tw`, `Tz` and `Ts` in force.
An edit can overflow the space the original occupied — which is exactly what `fits-width`
exists to refuse, and why Q1 must be right before the gate is removed.

## 7. Work items

Each is independently testable and each names the fixture that proves it.

1. **Compose the origin.** Add `page_origin`; route pairing, `locate_span`'s anchor and
   merge geometry through it. Prove with `rotated_by_graphics_matrix` (origin must equal
   PDFium's), `translated_by_graphics_matrix` (must pair, and `describe_runs` must report
   *editable*), and every existing unrotated fixture (must not move — asserted by the suite
   passing unchanged).
2. **Fix the mislabelled test.** Replace
   `a_run_translated_by_the_graphics_matrix_stays_editable` with one that runs the
   end-to-end `describe_runs` and asserts the user-visible verdict. This is the guard for
   item 1 and must fail when the composition is reverted. **Mutation-verify it** (standing
   rule).
3. **Axis-aware span and quota.** Project grid characters onto `u`; restrict `Quota::Box`
   to horizontal runs. Prove on `rotated_text`: the quota must be ≈114.67, not 18.12.
4. **Axis-aware merge.** Gap and baseline projection; `axes_agree`. Prove with a two-fragment
   vertical fixture (append `.`, expect one merged run) and with a control that must *not*
   merge (two vertical lines side by side).
5. **Remove the blanket refusal.** `font_admissibility` drops the `gates.rotated` branch and
   gains `gates.mirrored`. Prove: rotated text is editable; the width gate still refuses an
   overlong replacement *with the true numbers in the message* (e.g. "needs 200.0pt,
   available 114.7pt"); a `cm`-rotated run is editable; mirrored text refuses with its own
   gate.
6. **Version 0.7.0** in the six carriers, release-notes section, and the plan row moved to
   `[x]` only once gate and installer are both confirmed (Q9).

## 8. Acceptance

- Rotated runs are editable, with `fits-width` computed along the advance axis and its
  refusal reporting both true widths.
- A rotated replacement that fits is written, renders in place, and saves; the inverse
  restores the original bytes.
- `translated_by_graphics_matrix` is editable end-to-end (defect §3.2).
- Unrotated behaviour is byte-identical: the existing suite passes with no expectation
  changed except the two tests this phase deliberately rewrites.
- No new gate fires on any fixture that is editable today.

## 9. Risks

- **The merge frame is the riskiest change.** It touches horizontal text, which is every
  real document. Mitigation: `u = (1,0)` must reproduce today's arithmetic exactly, and the
  horizontal fixtures are the regression proof rather than a new expectation.
- **A rotated span can be located but mis-projected** if the grid's char origins disagree
  with the composed matrix (a producer that draws with both `Tm` and `cm` inconsistently).
  Mitigation: cross-check the projected span against `advance_exact` when both exist, and
  treat a disagreement beyond tolerance as `Unmeasurable` rather than picking one.
- **Selection geometry.** PDFium's box for a rotated run is a correct axis-aligned hull of
  rotated ink, so the overlay already draws in the right place; no frontend change is
  planned. If the caret proves wrong in practice, that is a separate finding, not a reason
  to keep the refusal.
