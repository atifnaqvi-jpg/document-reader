## 1. Why reflow is last

### 1.1 Corruption outranks inconvenience

Every phase before this one removed a **corruption** risk, or a refusal that protected one:

- P2.7.3 made text inside Form XObjects editable without editing a shared draw in place (B-7).
- P2.7.4 made rotated and skewed runs measurable before they were editable.
- P2.7.5 and P2.7.6 made non-WinAnsi and CID text settable without guessing glyph ids.
- P2.7.7 made Type0/CID embedding refuse rather than write a font it could not describe.

Reflow is different. Its failure mode is **inconvenience**: a line that is too long is refused
today, and the user has to shorten the text themselves. That is annoying, and it is correct. A
broken embed, by contrast, writes a file that renders wrongly and still opens.

So reflow ships last because it is the first phase whose worst case is "the user is
inconvenienced" rather than "the file is wrong". The ordering is not about difficulty. It is
about what is at risk while the phase is half-built.

### 1.2 Line-level only (C-2)

Ruling **C-2** is absolute on this: *"Reflow is line-level, named P2.8, derived from frozen
Stage 3. Paragraph-level stays out."*

Concretely, in scope:

- Spacing adjustment within a line.
- Moving trailing runs along the same baseline so a wider replacement fits.

Explicitly out, and refused rather than attempted:

- Wrapping a line to the next line.
- Changing the line count of a page.
- Moving any baseline.
- Repagination of any kind.

The reason wrapping is out is mechanical, not aesthetic. A wrap changes the number of lines on
the page; a changed line count moves every subsequent baseline; moving every subsequent
baseline is paragraph-level reflow under another name. There is no partial version of that
which is safe to ship, so there is no partial version at all.

## 2. The inverse model

### 2.1 Byte-range replacement is not expressible

**Byte-range splicing cannot be implemented in this architecture, and the reason is worth
stating precisely, because the natural design ("remember the bytes, put them back") does not
work here and will be proposed again.**

There is exactly one writer, `write_level` in `src-tauri/src/editor/textlocate.rs`. It builds
the stream from the parsed model:

```rust
let encoded = content.encode()?;      // Content<Vec<Operation>> -> bytes
// page: document.change_page_content(page_id, encoded)
// form: document.change_content_stream(form_id, encoded)
```

`Content::encode` (lopdf 0.45.0) walks the operation vector and emits each operation's operands
through `Writer::write_object`, separated by single spaces, with `\n` between operations. The
stream is **regenerated from the parsed structure on every write**.

Three consequences:

1. **A byte range has no address.** You cannot record "replace bytes 812..820" because no part
   of the model holds an offset, and after any write the offsets of everything downstream
   change. The address does not exist to be recorded.
2. **The encoder is not byte-faithful.** It normalises whitespace to `\n` and single spaces,
   re-formats reals, and drops comments (`%…`). Splicing preserved bytes into a re-encoded
   stream would produce a hybrid that no one had recorded and no test could describe.
3. **This is already true of every existing edit.** `revert` in
   `src-tauri/src/editor/textedit.rs` rebuilds the level through `read_level`, restores the
   operands in the model, and calls `write_level`. Today's undo is already model-level
   replacement. It merely happens to be byte-identical in the cases that matter, because the
   operands it touches are strings and a `BDC` name.

So the inverse must be expressed in the model's own terms.

### 2.2 Adopted: operation-vector replacement at `op_index`

**Decision: the reflow inverse records, for each write, the whole operation *vector* at one
`op_index` — old contents and new contents — and undo restores the old vector.**

```rust
/// One reflow write, as the inverse model records it.
///
/// Reflow creates positioning operators that did not previously exist, so an inverse that
/// can only *modify* an existing operand cannot express it. Recording the vector at
/// `op_index` makes insertion, deletion and modification the same operation: "the slice at
/// this index used to be `old_ops`, and is now `new_ops`".
pub struct ReflowOperation {
    /// 0-based page the run lives on.
    pub page: u32,
    /// Index into the decoded operation vector of the level named by `xobject_path`.
    pub op_index: usize,
    /// The operations at `op_index` before the reflow wrote. May be empty when reflow
    /// inserts; may be longer than one when reflow rewrites a run and its positioning
    /// operator together.
    pub old_ops: Vec<Operation>,
    /// The operations at `op_index` after the write. May be empty when reflow deletes.
    pub new_ops: Vec<Operation>,
    /// The content stream this write landed in. Empty is the page's own stream, matching
    /// the convention every existing inverse already uses.
    pub xobject_path: Vec<XObjectStep>,
}
```

This is deliberately **not** a generalisation of the existing `ContentOperation`. That struct
is also the serialised form persisted to SQLite, and generalising its `old_bytes: Vec<u8>` to
`Vec<Object>` would touch every existing inverse and its tests. A sibling struct is the smaller
change and matches the codebase's established shape, which is one struct per kind of write
(`FontSwap`, `PropertyClone`, `XObjectClone`) chained into one transaction.

### 2.3 Why not a "moved operand" struct

The obvious alternative is a sibling of `ContentOperation` that addresses a numeric operand
instead of a string one. It does not work, for one measured reason:

**Reflow creates operators that do not exist yet.** The shared fixture `two_run_line()` in
`src-tauri/src/editor/testpdf.rs` emits one `Td` followed by two `Tj`. Moving the second run
requires **inserting** a positioning operator, because there is no second `Td` to modify. A
struct whose only verb is "change the operand at `operand_path`" has nothing to point at, and
the index of an operator it would have to create is itself part of the write — so it cannot be
recorded in advance.

Vector replacement has no such gap: "the vector at this index was empty, and is now this `Td`"
describes an insertion exactly.

#### 2.3.1 The prediction, tested

**Confirmed, and the confirmation is what P2.8 case (a) ships against.** Case (a) is one run of a
multi-string `TJ` array widened, with the array's trailing fragments moved by an inserted `Td`.
Implementing it turned §2.3 from a prediction into two measurements:

| claim | result |
|---|---|
| "reflow creates operators that do not exist yet" | **holds** — the `TJ` at `op_index` becomes `TJ` + `Td` + `TJ` |
| "a struct whose only verb is *change the operand at `operand_path`* has nothing to point at" | **holds** — there is no operand path to the `Td`, because it did not exist |
| "the index of the operator it would create is itself part of the write" | **holds** — the `Td` lands at `op_index + 1`, which only exists after the splice |

So `ReflowOperation` is required, and undoing a case-(a) reflow without it would have to guess.

**A rejected alternative, and why the rejection is a choice rather than a proof.** The move can
also be expressed as a `TJ` kern inside the existing array: ISO 32000-1 9.4.3 displaces the pen by
`-n/1000 x Tf`, so a negative `n` moves the tail right, the array keeps its operand path, and the
write *would* fit a modified `ContentOperation`. That variant was built first and then replaced,
not because it is impossible but because:

- it encodes a **positioning** intent in an operator whose meaning is *kerning*, so the next
  reader of the stream — including a later reflow — cannot tell a layout move from a typographic
  adjustment;
- `Td` is the operator the format provides for exactly this, and it is the operator R2.1's
  semantics are stated about, so the write and the rule can be checked against one another;
- the brief specifies an inserted `Td`, and matching the brief is a reason.

The cost of that choice is `ReflowOperation`: `Td` insertion is what makes the vector-replacement
record necessary rather than convenient, and a `ContentOperation` cannot describe it.

The refusals case (a) added are enumerated in `src-tauri/src/editor/reflow.rs` as
[`ReflowRefusal`], each with a test that has been mutation-verified to fire. R2.1 is the one that
was found by measurement rather than by reading, and it is recorded under R2 above.

#### 2.3.2 R8 does not need a refusal for case (a), and that is a measurement

R8 was implemented as a `R8CrossesStructure` refusal, given a test, and then **removed**, because
the test could not be made to fire against a constructible state. The reasons are worth keeping
because they are properties of the format rather than of this implementation:

* A `TJ` array's elements are **strings and numbers only**. `Tf`, `BDC`/`EMC`, `Ts` and `cm` are
  operators, and no operator can appear between two elements of one array. So two fragments of
  the same array cannot carry different tags, faces, sizes or rises — the differences R8 exists to
  catch are not expressible.
* A fragment on another baseline or a different direction is dropped by `on_baseline` before any
  offset is computed, so it is never moved — that part of the original argument holds. **What did
  not hold** is the further claim that this covers everything `group_runs` would refuse: it does
  not, because a run can differ in *scope* while agreeing on every geometry `on_baseline` checks.
  `baseline()` is `origin.1 + rise` only; it carries no tag term. So a same-baseline run in
  another `MCID` survives the filter and reaches the `line_origin` computation. That gap is what
  **R8b** now rules on, and the sentence that used to be here ("Refusing would have been a second,
  weaker statement of a filter that has already run") was wrong: no such filter had run.

What replaces the refusal is an assertion (`one_tj_array_cannot_carry_two_tagged_units`) that the
invariant the argument rests on is actually true of the fixture, so the day a producer or a future
writer breaks it, a test notices instead of the reasoning quietly going stale. R8 still applies
unchanged to the general case, where a line's runs can span operations and levels.

[`ReflowRefusal`]: crate::editor::reflow::ReflowRefusal

### 2.4 The coarse-index risk, and the required pre-check

`op_index` is **coarse**. It names a position, not an identity. Two ways it goes wrong:

- A later ordinary edit inserts an operation earlier in the same level, shifting every
  subsequent index by one. The recorded `op_index` now points at the wrong operator.
- A level is rebuilt from a different starting point, and the same numeric index names
  different content with no change on the page to show it.

**Required pre-check, and it is load-bearing, not defensive:** before restoring, `revert` must
compare the recorded `new_ops` against the document's *current* operations at `op_index`, and
**refuse the undo if they differ**. This extends to a vector the discipline `revert` already
applies to bytes: it re-validates current operand bytes against `new_bytes` before writing
`old_bytes`. Undo must never write a vector into a position that no longer holds what reflow
put there.

Refusing an undo is a visible, recoverable failure. Writing the wrong vector into a live
content stream produces a file that renders wrongly and still opens, which is the failure class
this programme exists to prevent.

## 3. The content box

### 3.1 Which box

**Decision: the `/CropBox`, resolved through the page tree, read per page at edit time.**

`/CropBox` is what the reader shows. Reflow must not push text outside the region the user can
see, and the visible region is the CropBox, not the physical medium. `/MediaBox` is
over-generous: a Letter page with one-inch margins has its text already inset, and permitting
reflow into the margin is visibly wrong.

`/CropBox` appears **zero times** in `src-tauri` today. `/MediaBox` is read in exactly one
place, `media_box` in `src-tauri/src/editor/export.rs`, and only to place a watermark.

### 3.2 Default when `/CropBox` is absent

**`/CropBox` defaults to `/MediaBox`.** Both are *inheritable page attributes*:

- ISO 32000-1 §7.7.3.4 ("Inheritance of Page Attributes") makes them inheritable.
- Table 30 (entries in a page object) gives `/MediaBox` as **required**, and `/CropBox` as
  optional with the default **"the value of MediaBox"**.

So the resolution chain is:

1. Resolve `/CropBox` up the `/Parent` chain.
2. If absent from the page and every ancestor, resolve `/MediaBox` up the `/Parent` chain.
3. **If both are absent, error.** A page with no MediaBox anywhere in its chain is malformed,
   and silently inventing a box would turn a malformed file into a wrong reflow decision.

### 3.3 `export.rs`'s Letter fallback must not be reused

`media_box` in `export.rs` has a US Letter fallback of `(0, 0, 612, 792)`, and — measured — it
does **not** resolve inheritance at all: it reads `/MediaBox` from the page dictionary only, and
treats an inherited box as absent. Its doc comment says as much, describing the fallback as
applying "when it is inherited or absent".

That behaviour is acceptable for a watermark's diagonal placement. It is **not** acceptable for
a gate:

- A page that is actually A4 (595 × 842 pt) but inherits its MediaBox would silently be treated
  as Letter, moving the computed content box by roughly 17 × 50 pt.
- The reflow decision would then be wrong **with no error**, in the direction that permits
  text the user cannot see.

This is a reuse hazard, not a bug to fix here: `export.rs` is doing what a watermark needs.
P2.8 must have its own resolver, and the reason must be stated at the call site so the next
reader does not "simplify" the two into one.

### 3.4 Read per page, per edit, never cached

- The value is per page **and inherited**, so any document-wide constant is wrong by
  construction.
- It must be read at edit time because the document is mutable. A cached box could describe a
  page that has since been replaced.
- It is cheap: one dictionary walk, no PDFium call. The expensive measurement on this path is
  `measure` in `src-tauri/src/editor/runmetrics.rs`, not a box read.

### 3.5 Normalisation

Both boxes may be given with corners swapped and with a non-zero origin. They must be
normalised to `(min x, min y, max x, max y)` on read, exactly as `media_box` already does, and
the box must stay normalised because all reflow arithmetic happens in the box's own coordinate
space. A non-normalised box makes an available-width subtraction return a negative number,
which reads as "no room" and refuses every edit on the page.

## 4. Rulings

These bind P2.8. Each is stated with the reason it is a ruling and not a preference.

**R1 — A narrower replacement changes no operator.** The run is re-encoded and trailing runs
keep their positions; the gap widens.
*Acceptable. No compensation, no new gate.* Acrobat behaves the same way. Closing the gap
would require moving runs **backward** — an edit the user did not ask for, applied to text they
did not edit. Widening is visible and harmless; a compensating move is invisible and changes
layout. Stating the asymmetry explicitly matters, because otherwise it arrives as a bug report.

**R2 — A wider replacement that fits after shifting moves trailing runs on the same
baseline.** Each trailing run's new position is **line origin + measured prefix**, re-measured
through `measure` for the whole line.
*Never by incremental Δ.* `measure` returns `f32` per string; accumulating a Δ per run drifts
sub-point error across a line into a visible seam that grows with run count. One measurement of
the full prefix per run is the only formulation that cannot drift, and it is also what makes
the §5 guard comparable to the write. When the prefix is set by a `TJ` kern rather than by a
`Td`, what "measured prefix" includes is fixed by **R10**.

#### R2.1 — A `Td` translates the **line** matrix, so the prefix cannot be a pen delta

Measured, not reasoned. This is a separate reason from R2's drift argument, and it fails
*loudly* rather than by drift, so it is stated as a constraint on the operator and not on the
arithmetic:

* `Td tx ty` sets **both** `tm` and `tlm` to `translate(tx, ty) × tlm` (ISO 32000-1 9.4.2).
  `tlm` is the *line* origin — where the line was started — not the current pen. The pen's
  accumulated advance, held in `tm` since the last show operator, is **discarded**.
* Therefore `Td 40 0` inserted after a run that has already advanced 32.016 pt does not move the
  next run right by 40 pt. It moves it to *line origin + 40*, throwing the 32.016 pt away.

Measured on `kerned-line.pdf`, in the §5 expectation-reader test that builds the edit by hand:

| formulation | asked | `C` moved |
|---|---|---|
| `Td` as **pen + Δ** | 40.000 pt | **1.984 pt** (= 40 − 32.016 − 6.000 kern) |
| `Td` as **line origin + measured prefix** | 40.000 pt | **40.000 pt** |

Constraint: **every positioning operator reflow inserts must be computed as
`line origin + measured prefix`, never as `pen + delta`.** A pen-delta formulation is not
merely imprecise; it silently drops the advance of every run before the insertion point, and
the loss is proportional to how much text those runs contain — so it looks correct on a
one-character prefix and destroys a long one. R9 makes this worse rather than better: reflow
leaves the preceding runs' bytes untouched, so nothing else in the write records the width that
was thrown away.

This is why R2 says *line origin* and not *pen*: the two are the same number only when the run
being shifted is the first run on its line, which is exactly the case a one-run test would
cover.

**R3 — A wider replacement that does not fit the content box is refused.** `fits-width` stays
absolute.
*Unchanged. No new gate, no relaxation.* The refusal keeps its current shape — both measured
widths — but `old_width` for the **line** becomes the available width to the content box rather
than the run's own advance. That is a message change, not a gate change.

**R4 — Wrapping to the next line is out of scope.**
*Out.* A wrap changes the line count; a changed line count moves every subsequent baseline on
the page; that is paragraph-level reflow under another name, which C-2 excludes.

**R5 — A line that straddles levels is refused.** Text in a Form XObject and page-level text on
the same baseline cannot be moved as one line.
*Refuse.* There is no single content stream in which to write both moves. `read_level` and
`write_level` address one level; the walk flattens both levels into one run list with a per-run
`xobject_path`, so such a line can be *identified* as straddling but cannot be *written*
atomically. Writing two levels in sequence would make the edit non-atomic and break the plan's
own invariant that one-edit-one-undo stays absolute.

**R6 — A non-uniform form transform is refused.**
*Refuse.* `page_scale` is `None` under a non-uniform CTM, and the width gate in
`src-tauri/src/editor/textedit.rs` already refuses in exactly that case. Reflow inherits that
rule rather than inventing a factor: a non-uniform matrix maps a horizontal Δ to a
non-horizontal page displacement, and "the rest of the line" is then not a horizontal concept.

**R7 — Reflow moves runs; it does not re-admit them.**
*Absolute.* A run refused before reflow is still refused after it. Admissibility is a property
of the run's font, encoding and baseline, none of which reflow changes. The failure this
prevents is subtle: reflow calls `measure` on trailing runs to compute their new positions, and
it would be easy to let that measurement silently become an admissibility decision — turning a
refused run into an editable one as a side effect of editing its neighbour.

**R8 — ~~Reflow does not cross an MCID or structure boundary.~~ Superseded 2026-10-31 by R8b.**
Stated as written, R8 described something case (a) cannot do: the write replaces a single
operation (`operations.splice(op_index..op_index + 1, ...)`), and an `MCID` boundary is an
`BDC`/`EMC` *operator pair* — a separate operation. Text inside one `TJ` array therefore cannot
be moved across one, and no refusal can be reached. The original rule and the reasoning that
replaced its refusal are kept in §2.3.2 as the record of that measurement.

**R8b — Reflow establishes the line origin only from runs that would merge with the target.**
A same-baseline run outside the target's `merge_scope` must not contribute to `line_origin` (or
`line_right`); if one lies to the left of the target's own line start, reflow **refuses** rather
than guessing.
*Refuse.* This is the narrower property that **is** reachable, and it is a correction: the
earlier claim that `group_runs`' `A2` bound protects reflow is false, because reflow never
consults `group_runs`. `reflow_tj_array` takes `runs: &[RawRun]`, filters them by `baseline()`
alone — which is `origin.1 + rise`, with no scope term — and then takes `line_origin` as the
minimum `origin.0` over that set. `Td` is applied relative to the line matrix, so the offset is
correct **only if** the computed `line_origin` equals the true `tlm`. A run in another `MCID`,
on the same baseline, further left makes the computed origin too small, so the `Td` offset is
too large by exactly that difference and the tail is drawn right of where it belongs.

The failure is **silent in the worst way**: `moved_to` is computed as `line_origin + prefix`,
which algebraically reduces to `run.origin.0 + new_width` — the *intended* position — no matter
what `line_origin` was. So `ReflowApplied` reports the correct number while the ink is
displaced by `true tlm − line_origin`. A caller that trusted the returned position would write a
record claiming a move that did not happen. That is the corruption class this programme exists to
prevent, and it is reachable without any structure editing at all.

#### R8b.1 Why R8b refuses rather than correcting the origin

The obvious alternative is to compute the right `line_origin` — take it only from the runs in the
target's `merge_scope` — and carry on. That is rejected, and the reason is the shape of the
failure, not a lack of ambition.

`moved_to` is `line_origin + prefix`, and `prefix` is `(run.origin.0 - line_origin) + new_width`.
The `line_origin` cancels:

    line_origin + ((run.origin.0 - line_origin) + new_width)  ==  run.origin.0 + new_width

So the **number `ReflowApplied` reports is independent of `line_origin` entirely**. It is always
the position the write *intended*. If `line_origin` is wrong, the reported position is still
right, the ink is somewhere else by exactly `true tlm - line_origin`, and **nothing in the
returned record disagrees with anything else in it**. There is no internal contradiction for a
caller to notice, no failed assertion, no mismatch between two values that can be compared. The
document simply renders with its tail displaced, and opens again cleanly afterwards.

Correcting the origin would make the arithmetic right while leaving that reporting defect in
place: a caller comparing `moved_to` against the ink would still be comparing an intention
against a fact, and would go on being told they agree. Refusing is the only option that turns an
invisible wrong answer into a visible one, and a refusal is recoverable where a silent
displacement is not. The rule is therefore *refuse*, not *repair*.

*Scope note.* The general form — a multi-operation edit that genuinely moves text between
structure elements — remains out of scope for P2.8, because structure editing does not exist in
this tree. R8b is not that rule; it is what can actually go wrong today.

#### R8b.2 How R8b is enforced, and why it runs before R10b

**Implemented as `a_same_baseline_run_in_another_mcid_does_not_dislocate_the_tail` (R-2b), with
`a_run_outside_the_scope_does_not_set_the_line_extent` guarding the other half.** Both halves of
the ruled property are code, not just the refusal:

* the runs that would merge with the target are collected once (`in_scope`), and **both**
  `line_origin` and `line_right` are computed from that set only;
* a run outside the scope lying left of `line_origin` refuses with `R8b-scope-left-of-line`.

**The precedence over R10b is load-bearing, and it is a property of the format.**
`R10b-unattributed-kern` refuses *any* same-baseline run at a different `op_index`. No
constructible two-unit line can avoid one: a `BDC`/`EMC` pair is an operator pair, and a `TJ`
array's elements are strings and numbers only, so two fragments of one array cannot differ in
scope — which is exactly what `one_tj_array_cannot_carry_two_tagged_units` asserts. Run R8b after
R10b, therefore, and it is unreachable: measured, the fixture's `HI` produced
`R10b-unattributed-kern` where R8b was expected. Both rules refuse, so the precedence changes only
which *remedy* is named — and R10b would name the wrong one, "positioned outside this TJ array",
when the user's route out is to edit within one tagged unit.

R8b **not** refusing must stay reachable too, so R10b is scoped to `in_scope` as well. Scoped to
`on_baseline`, R10b refuses the right-hand neighbour that R8b's `line_right` exclusion is supposed
to ignore, and that exclusion becomes dead code: mutating `line_right` back to the full baseline
set then changes nothing observable. `a_run_outside_the_scope_does_not_set_the_line_extent` is
what makes it observable, and it is written against the committed fixture **plus one injected
run** for a measured reason — a wholly synthetic pair never reaches R4, because an empty document
fails at the content read first, so a synthetic version of this test passes whatever `line_right`
counts.

**R9 — Reflow never re-encodes a run it does not move.**
*Absolute.* This is the mechanical form of the corruption boundary. A run whose text bytes are
untouched cannot drift its glyph ids; a run re-encoded in order to "clean it up" can. The
cheapest safe implementation — moving runs with `Td`/`Tm` only, leaving every other run's bytes
alone — is also the one that satisfies this, which is why it is a rule and not implementation
taste.

**R10 — The measured prefix of a kern-positioned run includes that kern.**
Scoped deliberately: this holds only for a run whose start is set by a `TJ` adjustment **within
a single `TJ` array**. A run whose position also depends on a preceding `Tj`, or on a `Td`/`TD`
issued after the array began, is **refused** rather than measured.
*(i)* Excluding the kern makes the computed prefix disagree with where the renderer actually
drew the run, by exactly the kern — and §5 compares against rendered ink, so the guard's
expected position would be wrong by that amount and the guard would be asserting the defect it
exists to catch.
*(ii)* Refusing every kerned run would refuse most real lines: per-glyph `TJ` arrays with kerns
are what PowerPoint and InDesign emit, so the alternative is not a stricter rule but an
unusable one.
*(iii)* Including a kern the walk does not track — one that spans a `Tj`, or a `Td` issued
mid-array — would produce the same defect as excluding it, which is why the rule is scoped
rather than stated generally.

The arithmetic, because the sign is the part that is easy to get wrong: a `TJ` number `n`
displaces the pen by **`−n / 1000 × Tf` in text space**, and that displacement is then scaled
by **`Tz / 100`** along with everything else on the line (ISO 32000-1 §9.4.3 for the array
adjustment, §9.4.4 for the text-state scaling). So `n = −250` at `Tf = 24` and `Tz = 50` moves
the pen **+3.0 pt**, not +6.0: the double negative in `−n` makes a negative number widen, and
the half-scale halves it.

#### R10.4 — What the ruled scope becomes when it is enforced

Implemented as `a_kern_that_spans_a_tj_or_mid_array_td_refuses` (R-1b), and the ruling's wording
is left above unchanged. Two facts about the constructible shapes had to be established before
a refusal could be written, and both narrow *how* the scope is checked without narrowing what it
covers:

* **No operator can appear inside a `TJ` array.** Its elements are strings and numbers only, so a
  "mid-array `Td`" is not expressible — the same finding that removed R8's refusal (§2.3.2). Its
  reachable form is a **second array on the same baseline, started by its own `Td`**, which
  displaces the pen by a translation the target's array walk never sees.
* **A preceding `Tj` leaves no trace in the reported origin.** `TextMatrixWalk::step` is a
  deliberate no-op for a show operator, so after `Tj (WXYZ)` the next `TJ`'s fragments are
  reported at the line matrix origin while the ink starts an advance further right. That is why
  the shape needs a refusal rather than a correction: the reader's own origin agrees with nothing.

Both collapse to one property of the *run set*: every run on the target's baseline must come from
the target's own operation. `reflow_tj_array` therefore refuses with
`R10b-unattributed-kern` when any same-baseline run carries a different `op_index`. The check is
in the run set and not in the array walk because the walk cannot see the displacement — checking
it there would be checking a value that is already wrong.

#### R10.1 — The reader's kern term omits `Tz`, and that is a separate defect

`tj_fragment_origins` in `src-tauri/src/editor/textlocate.rs` computes the kern as
`pen_x -= number / 1000.0 * state.size`, with **no `horizontal_scale / 100` factor**. Every
other term on that line has it: `spaced_width` applies `* state.horizontal_scale / 100.0` to
glyph advance and spacing together. So on a page at `Tz ≠ 100` the reader's pen is wrong at
every kern, and a run's origin after a kern is displaced by `n/1000 × Tf × (1 − Tz/100)`.

**Fixed 2026-11-01 (plan T-8), separately from R10 as this section required.** The kern term now
reads `pen_x -= number / 1000.0 * state.size * state.horizontal_scale / 100.0`, so every term on
that line is scaled. Two guards hold it: the acceptance test named in R10.2 and a hand-built one
that needs no PDFium, because the acceptance test is `#[ignore]`d and therefore absent from the
Linux job while the defect is in the reader, not in the reflow.

**The reflow's own measurements were unscaled too (plan T-8b, landed 2026-11-02).** Fixing the
reader left `reflow_tj_array` measuring a *replacement* as the font's raw `w0` sum and its kern
term as `number / 1000 × Tf`, both without the factor. The line's origins and advances are
scaled, so placing an unscaled width into that space was `1 − Tz/100` too wide and the reported
tail landed past the ink: measured on `kerned-line-tz.pdf` at **136.704** against the correct
**104.352**, of which 29.352 pt was the width factor and 3.000 the kern. `RawRun` now carries
`horizontal_scale` and `reflow_tj_array` applies it to both, so the reader's kern term and the
reflow's cannot disagree about where a kerned tail starts. `shift` was already correct at `Tz 50`
only because it subtracted two quantities that carried the same unscaled kern; with both sides
scaled it is the scaled growth, and a guard asserts it independently.

**~~The same omission remains in the reflow.~~ RESOLVED 2026-11-02 (plan T-8b), as recorded just
above.** It was left as a separate task rather than part of T-8 because nothing in R-4 asserts a
position at `Tz != 100`, and changing a number with nothing watching is the failure this section
is about — so T-8b was written test-first and mutation-verified in both halves.

#### R10.2 — The fixture that would catch R10.1 does not currently test the reader

`kerned-line.pdf` and `kerned-line-tz.pdf` exist, and
`a_kerned_lines_glyphs_are_where_iso_9_4_3_puts_them_at_tz_50` is written against the second
one. It does **not** however call `tj_fragment_origins`: it computes its expectation in
`expected_fragment_origins` from hand-transcribed AFM constants and compares that against
PDFium's glyph grid. That is a correct test of *PDFium's* conformance to §9.4.3, and an
independent one by design. It is not a test of the reader.

Measured, not argued: replacing the kern term with `pen_x -= 0.0` — deleting it entirely —
leaves **both** kerned-line tests green at `Tz 50` and `Tz 100`. A test that cannot fail when
the implementation it would guard is deleted is not guarding it.

So the claim that "the `Tz 50` fixture would fail without the factor" was false as the suite
stood, and the task in R10.1 had to first **re-point the existing assertion at the reader**
(`tj_fragment_origins`) or add a sibling that does, and prove it red against the then-current
`pen_x` line before applying the factor.

**Done, and the sibling is `the_reader_puts_a_kerned_tail_where_pdfium_drew_it_at_tz_50`.** It
opens `kerned-line-tz.pdf`, takes PDFium's glyph grid, and compares the `CD` run's
`page_origin.0` against the ink. Red before the fix at the measured **94.008** against PDFium's
**91.008** — the predicted 3.000 pt, 60x the tolerance — and green after. It also asserts the
precondition R10.2 is about: that `Tz 50` moves `CD` by more than the tolerance from its un-scaled
position, so a fixture that lost its `Tz` cannot pass this test vacuously.
`the_kern_term_carries_the_horizontal_scale` states the same property over a hand-built text
state, which is what keeps it in the plain suite. Both were mutation-verified with the factor
removed from `tj_fragment_origins` and both fail; restored, both pass.

#### R10.3 — The kern is in the reported prefix, not in the `Td` offset

Implemented as `a_kerned_prefix_includes_the_kern` (R-1a). Two quantities, and they differ by the
kern, so writing "the prefix" once would have applied it twice:

* **`moved_to`** — the distance from the line origin to where the tail's ink actually starts —
  **includes** the kern. It is the number a caller compares against rendered ink, so it must.
* **the `Td` offset** — where the pen is put before the tail array — **excludes** it. The `TJ`
  number stays in the tail array and is applied there when the tail shows. Adding it to the
  offset as well was measured at 142.704 pt against the correct 136.704 pt; the first attempt at
  this rule made exactly that mistake.

`shift` is the growth alone, because the tail's old position carried the same kern. The three
relations are asserted separately, so a future change that collapses them fails on a number
rather than on prose:

```
moved_to = line_origin + (run.origin.0 - line_origin) + new_width + kern
td_offset = (run.origin.0 - line_origin) + new_width
shift     = moved_to - (run.origin.0 + old_width + kern) == new_width - old_width
```

*Scope.* This holds for a `TJ` number **between** the target's string and the tail's, inside one
array. A run whose position also depends on a preceding `Tj`, or on a second array on the same
baseline, is **refused** — that is R-1b, implemented above as R10.4.

## 5. The guard, which is written before the reflow

### 5.1 What it does

After a reflow write, re-extract the page's runs through PDFium and compare:

1. **every run on the edited line** — not only the edited run — against its recorded pre-edit
   ink position; and
2. **the edited run's text** against what was asked for,

and fail on any mismatch. A mismatch is a failure, not a warning.

### 5.2 Why it compares ink, not stream arithmetic

The whole failure mode is that **the stream says one thing and the renderer does another**. A
guard that compares the written operands to the intended operands proves only that the writer
wrote what the writer intended, which is the one thing that cannot be in doubt.

The measured precedent is the A7 defect: `RawRun::origin` is text-space and was never composed
with the CTM, so it does not pair with the ink PDFium actually drew, and four transform
fixtures refused as `run-mismatch` because the comparison was made against the wrong quantity.
Comparing stream arithmetic to stream arithmetic would have passed while the page was wrong.

The comparison is therefore on `PdfiumRun` / `PdfiumCharGrid` data obtained through
`extract_runs` and `page_runs_walked` in `src-tauri/src/editor/runmetrics.rs`.

### 5.3 Why it is written first

The guard needs nothing from reflow. It needs a fixture with at least two runs on one baseline,
a way to move one run, and PDFium. It can be written today against a hand-built operator edit —
insert a `Td`, re-encode — and it will pass, because a correct move is a correct move.

Then reflow is implemented **behind** it. Written afterwards, the guard would be fitted to the
implementation's assumptions, which is the failure mode it exists to catch. This is the same
ordering P2.7.7's row 6 used for Type0 embedding.

One consequence to accept deliberately: written before reflow, the guard has no caller and will
look like dead test code. That is the position row 6 was in, and the plan's answer applies — the
test asserts its reason rather than skipping. A test that returns early is a green pass wearing
a label.

**The inverse is a vector, and that is a record-shape change** (ruling A, 2026-11-02).
`ContentOperation` grew an `ops: Option<OpVector>` rather than a sibling type: a reflow writes
`TJ` + `Td` + `TJ` where one `TJ` stood, so the operator **count** changes and no `operand_path`
can address the write. An ordinary byte-level edit is the degenerate one-element case, so there
is no sum type to match on and every existing inverse keeps its meaning.

`OpVector` records both sides **encoded**, not as `Operation`s: neither
`lopdf::content::Operation` nor `lopdf::Object` implements `serde` in 0.45.0 (`content.rs` and
`object.rs` derive `Debug, Clone`; `Object` adds `PartialEq`), so the operands cannot travel as
themselves. Both sides use the same `reflow::encode` that `write_level` writes, so the record and
the stream are the same bytes by construction. The leg does not store its own length either:
`new_ops_len()` decodes the recorded stream, because a third number could disagree with its own
stream and an inverse that lies about its extent is worse than one that cannot be read.

**`revert()` takes the same discipline as a byte leg.** Before replaying, it re-encodes the
operations at `op_index` and refuses with `TEXT_RUN_MISMATCH` when they are not what the edit
left. Without it an undo would splice the old `TJ` into an index that now holds someone else's
operators — restoring a stream the user never had.

**The selection must end a word.** `try_reflow` declines unless the fragment's own text ends in
whitespace or the seam to the next fragment is wider than the merge tolerance. Editing `H` in
`Hi` and pushing `i` right duplicates a letter and leaves a gap: there the tail is the rest of
*this word*, not the rest of the line, and a merged edit is the machinery for it. This was not
foreseen; it was caught by the pre-existing `merged_width_refusal_quotes_both_widths` (whose
fixture is `Hi` split across two fragments), which failed only in the `--include-ignored` shape.

**Why that near-miss matters, and what it says about the pins.** The first post-change count read
`523 passed, 93 ignored` for the plain shape but `591` passed for `--include-ignored` — which does
not reconcile (`523 + 93 = 616`). The cause was not a lost test: `cargo test` **aborts the
remaining targets** after a failure, so the shortfall was one genuine failure plus five targets
that never ran. A single `test result: ok` line was all I had read. Re-counting across **every
`test result` line** and checking that the two shapes reconcile (`plain passed + plain ignored ==
ignored passed`) is what made it visible; the pin drop alone would have hidden it behind an
"expected" number.

**Measured.** Gate pins moved `531/93 → 523/93` and `624/0 → 616/0`. The drop is exactly **8 in
both shapes** and is accounted for rather than observed: retiring `undo.rs` removed its **10**
tests and this row added **2**, so `10 − 2 = 8`. The ignored count is unchanged at **93**, which
is the check that no PDFium-backed test was lost. `UndoStack` is retired with the module — 247

   by 0.9.0 that are reopened by 1.0.0.

5. **Whether R1's widening gap is ever closed by a later phase.** R1 rules that it is not
   closed *here*. It does not rule that the behaviour is permanent, and it should not be
   assumed to be.
